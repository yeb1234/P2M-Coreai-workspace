Concept / 2026.11 · 设计预演

让语言成为
操作入口，
而不是执行权限。

语控台不是“会敲命令的聊天机器人”。它把一句话拆成意图、上下文、能力计划、策略判定、预演、审批、执行和验证；模型只提案，策略与执行器保留最终决定权。

一句话不是命令。它先变成可检查的计划，再被策略、风险和审批约束；执行器只接受已签名的能力调用。

01 / 问题

不是运维不会操作，
是操作入口太贵。

查询、重启、改脚本、拉起整套系统，这些动作本身并不神秘。真正昂贵的是：找上下文、记顺序、判断影响、确认权限、事后解释。

现有“语言 → 豆包 → 系统”的能力已经证明入口可行，但它更像个人外挂。产品化要解决的不是“再多接几个工具”，而是把判断力变成可交接的控制面。

ENTRY COST

入口太散

查一个队列要进终端、记 Redis key；重启服务要翻 compose、确认容器名。每一步都在消耗注意力。

TACIT KNOWLEDGE

知识在个人脑子里

“先停谁、后起谁、哪一步能重试”散落在聊天记录和脚本注释里，换个人值班就重新学一遍。

EVIDENCE GAP

结果不可验证

命令返回 0 不等于服务恢复。谁在什么时候因为哪句话改了什么，往往要事后拼证据。

这个产品的核心承诺不是“AI 能操作”，而是“AI 操作错了，也有人能看懂、能叫停、能退回去”。

PRODUCT THESIS / 01
02 / 边界

先画不能做什么，
再谈能做什么。

权限不是一句“请谨慎操作”。它必须体现在能力目录、资源范围、审批级别和回滚路径里。语言可以模糊，系统不能。

点击左侧级别，查看允许的动作、审批方式与回滚责任。默认策略是拒绝，只有登记过的能力才有执行入口。

LEVEL 01 / SINGLE CHANGE

单点变更

1 人审批
允许重启一个无状态服务、重排一个失败任务、清缓存、暂停队列
前置资源存在、单资源范围、无同资源执行锁、变更窗口内
回滚恢复队列、重启回原状态、记录前后心跳
EXAMPLE“把 03 的 GPU worker 重启一下，只重启一个。”

永久拒绝 / NEVER

任意 shell、删数据或卷、改密钥、改防火墙 / IAM、DB schema、批量重启、外部写操作、生产凭据导出。这些动作不进入审批流，不提供“管理员绕过”，也不允许模型在计划里自行拼出来。

“不敏感脚本”不是“随便改脚本”：必须位于登记目录、无秘密、无外部写操作、通过静态扫描与语法检查、有 diff、沙箱预演、内容 hash、备份和回滚。满足不了，就降级成只读建议。

03 / 架构

模型提案，
策略裁决，
执行器兜底。

把“理解语言”和“拥有权限”拆开，是这套系统最重要的架构选择。模型负责把一句话变成候选计划；策略引擎负责说能不能做；执行器负责安全地做、验证、退回来。

点击架构中的节点，查看职责和“绝不允许”的边界。灰色连接表示证据/审计流，不表示执行权限。

CONTROL PLANE / LOGICAL VIEW
执行路径审批/风险证据链
SELECTED / POLICY

策略引擎

独立于模型的确定性判定层。输入是用户、环境、能力、参数、风险分和变更窗口，输出只有允许、拒绝、需审批或仅预演。

  • 模型不能修改策略，也不能把日志里的内容当指令。
  • 规则版本化；每次判定记录命中的规则和策略快照。
  • 默认拒绝；能力目录外动作没有执行入口。
04 / 生命周期

一句话要经过
九道门。

自然语言不是直接落到执行器，而是先被“翻译”成可检查的计划。每道门都有明确的输入、失败处理和证据；任何一步不通过，后面的门不会打开。

点击任一阶段，查看系统在这一步实际做什么、拒绝什么、留下什么证据。

PHASE 05 / PREFLIGHT

预演：先看会发生什么

风险分 0.31
系统做什么计算受影响服务、依赖上下游、预计停机、回滚耗时；生成 diff 和验证断言。预演本身不产生副作用。
拒绝条件影响范围超预算、无回滚路径、当前有同资源动作、变更窗口外，或预演发现会中断正在跑的任务。
留下什么证据风险分、影响图、diff、预计时长、回滚步骤、验证断言、预演时间戳和生成它的版本。
DRAFT→PREFLIGHT→AWAITING_APPROVAL→RUNNING→VERIFIED
05 / 操作预演

这是设计稿里的交互预演：输入或选择一句自然语言，系统展示它会被识别成什么能力、落到什么级别、需要谁审批、执行哪些步骤。只预演，不执行任何真实动作。

演示使用关键词分类，不是产品级意图模型；真实系统会走 schema、上下文解析和模型评估。

07 / 施工预演

如果让我来做，
先让模型互评，
再让另一种模型
拆台。

架构用 Claude/GPT 的最好模型做候选与互评，评审席位可以继续加模型；施工用 DeepSeek V4.1 Flash 做垂直切片和自测自评，收敛后打 0.9；再用 Kimi 做独立评估、测试和修改，打 1.0；人工复核后上传。

模型互评增加视角，不替代责任。最终架构由人类负责人签字，评审记录保留模型、版本、提示词和分歧。

W0 / FREEZE

冻结需求与禁区

先写清楚目标环境、资源清单、能力目录 v0、禁止动作、审批人、回滚责任。没有这份东西，后面的架构讨论都会飘。

OUTPUT / 需求基线 + 威胁模型
W1 / ARCH

三个候选架构，多模型互评

候选 A：聊天 + 自由工具调用；候选 B：能力型控制面；候选 C：事件驱动自治集群。用同一份证据、同一套评分维度盲评，记录致命缺陷和反对意见，人类架构负责人定案并写 ADR。

CLAUDE / GPT / KIMI / DEEPSEEK · 可加席位
W2 / UI

先设计审批人的 30 秒

指挥台、审批箱、拓扑、执行时间线、版本台账。评审标准不是“好看”，而是审批人能否在 30 秒内看懂：会发生什么、影响谁、出了事怎么退。

OUTPUT / 高保真控制室 + 可用性测试
W3–W5 / BUILD

DeepSeek V4.1 Flash 施工，切片收敛

L0 查询 → L1 单服务 → L2 脚本 → L3 整套启动。每个切片同时交付 schema、策略、预演、验证、回滚和测试；每轮自测后做自评，收敛后打 0.9，不直接宣称生产可用。

0.9 / 候选版本，不是生产版本
W6 / REVIEW

Kimi 独立评估、测试、修改

用不同提示词、不同测试集，不看施工方的自评结论。重点打歧义指令、提示词注入、重复点击、并发冲突、半失败和回滚失败；修复后打 1.0。

1.0 / 独立证据 + 回归测试
SIGN-OFF

人工复核，上传 1.0

复核能力目录、策略矩阵、审批链、回滚演练和审计样本；签署 release manifest；上传 1.0 发布包。没有人工签字，模型评分不构成发布许可。

08 / 风险与开放问题

先承认它会坏，
再设计它怎么坏。

这套系统的最大风险不是“模型不会操作”，而是“模型看起来会操作，实际把边界弄丢了”。所以策略、审批、验证、回滚必须比语言能力更早成熟。

风险后果处理
模型幻觉/计划错调用不存在的服务或错误参数能力 schema + 资源存在性校验 + 歧义追问
日志提示词注入模型被诱导调用危险工具日志只当数据；策略独立；能力目录不可由模型修改
审批替换/重放批的是 A，执行的是 B审批绑定 plan_hash；执行前重算；一次性 token
半失败服务停了一半、队列卡住持久化 checkpoint；恢复先验证；补偿/回滚
验证假阳性命令成功但服务仍坏多断言 + 观测窗口；失败强制回滚或转人工
