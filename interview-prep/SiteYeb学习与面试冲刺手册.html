01

项目全景分析

先回答三件事：它是什么、由什么构成、凭什么能打。这一章是整份手册的地基，所有面试故事都从这里长出来。

一句话定位

SiteYeb（代号 P2M / CoreAI Workspace）是一个本地优先（local-first）的个人 AI 工作台：用 React 19 做前端、FastAPI 做后端、SQLite 做数据底座，把「待办 / 日历 / 番茄钟 / 笔记 / 本地视频学习 / AI 助手」收进一个可扩展插件体系，并通过 LM Studio 与云端 OpenAI 兼容接口接入 LLM。它强调「先让个人工作流真的好用」，再逐步长出 AI、检索与任务编排能力。

面试一句话版：“我独立完成了一个本地优先的 AI 学习工作台，核心是给视频字幕库搭了一条完整的 RAG 检索问答管线，以及一套可取消、可恢复的异步任务系统——它让我把 LLM、向量检索、流式与前后端工程在一个真实产品里串通了。”

为什么这个项目能打（面试叙事核心）

真实亮点 · 面试主攻
  • 一条完整的 RAG 生产管线：查询改写 → 混合检索 → RRF 融合 → Rerank → 过滤压缩 → 生成，不是 demo，是挂在真实视频字幕库上的。
  • 务实降级文化：reranker 三级降级、检索 FTS→LIKE→近期兜底、LLM local/external 失败回退——每个依赖都留后路，这是工业级思维。
  • 异步任务状态机：可取消、可恢复、worker 重启自动 requeue，含「取消竞态」的防御处理。
  • 本地优先同步架构：IndexedDB 本地优先 → 登录后同步后端，debounce + pagehide flush，多端能接上状态。
  • 单文件多模检索：SQLite 同时承载业务、FTS5 全文与 vec0 向量，轻量但体系完整。
  • 190 个测试 + 边界用例（意图识别 13 条、番茄持久化、主题调度）。
诚实短板 · 面试主动认领
  • 密码用 SHA-256（应换 bcrypt/argon2）——README 也承认公网需加固。
  • JWT secret 为默认值，CORS allow_origins=["*"] 且带 credentials（按规范浏览器会拒收）。
  • 无 Alembic，靠手写 SQL 迁移；无速率限制、多租户隔离未做。
  • RAG 没有评测基座：检索质量靠手感，没接 RAGAS 这类量化评估。
  • 向量检索 vec0 无 JOIN，按 video 过滤是「多取 4 倍 + Python 过滤」。
  • RAG 问答是同步 llm.invoke，未上流式（llmStream.ts 只做了解析工具）。

短板怎么用：面试里主动说出「我知道这里不够好」，再补一句「我准备这样升级」——比藏着掖着强得多。这些短板恰好指向 RAGAS 评测、Alembic、bcrypt、流式输出、agent 编排这些高频考点，等于给自己铺好了「下一步」的答案。

02

RAG 全链路深挖

这是你项目的技术护城河，也是面试官最想听的部分。把它讲成一条「从原始查询到带引用的回答」的流水线，每个阶段你都能说清「为什么这么设计」和「挂了怎么办」。

完整管线（6 个阶段 + 意图前置）

入口处先做意图识别（前端正则给 hint，后端 LangChain 结构化输出做最终裁决），然后进入检索六阶段。下面这张流程图画清了每一步的输入输出与降级路径。

流程示意图（按源码逻辑绘制）：整体保证「任一层挂了都不白屏」——这是你最能体现工程成熟度的地方。

逐阶段深挖：面试怎么讲

意图识别：双通道裁决

  • 前端快判（src/lib/intentRouter.ts）：5 类意图（search/summary/video_context/learning_plan/chat），纯正则，0 延迟，同时产出 intent_hint。
  • 后端终判（intent_recognition.py）：LangChain with_structured_output，Pydantic 模型 IntentRecognitionResult(intent, confidence, cleaned_query, keywords, reasoning)，temperature 0.1。
  • 面试点：这是「规则快判 + 模型兜底」的经典混合模式——为什么不在后端只跑一次？因为正则 0 延迟、省 token、高置信场景直接采纳；模型则处理模糊语义。失败一律回退 general，不阻断主流程。

阶段 1 · 查询改写

把「用户怎么说」翻译成「文档里怎么写」。维护一张同义词/缩写映射表（js→javascript、爬虫→crawler、LLM→大语言模型）和反向索引；再按意图扩展变体（summary 模式去掉「帮我/请」等修饰词，保留核心主题）。

面试讲：「关键词召回覆盖的是'词面'，同义词扩展就是为了打掉'说法不一致'导致的召回缺口。变体数量我做上限控制（3 个），避免检索爆炸。」

阶段 2 · 混合检索

两路召回：FTSRetriever 走 SQLite FTS5（bm25 排序，三级兜底：FTS MATCH → substring LIKE → 近期/收藏视频）；VectorRetriever 走 sqlite-vec（bge-m3 1024 维，距离转分数 1-d/2）。查询扩展后逐变体多路检索再合并。

面试讲：「关键字保证精确命中与可解释，向量保证语义相关。FTS 和向量各有失效场景，混着来召回率才稳。」

阶段 3 · RRF 融合

把两路分数统一到 0–1，再按权重累加：score = norm(fts)×fts_weight + norm(vec)×vec_weight（默认各 0.5）。关键细节是用复合键 (video_id, start_sec) 去重，避免同一条字幕被两路分别命中导致分数虚高。

key = (it["video_id"], it["start_sec"])
combined[key] = {**it, "_hybrid_score": it["_norm_score"] * self.fts_weight}
# vec 命中同键时累加，否则新建

面试讲：「RRF 不是简单拼接，我用归一化加权融合保证两路可比；复合键去重防止同片段被双计。权重可配，这是给 rerank 留出足够候选池（3×limit）的关键。」

阶段 4 · Rerank（最有含金量的一段）

用 bge-reranker-v2-m3 对融合后的候选（rerank_pool_size = limit×3）重排序，提纯 Top-K。Reranker 是交叉编码器，比双塔向量更准，代价是慢，所以只对少量候选跑。

三级降级是这段的亮点：

  • 一级：走 POST /rerank（Cohere 格式，LM Studio 支持），拿 relevance_score 映射回文档。
  • 二级：/rerank 端点不可用 → _rerank_via_chat，让 LLM 输出排序索引 JSON，temperature 0。
  • 三级：连接失败/超时 → _fallback_rerank，用关键词覆盖率加权 0.6×原分 + 0.4×覆盖。

面试讲：「重排序是检索质量的上限提升器。我特意做了三级降级——宁可降级也不让检索链路挂掉。这也暴露了真实系统的常态：模型服务不可靠，必须把'失败'当成正常路径设计。」

阶段 5 · 过滤 + 压缩

RelevanceFilter：低于 min_score=0.15 的丢掉（优先用 rerank_score，其次 score_hint）；若全被滤掉，保留最高分那条，避免空结果。ContextCompressor：同一视频相邻 ≤3s 的片段合并成一段，再按总分控制 max_chars=6000（高分优先，最后可截断）。

面试讲：「进入 LLM 的上下文是 token 预算，压缩就是预算管理：合并碎片降低噪声，总量封顶控制成本与延迟。」

阶段 6 · LLM 生成（search vs summary）

根据意图选用不同的 RAG prompt：search 要求「只依据参考片段、给出视频标题+时间点、不够就明说」；summary 要求「提炼结构化大纲、标注时间点、说明缺失部分」。带 session 时先加载最近 10 轮历史再拼消息，回答与 references 一并入库。

面试讲：「同样是检索增强，'找一段话'和'总结一整课'的指令诉求完全不同，所以 prompt 分叉。回答要带可追溯引用（视频+秒数），这是 RAG 区别于裸 LLM 的核心价值——不编造、可验证。」

一套你要能脱口而出的「RAG 十问自检」

1) 为什么混检？2) 为什么加 rerank 而不是直接 top-k？3) 融合权重怎么定？4) 查询改写解决什么问题？5) 上下文为什么要压缩？6) 引用怎么保证不编造？7) 向量库和 FTS 的失效场景？8) 召回率 vs 准确率怎么平衡？9) 失败降级路径有哪些？10) 怎么评测检索质量（RAGAS）？

——每一条你都能用这章的内容接住；第 10 条是你的「下一步」钩子（见第 06 章精进路线）。

K1 · React 19 + TypeScript 工程化

  • 概念：组件即函数、Hooks 即状态副作用、单向数据流、TS 静态类型。
  • 读项目：src/components/video/useVideoPlayback.ts（一个视频播放器的 Hooks 拆分）、src/hooks/useCrossModuleSync.ts（跨模块同步）、src/components/layout/Header.tsx（大组件组织）。
  • 提取：一个页面拆成「数据 Hook + 展示组件 + 交互组件」的分层；Hooks 之间如何通过 Zustand 而非 prop-drilling 通信。
  • 练习：挑一个现有页面，把状态逻辑重构成一个自定义 Hook 并抽测试；或新增一个「闪卡复习」页面，复用插件注册体系。

K2 · Zustand + IndexedDB 持久化（本地优先）

  • 概念：全局状态、persist 中间件、Storage 适配、本地优先 + 云端同步。
  • 读项目：src/stores/aiStore.ts（persist + migrate + partialize + sanitize）、src/lib/idbStorage.ts（3 秒 debounce 写入、pagehide/visibilitychange flush、登录后切后端、scoped 命名）。
  • 提取：migrate 处理 schema 演进、partialize 控制持久化字段、损坏数据防御（hasCorruptText）、内存兜底（无 IndexedDB 时用 Map）。
  • 练习：给一个新 store 加「本地优先 + 登录后同步」双写，并验证刷新不丢状态——这是你项目里反复打磨过的点。

K3 · FastAPI + SQLAlchemy

  • 概念：ASGI、路由、Pydantic 校验、依赖注入、ORM 映射、事务。
  • 读项目：main.py（lifespan、中间件、路由挂载、SPA fallback）、routers/videos.py（业务最重的一个）、schemas.py、auth.py（JWT）。
  • 提取：依赖注入 get_db 的会话生命周期；统一错误转成友好 detail（connection/timeout/401/404 分诊）。
  • 练习：新增一个 /api/assistant/eval 端点（接 RAGAS），打通「检索质量可查」——直接解决你最大的短板。

K4 · SQLite：WAL / FTS5 / vec0 三合一

  • 概念：嵌入式数据库、WAL 并发、全文索引、向量扩展、触发器同步。
  • 读项目：database.py（PRAGMA journal_mode=WAL / busy_timeout=30000、FTS5 表 + ai/ad/au 三个触发器自动同步、vec0 建表、手写迁移）、vector_store.py（struct.pack 二进制向量、批量 upsert、增量索引 get_unindexed_segment_ids）。
  • 提取：为什么 local-first 选 SQLite 而非 PostgreSQL；FTS5 用 content 外置表 + 触发器保持一致性；vec0 无 JOIN 的限制怎么绕。
  • 练习：给字幕加一个「按视频聚合统计」的索引/查询，或写一段把 SQLite 导出到真实向量库（如 Qdrant/Chroma）的适配层。

K5 · LLM 接入与 Provider 抽象

  • 概念：OpenAI 兼容协议、多 provider、运行时策略、结构化输出、降级链。
  • 读项目：langchain_chat.py（_resolve_provider 按 llm_usage_policy 四策略回退；provider 探测 openai vs ollama）、intent_recognition.py（with_structured_output）、embedding.py（用 requests 直连绕开 httpx 兼容问题）。
  • 提取：把「选哪个模型」做成可配置策略而非写死——local 便宜私密、external 更强，四档策略覆盖成本/可用性权衡。
  • 练习：给聊天加流式（SSE），并把 llmStream.ts 的解析工具接到后端 stream=True。

K6 · RAG 检索管线

  • 概念：Embedding、向量检索、混合检索、RRF、Rerank、上下文压缩、引用生成。
  • 读项目：第 02 章已逐段拆解——rag_chain.py → hybrid_retriever.py → query_enhancer.py → reranker.py → retrieval_postprocessor.py 按调用链读一遍。
  • 提取：把「召回 → 融合 → 重排 → 压缩 → 生成」画成一张图（你面试要能白板画出来）；记熟每个阶段的参数与降级。
  • 练习：写一个 RAGAS 评测脚本，对 20 条真实查询算 faithfulness / context_recall / context_precision，量化当前质量。

34 道预测问答

点开看参考答案。分五类：RAG 技术 / 架构设计 / 异步与并发 / 前端与持久化 / 行为与业务。先自己答一遍，再对照。

A · RAG 技术
RAG你的 RAG 和普通「检索 + 拼接 prompt」有什么本质区别？

区别在把检索本身做成了有取舍的工程：我有查询改写（同义词/缩写扩展打召回缺口）、混合检索（FTS 关键字 + 向量语义双路）、RRF 融合、Reranker 提纯、相关性过滤 + 上下文压缩，最后才交给 LLM。而且回答带可追溯引用（视频 + 秒数），要求模型只依据片段回答、不够就明说——这是 RAG 区别于「把文档糊进 prompt」的核心：可控、可验证、不编造。

RAG为什么同时用 FTS 和向量检索？各自失效场景是什么？

关键字（FTS）强在精确匹配、可解释、快，但失效于同义改写（用户说「爬虫」字幕写「crawler」）；向量强在语义相关，但失效于专有名词、缩写、数字（向量对这些敏感度低、也可能误召回）。两者互补，混合召回率更稳。所以我还做了同义词扩展，专门缓解 FTS 的召回缺口。

RAGRRF 融合你怎么实现的？为什么用复合键去重？

先把两路分数各自归一化到 0–1，再按权重累加：score = norm(fts)×fts_weight + norm(vec)×vec_weight（默认 0.5/0.5）。去重键是 (video_id, start_sec)——因为同一条字幕可能被两路同时命中，如果不合并就会分数虚高、排名失真。权重和候选池（limit×3）都可配，给 rerank 留足空间。

RAGReranker 和向量检索的 Embedding 有什么区别？

Embedding（双塔）把 query 和 doc 各自编码成向量，用余弦/距离比相似度，快但粗——query 和 doc 之间没有交互。Reranker 是交叉编码器，把 query 和 doc 拼接一起过模型，能捕捉细粒度相关性，准但慢。所以正确姿势是：向量粗召回一大批候选（我取 limit×3），再用 reranker 精排到 Top-K——用算力换精度，但只在少量候选上花。

RAG你的 Reranker 三级降级具体是什么？为什么值得做？

一级 POST /rerank（Cohere 格式，LM Studio 承载）；端点不可用则二级，用 LLM 输出排序索引 JSON（temperature 0）；连接失败则三级，退到关键词覆盖率加权 0.6×原分+0.4×覆盖。值得做是因为真实系统里模型服务不可靠，链路要保证「哪怕降级也不挂」。这体现的是把失败当正常路径设计的工程思维。

RAG检索结果为什么要过滤和压缩？

过滤（RelevanceFilter，阈值 0.15）去掉低质量噪声，避免把无关内容喂给 LLM 干扰生成；压缩（ContextCompressor）先把同一视频相邻 ≤3s 的片段合并成一段，降低碎片化，再按 6000 字符总量控制——因为 LLM 上下文是 token 预算，塞太多会稀释注意力、增加成本和延迟。全滤空时保留最高分那条，避免「无结果」的坏体验。

RAG怎么保证 RAG 回答不编造？

三层：① prompt 约束「只依据参考片段、不要编造，不够就明说」；② 回答带结构化引用（视频标题 + 起止秒数），面试官可以回溯验证；③ 检索侧用阈值过滤掉低分噪声，从源头减少「无关上下文诱导幻觉」。诚实地说，引用可追溯是 RAG 控制幻觉最有效的产品手段。

RAG你的检索质量怎么评估？有没有量化指标？

这是我知道的短板：目前靠人工抽检 + 阈值调参，没有接 RAGAS 这类量化评测。我的下一步计划是：对一批真实查询标注 ground truth，跑 RAGAS 的 faithfulness / context_recall / context_precision，用数据驱动调 rerank 权重和阈值。这既补了短板，也是当前 Agent 岗位很看重的能力。

RAGsearch 和 summary 两种意图在检索上有什么不同？

search 是精确检索——找「特定片段」的位置，走精准匹配 + 精确回答 + 引用；summary 是覆盖式检索——要把整课讲清楚，查询改写会去掉修饰词保留核心主题，prompt 要求输出结构化大纲并标注时间点，还会说明「参考片段不足以覆盖哪些部分」。检索粒度一样，但改写策略和生成指令分叉。

RAG上下文窗口有限时，你的 token 策略是什么？

总量封顶（6000 字符）+ 高分优先：压缩时按 rerank_score 降序先保高分的，最后一条可截断。配合相邻片段合并，既保证质量优先，又严格控制成本与延迟。

B · 架构设计
架构为什么选「本地优先 + 单机全栈」而非微服务？

因为场景是个人/小团队/工作室在可信局域网内使用，核心诉求是数据私密、运维极简、迭代快。单进程 React+FastAPI+SQLite 完全够用，代价是并发和隔离弱——README 也明确说了「面向公网要先加固」。这是基于场景的取舍：不为不存在的规模提前买单。面试里主动讲清取舍边界比堆架构更有说服力。

架构FastAPI 的 lifespan 里你做了什么？

建表（Base.metadata.create_all）、确保运行时 schema（FTS/vec/索引）、启动文件监听、后台线程跑启动扫描和缩略图/雪碧图生成、拉起独立的 RQ worker 子进程（并起线程 drain 其 stdout 防 PIPE 死锁）；退出时 terminate worker。把 AI 任务从 API 进程里拆出去，长任务不阻塞接口。

架构为什么把 AI 任务放独立 worker 进程？

转录/摘要这类任务是分钟级长任务，如果同步跑在 API 进程会阻塞请求、拖垮并发。拆到 Redis+RQ 独立 worker：① 任务入队即返回，前端轮询状态；② 可取消、可暂停、可恢复；③ worker 崩了任务还在 DB/Redis 里，重启自动 requeue；④ 用 update_job_state 刷新后再写，防止取消竞态把已取消任务复活。

架构认证你用的什么方案？有没有隐患？

FastAPI OAuth2 + JWT（HS256，exp 2160h）。诚实说隐患：密码目前用 SHA-256 哈希，生产应换 bcrypt/argon2；JWT secret 是开发默认值；CORS 开了 allow_origins=["*"] 且带 credentials（按规范浏览器会拒绝）。这些我清楚，也写在 README 的「公网加固清单」里——本地工具够用，上公网前必须先处理。

架构你的数据模型怎么设计的？

核心表：videos（含转录/摘要/产物路径/AI 状态）、subtitle_segments（逐条字幕，供 FTS5 与向量索引）、ai_jobs（任务状态机 + 全部转录参数快照）、chat_sessions/chat_messages（对话历史 + references）、schedule_items（统一待办/日历/番茄）、user_data（前端状态的后端镜像）。AI 状态直接冗余在 video 行上，查询快。

架构没有用 Alembic，你迁移怎么做？为什么？

用 ensure_runtime_schema 手写幂等迁移：读 PRAGMA table_info 判断缺哪些列，ALTER TABLE ADD COLUMN 补齐，建索引、FTS 触发器、vec 表，全部 IF NOT EXISTS。早期 MVP 图快没上 Alembic，但我知道这不可扩展——下一步升级计划就是把迁移切到 Alembic。

C · 异步与并发
异步画一下你的 AI 任务状态机

queued → running（子阶段 extracting → transcribing → correcting-subtitles → summarizing → writing）→ completed / failed / cancelled。worker 启动时：running 且无存活 worker → requeue；cancelling 但 worker 已死 → 终结为 cancelled，避免卡死。

异步取消一个正在跑的转录任务，你如何保证它真的停？

三层：① RQ 层面按 job_id 取消/中断；② 真正的 ffmpeg/whisper 子进程会被 terminate，faster-whisper 迭代中也支持中断；③ 最关键的防御——update_job_state 在写状态前先 db.refresh(job)，如果 API 已经把它翻成 cancelled，就抛异常短路，避免 worker 用陈旧缓存把已取消任务复活回 running。这个竞态是真实踩坑后补的。

异步worker 重启后，正在跑的任务怎么处理？

启动时 requeue_interrupted_ai_jobs：把所有 running 的任务置回 queued 重新入队（因为无存活 worker 接），把 cancelling 的终结为 cancelled。同时 sync_db_queue_to_rq 把 Redis 不可用期间积压在 DB 的任务补推。这让「机器/worker 挂了」变成可恢复事件而不是丢数据。

异步数据库与 Redis 双队列怎么保持一致？

DB 是权威源（任务持久化），Redis/RQ 是执行队列。Redis 正常时任务同时入 DB 和 RQ；Redis 不可用时任务先进 DB，worker 启动或恢复时用 sync_db_queue_to_rq 把积压任务补推进队列。状态更新始终以 DB 为准，worker 每次写前 refresh，保证多组件视角一致。

异步Windows 上跑 RQ 你遇到什么问题？

RQ 的 death_penalty 依赖 Unix 信号，Windows 不支持。我用 NoOpDeathPenalty 覆盖它，自定义 WindowsWorker。副作用是 worker 用 SimpleWorker 在进程内跑 job，job 被强杀时 worker 进程会死，需重启——我用外层 while 循环 + 2s 退避让 worker 自动重启。这类平台适配是个人全栈项目常见的真实工程挑战。

异步转录的 GPU/CPU 双路线你怎么设计？

CPU 路线用 faster-whisper（通用，int8、线程数 = CPU 核−2）；外部引擎路线用 whisper.cpp，本机为 A 卡做了 Windows 兼容层。GPU 部分跟本机环境绑得比较深，所以 README 标注了「非相似环境需改」，CPU 路线保持通用——这是「环境绑定逻辑」和「通用逻辑」分离的实践。

D · 前端与持久化
前端「本地优先」的同步策略具体是什么？

用 Zustand persist + 自研 idbStorage：状态先写 IndexedDB（Dexie），写入做了 3 秒 debounce，并在 pagehide/visibilitychange=hidden 时 flush 掉待写，避免刷新丢状态。登录后带 token 时改走后端 user_data，未登录走本地。部分高频状态（番茄/插件/UI）立即写不 debounce。IndexedDB 不可用时降级到内存 Map——每层都有兜底。

前端为什么状态持久化要加 debounce？

避免每次 set 都触发一次磁盘/网络写——番茄钟秒级计时、拖拽排序等高频操作会写爆 IndexedDB 和请求。debounce 到 3 秒合并最后一次写入，再在页面隐藏时强制 flush，兼顾性能和「不丢最后状态」。partialize 只持久化必要字段，还控制消息只留最近 50 条。

前端store 的 schema 升级你如何处理？

Zustand persist 的 migrate + version：读旧数据时做清洗——校验字段类型、剔除损坏文本（hasCorruptText 检测乱码）、归一化 endpoint、兜底模板。这样升级不炸历史数据，还能防御持久化被写坏的情况。

前端番茄钟的混合同步你怎么实现？

浏览器本地每秒计时保证流畅，后端只保存关键事件和 15 秒运行快照；配置、历史、运行态拆成三个后端 user_data（v2 三件套）。这样局域网多设备刷新能接上当前状态，又不至于每秒打后端。这是「前端体验」和「后端权威」的平衡。

E · 行为与业务
行为这个项目是你一个人做的，你怎么保证代码质量？

三层：① 测试锁边界——190 个 Vitest 用例覆盖意图识别（13 条）、番茄持久化、主题调度、日期/时区等最容易回归的逻辑；② 构建门槛——改前端至少跑 npm test + npm run build，后端跑 compileall；③ 踩坑记录——docs 里有详尽的「今日踩坑与维护记录」和技术报告，把每次修的根因沉淀下来，避免重复踩。代码是给自己用的，但质量习惯是职业的。

行为你踩过最深的坑是什么？怎么爬出来的？

取消竞态算一个：worker 端在 summarize/write 期间，如果 API 已把任务翻成 cancelled，worker 用缓存对象继续写会把它「复活」成 completed。根因是 expire_on_commit=False 导致缓存陈旧。修复是 update_job_state 写前先 db.refresh(job) 校验，失败短路。这件事让我学会了多进程写同一状态的竞态，必须回到权威源确认再写。

行为如果让你加一个功能，你会怎么开工？

先用现有插件体系注册一个最小可跑页面，再把数据层打通、补测试、跑构建。举例：加「RAG 检索质量评测」——新增 /api/assistant/eval 端点 + 一个评测页面，接 RAGAS 对真实查询算三个指标，量化调参。做完既补短板，又是一次完整的功能交付。

行为为什么这个项目适合你投的 Agent / RAG 岗位？

它覆盖了 Agent 岗位的核心链路：意图识别（规则+模型混合）、检索增强（混合检索+Rerank）、任务编排（异步状态机）、多模型接入（local/external 策略）。它不是 Demo，是真实在用的产品，我理解每一层为什么这么设计。而且我有英语优势，适合出海/跨境业务——能把英文技术文档和海外模型生态直接用起来。

行为你英语不错，这对你的技术工作有什么加成？

能直接读 LangChain/LangGraph/RAGAS 的一手文档和论文、跟进最新模型生态，也能在需要读英文产品/跨境业务的需求上无缝衔接。面试官可以自由切换考我英文技术表达。

行为你未来一年想往哪个方向精进？

把「本地优先 RAG 工具」往「真正智能的 Agent」演进：① 给检索接 RAGAS 量化评测，用数据驱动调优；② 把意图识别+模板切换升级成 LangGraph 的多步 Agent 编排；③ 把同步 RAG 问答改成流式；④ 安全加固（bcrypt、Alembic、限流）。这些方向正好对应 Agent 工程的核心能力，我会拿这个项目持续当试验田。

行为如果团队要多人协作，这个项目哪里要改？

① 认证升级——bcrypt + 强 secret + 正确的 CORS 策略；② 引入 Alembic 管理迁移；③ 加角色/权限和多租户数据隔离；④ 加限流、审计日志；⑤ 部署走 HTTPS 反向代理 + 访问控制；⑥ 视频目录做权限隔离。README 里我已经列了这份加固清单，方向是清楚的。

行为你最大的短板是什么？

技术上，我的项目缺少量化评测和自动化运维——RAG 质量靠手感、迁移靠手写 SQL、没有 CI。我正在补：接 RAGAS、上 Alembic、给仓库配 CI 跑测试和构建。过程上，个人项目让我习惯了单兵作战，所以我也在刻意练习「把设计和取舍讲给团队听」的沟通方式。短板我会主动说，同时给出正在推进的解法。

三条精进线

线一 · 技术纵深：从「会用」到「能做对并说清为什么」

  1. RAG 评测与调优（你已计划学 RAGAS）：给项目接 RAGAS 的 faithfulness / context_recall / context_precision，建立基准后调 rerank 权重、阈值、分块策略，用数据说话。这是当前 Agent 岗最稀缺的能力。
  2. Agent 编排升级：把「意图识别 + 模板切换」升级成 LangGraph 多步编排——检索 → 判断是否够 → 决定要不要二次检索 / 调工具。你的正则+结构化输出已经是最好的入门锚点。
  3. 进阶检索：分块策略（semantic / 重叠）、query 改写用 LLM 而非规则表、多路召回 + 更好的融合；了解 Chroma / Qdrant / Milvus 等真实向量库与 sqlite-vec 的差异。
  4. 流式 + 长任务：把 RAG 问答改 SSE 流式；任务系统加重试上限、指数退避、超时熔断。
  5. 工程深度：Alembic 迁移、CI（GitHub Actions 跑测试+构建）、bcrypt、限流、Docker 部署。把「个人工具」推向「可交付小团队」的工程底线。

线三 · 职业路径：让项目和目标岗位互相成就

  • 定位：你的组合（全栈 + RAG/Agent + 英语）很适合出海业务 / 综合型 AI 工程岗——既写前端交互，又管检索与 Agent 链路，还能对接英文模型生态。
  • 持续开源：把项目文档化、MIT 开源，PR 里写清架构决策。面试时丢出链接，可信度远超口头描述。
  • 跟随生态：LangChain → LangGraph → LangSmith 的评测/可观测；关注 RAGAS、Dify、Coze 的实践，用你的项目做对照实验。
  • 建立作品节奏：每 2–4 周在项目上落地一个「能讲 5 分钟」的新能力（流式 / 评测 / Agent / 加固），保持持续产出。

记住这件事：你不是在「为面试做一个项目」，你是在持续打磨一个真实好用的产品，面试只是顺带的复利。项目越真实、迭代越持续，面试就越有东西讲——这比任何话术都硬。
