# P2 7.2 Lite：云上轻量 demo 与 2GB 共享数据底座

> 状态：现行（2026-11-20 实测）
>
> 分支：`feat/p2-lite`，已合并 `main`（2026-11-20 收尾）
> 默认入口：`http://127.0.0.1:12305`，API `http://127.0.0.1:12705`；本机全项目并存时用 `12315` / `12715`

## 结论先说

P2 Lite 不是把完整版“隐藏几个菜单”，而是独立 profile：

- 不导入视频、分类、AI 任务、检索、学习路径、观看事件、ops 七组路由；MCP 路由保留，但只暴露 Lite 实际可用的工具；
- 不建 `content_chunks` / `content_chunks_history`，不要求 PostgreSQL 安装 `vector`；
- 不启动视频扫描、缩略图、embedding 预热、雪碧图、内嵌转写 worker；
- 只保留 Agent、面试题、笔记、待办、日历、时间中心、番茄钟、统计、设置这些 OLTP 页面，另加 3 个不接后端的静态产品演示页；
- 健康检查按 Lite 口径只查数据库、LLM 配置、站内数据和 Lite 能力边界，不把 GPU、whisper、视频库判红。

实测本机空闲时 P2 Lite 两容器约 **189.5 MiB**；4 路并发 Agent 峰值 **189.8 MiB**（backend 177.7 + frontend 12.1）。共享 PG 空库约 78 MiB，Redis 约 3.9 MiB。

> “2GB”指共享 PostgreSQL 容器的内存上限，不是整台云主机只有 2GB。整机建议 4GB 起步；如果整机真的只有 2GB，必须把 PG 的 `shared_buffers` 降到 384MB 并下调 `mem_limit`，否则 P1 + P2 + PG 会一起抢内存。

### MCP 与能力清单

Lite 的 `/api/mcp/tools` 返回 11 个工具：

`calendar_create`、`get_interview_question`、`get_lite_learning_status`、`note_create`、`note_detect_actions`、`note_polish`、`note_summarize`、`search_interview_knowledge`、`search_interview_questions`、`search_notes`、`todo_create`

`registry.py` 的 `active_tools()` 以当前 `list_skills()` 能力包为白名单，再加 6 个原生笔记/待办/日程 MCP 工具；`call_tool()` 对 Lite 不可用工具抛 `KeyError`，不会出现“清单里没有、调用却穿透到视频检索”的情况。完整版仍返回全量 MCP 工具。

`/api/assistant/capabilities` 在 Lite 下只返回 10 个 Agent 工具：能力包工具 + `PERSONAL_ACTION_TOOLS` + `ask_user`。`search_videos`、`get_learning_profile`、`get_my_learning_path`、`recommend_next_videos` 不再混进 Lite 清单；完整版仍是 18 个。

前端 `AIAgentPage` 在 Lite 下使用 `LITE_TOOL_SNAPSHOT`、`LITE_SKILL_SNAPSHOT`、`LITE_ASSISTANT_INTENTS`，MCP 总数按 11 回落。接口短暂失败时不会再显示完整版工具数，也不会出现“实时清单读取失败”后仍展示视频推荐能力。

### Lite 健康检查

`/api/admin/health` 在 Lite 下不再复用完整版检查项，只查：

- 数据库：`SELECT 1`；
- LLM 配置：外部模型是否配置；
- 站内数据：私人笔记数、Todo 数；
- Lite 能力边界：Lite 能力包与工具清单是否可用。

不检查视频目录、ffmpeg、whisper.cpp、CUDA/GPU、Ollama、AI 队列、视频库。数据库详情只回传 `host/port/database/user`，完整版与 Lite 都不再把带密码的 DSN 发给前端。当前 Lite 返回 `ok=true`，设置页显示“核心服务正常”。

### Lite 自己的学习状态

Lite 不接视频观看记录，所以学习评价只看站内自己的记录。`app/services/lite_activity.py` 汇总最近 N 天：

- Todo：新建、完成、完成率、当前未完成、逾期、专注分钟、番茄轮次
- 日历：安排数、今天/未来 7 天、类型、累计分钟
- 私人笔记：新建、更新、总篇数、字数、最近标题
- 面试练习：作答数、题目数、平均分、通过率、分组、已掌握/收藏
- 使用痕迹：登录、聊天轮次、会话、提问、动作审计、设置更新
- 连续天数：活跃天数、当前连续、最长连续、每日来源

工具 `get_lite_learning_status(days=7)` 只在 `study-summary` 意图下挂给模型，输出事实快照，不替模型下结论。提示词要求：记录少就直说“站内数据很少”，不能拿视频观看、课程进度或学习时长补足。

### 聊天写动作到插件页联动

聊天侧四个写工具（`save_note`、`summarize_and_save_note`、`create_calendar_event`、`create_todo`）都走 HITL 确认卡；用户点 A 后才发放一次性写许可，点 B 不落库。动作完成后的 `done` 事件由 `frontend/src/lib/assistantActionSync.ts` 统一处理：

- note：按动作 `target_id` 调 `GET /api/notes/{id}`，回填到当前页面目标（便签墙或 Markdown 笔记）；
- note 页面自愈：Markdown 笔记页在首次挂载、窗口重新聚焦或从后台切回时，会调 `syncAllServerNotesIntoLocal('md')` 增量同步私人笔记。同步前记录当前 `activeNoteId`，同步后若原笔记仍在则恢复，避免后台导入把正在编辑的笔记切走；本地 `srv-*` 副本若不在服务端列表里，会再单独 `GET /api/notes/{id}`，只有明确返回 404 才清掉，网络错误或列表分页截断不会误删；
- sticky 页面自愈：便签页用同一套 hook 同步 `surface=sticky` 的服务端便签，右上角保留手动同步按钮。`notes` 表新增 `surface`（老数据默认 `md`），聊天保存按当前页面写归属；Markdown 页只拉 `md`、便签页只拉 `sticky`，两边不再互相导入。便签仍由 `p2m-notes-v1` 快照跨设备同步；已在垃圾箱的副本不会被自动复活，永久删除会同步删除服务端记录；
- todo / calendar：调用 `refreshScheduleFromServer()` 重新拉取 `schedule_items`，待办、日历、周历三个页面共用同一个 store，不需要重新进入页面。

数据模型统一：`create_calendar_event` 与笔记 AI 的“加入日历”都写 `schedule_items`，不再写前端日历页不读取的 legacy `calendar_events`；日期型 Todo / 日程统一为当天 `00:00–23:59`，定时日程缺结束时间默认加 1 小时。撤回时后端软删 `schedule_items`，前端重新对齐服务端，页面即时消失。

番茄钟完成也统一到 `schedule_items`：完成 work 阶段时 `pomodoroStore` 已经写回待办 `pomodoroCount` / `totalFocusMinutes`，`useCrossModuleSync` 不再重复累加，只按当前计数补“达到计划番茄数则完成”的状态；同时写一条 `type=event` 的专注记录，日历页、周历和统计徽章都能看到。此前 legacy `calendar_events` 的 `专注 92分钟` 重复行已清理。

确认卡增加了两道保护：`AIChatPanel` 用同步 ref 锁住 `run_id + interrupt_id`，同一确认按钮双击只 resume 一次；新的待确认卡出现时自动滚入聊天面板可见区，避免按钮滚出视口后点不到。

确认卡还补了跨进程恢复。LangGraph 的中断点原本只存在进程内 `MemorySaver`，Lite 重建/重启后，旧卡片再点 A 会因 checkpoint 丢失而断开 SSE，页面只显示“请求失败，请检查后端与模型服务”。现在 resume 找不到 checkpoint 时，会从 `AgentRun.steps` 取回用户已确认的工具名和参数，直接执行这一次写入并生成 `done + actions`；点 B 仍只取消、不写库；已完成的确认再次提交会返回“这条确认已经执行过了”，不会重复落库。该兜底只覆盖四个写工具，普通问答的 checkpoint 丢失仍按原错误处理。

已用真实链路验收：发起保存笔记确认 → `docker restart p2lite-backend-1` 清空进程 checkpoint → 再用同一 `run_id` 点 A，返回 `provider=hitl-recovery`，笔记正文完整写入、动作回执可撤回；同一确认再次提交被拒绝。后端新增 4 条 `test_hitl_recovery.py`，全量 99 项通过。

真实浏览器在 Lite 实测：

- 聊天创建 Todo：确认卡 A 后待办页计数和列表即时出现；B 取消后数据库 `schedule_items` 无对应行；
- 日历事件：确认后月视图当天出现；周历在包含目标日期的四天窗口内显示 15:00–16:00 块；
- 撤回：页面条目消失，数据库对应行 `deleted_at` 有值；
- 便签 / 笔记：在 `#/notes` 和 `#/mdnotes` 分别确认保存，页面计数从 3→4 / 4→5 且卡片出现；撤回后计数回落，服务端 `notes` 行删除；
- 确认卡双击：同一次确认按钮连点两次，只产生一条 Todo、一张动作卡；
- 确认卡跨重启：保存笔记弹卡后重启 Lite backend，再点 A 仍能落库，返回 `provider=hitl-recovery`；同一确认重复提交被拒绝，不产生第二条笔记；
- 番茄钟：从待办页点“开始专注”，番茄钟页显示“当前专注：聊天创建的待办”，说明 Todo 已被番茄钟 store 正确关联。

Media 站点共用同一套前后端代码，已重建 `p2-siteyeb-frontend:3.0` / `p2-siteyeb-backend:3.0`。Media 前端当前停在登录页，完整 UI 验收需要登录态；本轮用 API 级 SSE 对同一条链路做了验收：聊天触发确认卡（A/B 选项齐全），选 A 后 `schedule_items` 新增 `type=todo` 且带 `start_at/due_at`，选 B 后数据库无对应行，测试待办已删除。

确认卡跨重启恢复这次最初只重建了 Lite backend。随后为保持“原版与 Lite 同源都通”，Media 前后端也已用同一套代码重建：`p2-siteyeb-frontend:3.0` 产出 `assets/index-CVZMDl5L.js`，`p2-siteyeb-backend:3.0` 启动后 `/ready` 返回 `ready=true`，完整版 `notes.surface` 迁移已执行（默认 `md`）。Media 与 Lite 现在共享同一套 notes/MCP/capabilities/health 代码，不再是一边修完、另一边留着旧进程。

入口页缓存也一并收口：`infra/nginx.conf` 的 SPA fallback 现在对 `/` / `/index.html` 返回 `Cache-Control: no-store`，静态 hash 资源仍保持一年 immutable。此前镜像更新后浏览器继续用旧 `index.html`，会请求已被删除的旧 chunk 并白屏；这次重建后实测 Lite / Media 入口都返回 `no-store` 头。

### 笔记 AI 面板跨页面 / 跨笔记恢复

问题现象：在 Markdown 笔记页发起“润色”后，只要切到别的页面或别的笔记，AI 面板、加载态和结果全部消失；慢请求即使完成也不会回到原笔记。

根因是 AI 面板状态原本是 `MarkdownNotesPage` 的组件局部 state，组件卸载或 `activeNote.id` 变化时会被清零；异步结果又被组件内 `aiRunRef` 拦截，请求生命周期和页面绑定。

修复改为按 `noteId` 维护内存会话，新增 `frontend/src/stores/noteAiStore.ts`：

- `sessions[noteId]` 保存 `open`、当前 tab、`loading`、`error`、摘要、润色结果、待办/日程建议和动作回执；
- `runSession(noteId, view, input)` 在 store 内直接调用 `runNoteAi`，请求不依赖组件挂载；完成时按原 `noteId` 回写，不会落到当前正在看的另一篇笔记；
- 关闭面板只把 `open=false`，不取消请求；切走再回来仍能看到 loading，完成后再看到结果；
- 重新打开恢复上次 tab；待办/日程回执按笔记保存，避免切回来重复创建。

`MarkdownNotesPage` 的 AI 面板、tab、插入摘要、替换正文、创建待办/日程全部改为按当前 `activeNoteId` 读写 store，删除了局部 AI state、`aiRunRef` 和笔记切换时的 AI 清零逻辑。面板没有 click-outside 关闭，点编辑区或空白处不会收起。

实测三套 profile：Demo `12306`、正式 Lite `12305`、Media `12302` 均完成“打开 AI → 润色出结果 → 切到另一篇笔记 → 切回原笔记”，面板和结果仍保留；切到另一篇笔记时面板按 `noteId` 隔离关闭属预期。新增 `noteAiStore.test.ts` 3 条与 `markdownNotesAiPersistence.test.tsx` 2 条覆盖关闭后请求继续、结果按笔记隔离、失败归属、组件卸载重挂载、跨笔记切换恢复。

边界：会话只在内存，浏览器整页刷新或关闭标签页会丢失；不写 `localStorage` / IndexedDB，避免把可能含整篇笔记正文的 AI 结果额外落到浏览器持久存储。


问题根因不是“笔记页刷新按钮坏了”，而是服务端 `notes` 表和前端两个 IndexedDB store（`p2m-notes-storage`、`p2m-md-notes-storage`）之间没有回填链路：`save_note` 只写数据库并返回聊天动作回执，页面不会自动出现这篇笔记。

修复分三层：

- 后端新增 `GET /api/notes/{note_id}`，按 id 取回完整正文，避免把 60k 字正文塞进 SSE 动作回执。
- 聊天 `done` 事件按 `action_type='note' && status='applied'` 的 `target_id` 回填：便签页进便签墙，Markdown 笔记页进笔记 store；本地 id 固定为 `srv-<server_id>`，同标题同正文去重，撤回动作同步清理。
- 便签页当前正文通过 `pageNote` 随聊天请求提交；Markdown 笔记页目录头新增“从服务端同步”按钮，可增量拉取已有私人笔记。

实测 Lite：在便签页保存当前便签，服务端 `notes` 表写入 30 字完整正文，页面不重复；在工作台让 AI 新建《回填新增验证-1351》，笔记页出现该篇；再让 AI 新建《便签回填新增-1354》，便签墙计数从 4 增到 5；浏览器刷新后两条仍在。Media 与 Lite 共用同一套前后端代码。

### 便签 / 笔记分面

`notes` 表只增加一个归属字段，不拆表：

- `surface='sticky'`：便签墙的短卡片，仍保留颜色、标签、置顶、拖动排序和 `p2m-notes-v1` 快照同步；
- `surface='md'`：Markdown 长文笔记，继续走 `p2m-md-notes-storage` 和笔记页的目录、编辑区；
- 老数据和视频转写笔记统一回填 `md`，升级后不会突然铺满便签墙；
- `GET /api/notes` 接受 `surface` 过滤；聊天 `page_note` 带上当前页面归属，`save_note` / `summarize_and_save_note` 写入对应 `surface`；单篇回填先读服务端 `surface`，再决定进哪个 store。

便签页打开和窗口重新聚焦时会拉 `surface=sticky`；右上角保留同步按钮。已在垃圾箱里的 `srv-*` 副本不会被自动同步复活，永久删除/清空垃圾箱时会向服务端发 `DELETE`。真实浏览器验收：插入 `sticky` 与 `md` 各一篇后重载，便签页 3→4 且只出现便签篇，笔记页只出现 `md` 篇并保留 B-4-1；删除服务端两篇后重载，便签页回落到 3 条、无 `srv-*` 残留。

## 共享数据底座

### PostgreSQL：一套实例，四个 database

| 项目 | database | owner |
|---|---|---|
| P1 | `db_p1` | `u_p1` |
| P2 | `db_p2` | `u_p2` |
| P3 | `db_p3` | `u_p3` |
| P4 | `db_p4` | `u_p4` |

初始化脚本：`infra/shared/init-shared-databases.sh`，由官方 postgres 镜像在 `shared_pgdata` 卷为空时执行；手动重跑也只更新口令，不覆盖库。镜像用 `postgres:16-alpine`，与 P1 最终稿对齐。P1 最终稿的 app 角色 `slimtrack_app` 由 `P1_APP_PASSWORD` 选择性创建，并只授予 `db_p1` 的 CRUD 权限。

2GB 参数在 `infra/shared/postgresql.2g.conf`，实测值：

| 参数 | 值 |
|---|---|
| `shared_buffers` | 512MB |
| `work_mem` | 4MB |
| `maintenance_work_mem` | 64MB |
| `max_connections` | 30 |
| `effective_cache_size` | 1GB |
| `wal_buffers` | 16MB |
| `autovacuum` | on |
| `statement_timeout` | 60s |
| `idle_in_transaction_session_timeout` | 60s |

连接预算：P1 app + P2 Lite 各 5~10 条，`max_connections=30` 给迁移和健康检查留余量。不要四个项目同时把连接池开满；P3/P4 上线时按需下调每库池大小。

### Redis：一套实例，四个 DB

| 项目 | DB | key 前缀 |
|---|---|---|
| P1 | 0 | P1 自己的前缀 |
| P2 | 1 | `p2:` |
| P3 | 2 | 待定 |
| P4 | 3 | 待定 |

P2 的队列名也带前缀：`p2:queue:ai_jobs`、`p2:queue:summary_jobs`、`p2:queue:background`；取消标记 `p2:ai_job:cancelled:{job_id}`；暂停键 `p2:ai_queue:paused`。`app/services/redis_keys.py::p2_key()` 是唯一入口。

Redis 用 `maxmemory=256mb` + `maxmemory-policy=noeviction` + AOF `everysec`。队列任务不能像缓存一样被 LRU 清掉；内存满时宁可入队失败，也不静默丢任务。

## 已知风险

1. **共享 PG 的连接数**：P1/P2 同时在线约 20~25 条，`max_connections=30` 余量不大。新增服务前先降每库池大小，或把 `max_connections` 提到 40 并相应加内存。
2. **共享 page cache**：P2 Lite 不建向量表，最大的 IO 风险来自 P1/P3 的大批量导入。演示时段禁止批量导入/重建索引；维护脚本加 `nice`/`ionice`。
3. **Redis 不淘汰**：`noeviction` 保护队列，但缓存写满会直接报错。P2 Lite 只有面试题缓存和少量画像 key，256MB 足够；P3/P4 加缓存前要重新算预算。
4. **前端仍会产出完整页面的 chunk**：Lite 构建过滤了 `PAGES`，未裁页面的静态 chunk 仍可能被 Vite 打出，只是导航与路由不可达。若要把镜像体积也压到最小，下一版再把 `PAGE_LOADERS` 改成 profile 分支。
5. **Lite 没有 worker**：`p2:queue:*` 仍由 `rq_client` 懒初始化，但 Lite 不消费。不要在该实例上调用会入队的接口；相关路由已经被裁掉。
6. **`stats` 页**：保留但数据来自空的 `videos` 表，显示为零。它不再代表“学习统计”，只是保留页面入口；如果演示不需要，可在下一版移除。

## 与 P1 最终稿的衔接

P1 当前正式运行的仍是自带 `postgres` / `redis` 的 `docker-compose.yml`；共享底座切换文件已放在 P1 仓库的 `docker-compose.shared.yml`，原文件保留可回滚。切换步骤见 P1 的 `docs/SHARED_DB_CUTOVER.md`。

```text
DATABASE_URL=postgresql://slimtrack_app:<P1_APP_PASSWORD>@shared-postgres:5432/db_p1
DATABASE_ADMIN_URL=postgresql://u_p1:<P1_DB_PASSWORD>@shared-postgres:5432/db_p1
REDIS_URL=redis://:<SHARED_REDIS_PASSWORD>@shared-redis:6379/0
```

并把 P1 的 `postgres` / `redis` 服务从启动命令里去掉，或者用 override 覆盖掉。P1 的 `slimtrack_app` 角色保留 RLS 口径；共享初始化脚本已经在 `db_p1` 上授予它 CRUD 与默认权限。

共享网络名默认 `p2-shared`，P1 的 `slimtrack-mcp` 需要加入该外部网络，才能用 `shared-postgres` / `shared-redis` 这两个服务名。

### P1 兼容性实测
