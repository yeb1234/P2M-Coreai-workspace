# PR-004 学习路径 TAB 与 Agent 上下文

- **分支**：`feat/learning-path`
- **合并提交**：`5a82093`（与 PR-001 同批，见下方复盘）
- **影响面**：前端导航、LangGraph 规划、对话 Agent、任务队列
- **风险等级**：中（新增重任务入口）

---

## 为什么

原来的「学习路径规划」只有 API，没有界面。用户要生成一条路径得用 `curl`，
生成的路径也没地方看，只能从数据库里读 JSON。

更关键的是：**规划出来的路径和对话 Agent 是两套东西**。
用户问「我下一步学什么」，Agent 会重新检索、重新推荐，
完全不知道已经有一条排好的路径 —— 结果就是每次回答都不一样，而且和路径冲突。

---

## 改了什么

**前端**

- 新增导航 TAB「学习路径」：画像概览 4 卡 → 目标表单 → 步骤时间线 → 进度条
- 每一步绑定真实视频，点击直接跳播放器（复用已有的 `p2m:play-video` 事件）
- 库里没有素材的步骤**如实标注「需外部补充」**，不编课程名

**后端**

- `GET /api/learning/paths/active`：当前路径，前端首屏和 Agent 都用它
- `_serialize_path` 补 `videos` 详情（只有 id 前端没法渲染标题）
- 步骤状态两段式：`pending → in_progress → done`，全部完成自动收口
- 规划任务：**去重 + 并发上限 4 + 15 分钟僵尸清理**

**Agent 上下文**（`app/services/learning_context.py` 新增）

- `active_path_text` 压成 LLM 可读的摘要，注入系统提示词
- 新增 `get_my_learning_path` 工具，用 `ContextVar` 传用户身份
- 系统提示词加一条硬规则：回答「下一步」必须先调这个工具，按路径推进

## 怎么验证

```bash
# 生成一条路径（12 秒）
curl -s -X POST http://localhost/api/learning/paths/generate \
  -H "Content-Type: application/json" -b cj.txt \
  -d '{"title":"补齐 RAG 工程化闭环","weekly_hours":15,"skills":["LangGraph","RAG"]}'

# 连续提交同一目标 → 应去重返回同一个 run_id
# {"run_id":"...","status":"running","deduplicated":true}

# Agent 是否真的在读路径
curl -sN -X POST http://localhost/api/assistant/chat/stream \
  -H "Content-Type: application/json" -b cj.txt \
  -d '{"message":"我下一步学什么？按我的路径说"}'
# 期望工具调用里出现 get_my_learning_path，
# 回答里出现「第 1 步 ... 0/6 步」
```

实测回答：

> 按你的路径，下一步是**第 1 步：LangGraph 工作流编排基础**（约 5 小时，目前 0/6 步）。
> 这一步的目标很具体：能搭出含节点、边、状态的基础 LangGraph 工作流。
> 路径里绑定的素材是：《01_回顾》《02_deepagents_进阶应用》……

浏览器端到端 11 项全过。

## 风险与回滚

**风险**：规划是重任务（20–40 秒、多次 LLM 调用）。开放给多用户后，
并发不当会把额度打爆。已加去重 + 并发上限 + 每日配额。

**回滚**：前端删掉 `pageRegistry` 里的那一行就下线入口；后端 API 可留着不影响。

## 复盘

### 1. 端到端测出来的 bug，单元测试测不出来

勾选步骤后，页面整页进入 `loading`，`StepRow` 被卸载重建，
`useState(step.status === 'in_progress')` 重新初始化 —— **展开状态丢了**。

用户体验是：点「开始这一步」，卡片收起来，想再点「标记完成」得重新展开。
更糟的是自动化脚本点第二下时元素已经不在，测试直接失败。

修复：展开状态提到父层 + 静默刷新（`load({ silent: true })`）。

**这个 bug 只有真实点击两次才会暴露。** 单元测试里 store 是 mock 的，
不会重渲染；接口测试也不关心 UI 状态。

可复用的检查：**任何「操作后需要再操作一次」的流程，都要连点两次验证。**

### 2. 「如实说没有」比「编一个」难，但必须做

规划出的第 6 步「RAG 评估体系」，库里只有 2 个视频，模型没有硬凑。

这件事需要代码层面保证：`node_retrieve` 只从检索结果里挑视频，
模型返回的、库里不存在的课程名会被丢弃。**模型的输出不当事实用。**

产品上表现为：那一步标注「需外部补充」，而不是显示一个点开是空的步骤。

### 3. 提示词注入 + 工具调用，两条路都要有

路径信息同时做了两件事：

- **注入系统提示词**：每轮都看得见，推荐时不会给冲突方案
- **提供工具**：模型可以主动查细节（每步的视频、进度）

只做工具：模型可能想不起来调。
只做注入：上下文会随路径变长而膨胀。

**「常驻摘要 + 按需详情」是 context 管理的通用模式。**

### 4. 反例：这个 PR 不该和 PR-001 合并

学习路径的鉴权和数据隔离确实是安全改造的一部分，所以打包进了同一个提交。

结果：**没法独立评审，也没法独立回滚**。
如果学习路径页有严重 bug 要紧急下线，得连着安全加固一起回滚 —— 显然不行。

PR-002 之后就把主题拆开了。**耦合的代价当时看不出来，出事时才知道。**

## 附：为什么「去重」比「排队」重要

最初的设计是任务队列，用户连点 10 次就排 10 个 30 秒的任务，第 10 个要等 5 分钟。

改成了「同用户 + 同目标 + 15 分钟内有 running → 直接返回原 run_id」。

对比：

| 方案 | 用户感受 | 成本 |
|---|---|---|
| 排队 | 等 5 分钟，最后可能失败 | 10 次 LLM 调用 |
| 去重 | 立刻拿到同一个任务 | 1 次 LLM 调用 |
| 直接 429 | 立刻知道不行 | 0 次 |

**「立刻告诉我不行」比「让我等 5 分钟再告诉我不行」体验好得多。**
这是产品判断，不是技术优化。
