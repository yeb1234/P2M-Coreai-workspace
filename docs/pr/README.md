## 分支命名

| 前缀 | 用途 |
|---|---|
| `feat/` | 新功能 |
| `fix/` | 缺陷修复 |
| `perf/` | 性能优化 |
| `chore/` | 构建、依赖、配置 |
| `release/` | 发布快照，只合并不开发 |

## 合并前的最低要求

一份 PR 要能合并，至少满足：

1. **能编译**：前后端都过（`tsc -b --force` 不用增量缓存）
2. **能启动**：容器 healthy，`/health` 返回 200
3. **能验证**：有具体的命令或脚本证明这个改动生效，不是「看起来对」
4. **有回滚**：说清楚怎么退回去

不满足第 3 条的改动不该合并 —— 这也是这轮审计里最大的教训：
**之前那些「接口返回 200 就算完成」的功能，后来发现中文检索整个是失效的。**

## 一份 PR 记录该写什么

看这几个文件的结构，共同点是：

- **为什么**：不写「优化了体验」，写具体症状和量化影响
- **改了什么**：按文件列，不按功能列
- **怎么验证**：贴真实输出，不写「已测试」
- **风险与回滚**：说清楚哪一步可能出错
- **复盘**：这一节最重要，见下

「复盘」不是复述改动，而是回答：**如果重来一次，哪一步可以更早发现这个问题？**

这条标准是为了防止复盘写成流水账。
