# 转写流水线对照测试（2026-11-17 夜间）

## 测试目标

验证「CPU 预抽 WAV → C 盘 SSD 缓存 → 2 个 GPU worker 只做转写」是否比 GPU worker 自己从 D 盘 HDD 抽音频更快、更稳，并确定并发/缓存参数。

## 最终选择

**CPU 抽音频并发 1 + 缓存上限 8 + 队列头对齐 + 2 个 GPU worker**。

- GPU 只做转写，不再从 D 盘抽音频。
- 显存稳定在 **5.6–5.8 GiB / 8 GiB**，2 个 worker 无 OOM。
- 转写期间 GPU 利用率 **97–100%**。
- CPU 抽音频与 GPU 转写同时进行时，GPU 仍能维持 97% 左右；抽音频并发 2 时会掉到约 90–91%。

> `WHISPER_BATCH_SIZE=4` 目前没有真正生效：`faster-whisper 1.0.3` 没有导出 `BatchedInferencePipeline`，运行时回退 single-pass。该参数保留为配置，但本次测试结果全部按 single-pass 计。

## 对照数据

### A. GPU worker 自己从 D 盘抽音频（2 worker，CPU 预取未对齐）

| 视频 | 音频时长 | 总耗时 | 折合 |
|---|---:|---:|---:|
| 45538 | 2:14:00 | 10.53 min | 4.72 min/音频小时 |
| 50340 | 2:18:50 | 10.65 min | 4.61 min/音频小时 |

抽取阶段约 4.5 分钟；D 盘随机读只有约 2.7 MB/s、80–183 reads/s，GPU 在抽取阶段只有 17–22%。两个 worker 同时读不同视频，HDD 寻道放大明显。

### B. CPU 预抽 + C 盘缓存，队列头命中（2 worker）

| 视频 | 音频时长 | 总耗时 | 折合 |
|---|---:|---:|---:|
| 50106 | 3:22:15 | 8.05 min | 2.39 min/音频小时 |
| 36553 | 2:47:18 | 7.12 min | 2.55 min/音频小时 |
| 40650 | 2:00:02 | 4.07 min | 2.03 min/音频小时 |
| 36854 | 2:30:17 | 5.50 min | 2.20 min/音频小时 |

后两项是抽音频并发降到 1 之后的数据，GPU 97%，明显好于 A，也略好于并发 2 的阶段。

### 未选方案

- **单 worker + 加大 batch**：当前 2 worker 已经只占 5.6–5.8 GiB，GPU 97–100%；单 worker 会直接损失一半并行度，batch 又因库缺 `BatchedInferencePipeline` 无法真正启用，暂不采用。
- **CPU 抽音频并发 2**：能更快铺缓存，但与 GPU 转写抢 CPU，GPU 从 97% 掉到约 90–91%，长视频总耗时反而更高。
- **GPU worker 回退自己抽 D 盘**：只在缓存未命中时保留为兜底，不应成为常态；两个 worker 同时读 HDD 会把抽取拖到 4–5 分钟。

## 已落地配置

- `audio-prep` 增加 `REDIS_URL=redis://redis:6379/0`，优先读 RQ `ai_jobs` 队列头，不再按数据库 `created_at` 铺缓存。
- `AUDIO_PREP_CONCURRENCY` 默认 1。
- `AUDIO_PREP_MAX_FILES` 默认 8。
- 缓存目录走 C 盘 SSD：`/data/audio-cache`。
- 缓存文件按队列头顺序生成；GPU 命中后直接跳过 ffmpeg。
- 清掉了此前按数据库时间铺的 16 个非队列头 WAV，相关任务退回 `queued` 重新排队。

## 当前队列与预估

测试结束时：

- 已完成：628 个任务，约 107.5 音频小时。
- 待转写：5113 个任务，约 **1347.2 音频小时**。
- 失败：2 个旧任务（一个事务中止，一个 `libcublas.so.12` 找不到），不是本轮 2 worker 造成的。

按最近一组 2 worker 实测（4.5 音频小时 / 5.5 分钟，约 49 音频小时/小时）估算：

- 纯转写：**约 27–28 小时**。
- 考虑大量 15 分钟级短视频的模型加载/清理固定开销，保守 **30–34 小时**，约 1.3–1.4 天。

## 备注

- 当前 GPU 显存 5.6–5.8 GiB，仍有余量，但没有继续加 worker 或 batch 的必要；再加会进入 8 GiB 边缘，收益不如稳定性。
- 缓存上限 8 对应约 2.1–2.2 GB WAV，C 盘可用约 776 GB，空间充足。
- 后续如果要真正启用 batch，需要升级/替换 `faster-whisper`，并重新验证 8 GiB 显存；当前版本不建议动。
