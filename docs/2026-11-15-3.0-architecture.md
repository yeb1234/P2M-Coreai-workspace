# P2 Learning OS 3.0 架构重构报告

日期：2026-11-15
分支：`3.0-agent-rag`
基线标签：`baseline-before-3.0`（提交 `3490840`）

---

## 一、为什么必须重构

重构前的问题不是「不好用」，而是**核心链路是假的**。逐项实测：

### 1. 中文检索完全失效

原实现依赖 SQLite FTS5，使用默认 `unicode61` 分词器。实测三个查询：

| 查询 | FTS5 默认分词 | FTS5 trigram |
| --- | --- | --- |
| 依赖注入 | 0 命中 | 命中 |
| Milvus 索引 | 0 命中 | 命中 |
| 红烧肉 | 0 命中 | 命中 |

聊天里显示的「相关视频」实际靠 `LIKE %关键词%` 兜底，`score_hint` 只是「关键词出现次数」，与相关度无关。

### 2. 319 万条向量是废数据

`subtitle_segment_embeddings`（sqlite-vec vec0）占 **14GB**，359 万条 × 1024 维。

- 用 qwen3-embedding 查询：距离恒为 **1.35**（负相关），返回「33B」「申考贝」这类 ASR 碎片
- 换 bge-m3 查询：距离 **0.647**，说明原向量是 bge-m3 建的，但文本质量太差
- 即使模型配对正确，**暴力 KNN 耗时 26 秒**——vec0 没有 ANN 索引，全表扫 14GB

### 3. Agent 开关是装饰品

`use_rag` / `use_web_search` / `use_deep_research` 三个参数被原样回写到响应体，没有任何实现。

### 4. 聊天失忆

`chat_messages` 存了 130 条历史，`run_assistant_chat` **从不读回**。每次对话都是全新开始。

### 5. 学习行为数据几乎为零

- 14,327 个视频，8,769 个有字幕，359 万片段，但 **≥10 字的只有 124.8 万（35%）**
- `watch_history` 只有 320 条，完成 12 条
- `notes` 8,770 条全是 AI 自动生成的模板
- 想做「分析观看时长做路径规划」，数据基础是空的

## 二、架构决策

### 决策 1：PostgreSQL + pgvector，而不是 Milvus

| 方案 | 业务库 | 向量库 | 运维成本 |
| --- | --- | --- | --- |
| 保留 SQLite + Milvus | SQLite（15GB、单写锁） | Milvus（Docker + etcd + MinIO） | 两套系统、两份备份 |
| **PostgreSQL + pgvector** | **同一套** | **同一套** | **一个容器** |

选 pgvector 的核心理由：**业务库本身也是问题**。15GB 的 SQLite 在并发写入、备份、迁移上都在拖后腿，单独上 Milvus 只解决向量，业务库还得再治一次。

迁移结果：

| 指标 | 迁移前 | 迁移后 |
| --- | --- | --- |
| 库体积 | 15 GB | **1.77 GB**（清了 14GB 废向量） |
| 中文检索 | 0 命中 | **3–32ms 命中** |
| 向量检索 | 26 秒 | **6–25ms** |
| 359 万片段迁移 | — | **53.8 秒**（COPY 协议，6.7 万行/秒） |

> Milvus 留作后续：若向量规模超过 1000 万条或需要多租户隔离，再引入。当前 186 万条（≥8 字）用 HNSW 完全够。

### 决策 2：全面采用 LangChain + LangGraph

用户明确选择全面采用。落地方式：

- **LLM 层**：`langchain-openai` 的 `ChatOpenAI`。deepseek 的非标参数必须走
  `extra_body={"chat_template_kwargs": {"thinking": False}}`
  （用 `model_kwargs` 会抛 `TypeError: Completions.create() got an unexpected keyword argument`）
- **Agent 层**：`langgraph.prebuilt.create_react_agent`，`recursion_limit=12` 防工具死循环
- **规划层**：手写 `StateGraph`，五节点带条件边与重排循环

代价与应对：

| 风险 | 应对 |
| --- | --- |
| 抽象层厚、出错难定位 | 工具全部返回压缩后的纯文本，日志记录 `AgentRun.steps` 全轨迹 |
| 版本漂移（langchain 1.x API 变动大） | `requirements.txt` 锁 `>=1.0`，关键调用点集中封装在 `services/llm.py` |
| 流式事件结构不稳 | `astream_events(version="v2")`，只消费 `on_chat_model_stream` / `on_tool_start` / `on_tool_end` 三类 |

### 决策 3：不引入 RabbitMQ

**结论：保留 Redis + RQ，不引入 RabbitMQ。**

理由：

1. **量级不匹配**：日任务量几十个，RabbitMQ 的吞吐优势（万级/秒）完全用不上
2. **运维成本翻倍**：Windows 装 RabbitMQ 需要 Erlang 运行时，而 Redis 已经在跑（RQ + 缓存共用）
3. **真正的问题不是队列选型**：RQ 在 Windows 用 `SimpleWorker`，任务崩溃会带走 worker 进程。这是执行模型问题，换 RabbitMQ 一样存在（消费者崩了也得重启）
4. **已有兜底**：DB 状态机 + `sync_db_queue_to_rq` 已经能在 worker 重启后恢复

若将来要动，正确顺序是：先做**任务级子进程隔离**（崩溃只死子进程），再考虑换 broker。

### 决策 4：混合检索 + 加权 RRF

两条通路各自的短板（实测）：

- 纯词法：`FastAPI 依赖注入是怎么实现的` → 前四条全是 "from fastapi" 这类碎片，整句 trgm 被长文本稀释
- 纯语义：能跨表述召回（问「函数返回另一个函数」也能找到闭包），但对生僻 API 名、版本号不敏感

融合策略：RRF，词法权重 0.8 / 向量权重 1.2（语义更可靠）。再加一层 LLM listwise 重排（8 秒硬超时，失败退回 RRF 原序）。

## 四、记忆与规划

### 三层记忆

| 层 | 存储 | 作用 |
| --- | --- | --- |
| 会话摘要 | `chat_sessions.summary` | 超过 24 条消息时压缩旧内容，保留目标/结论/待办 |
| 原始消息 | `chat_messages` | 最近 10 条原文参与上下文 |
| 长期记忆 | `memory_items` | 跨会话稳定事实（偏好、约束、目标），按重要度 + 新鲜度召回 |

### 行为埋点

新增 `watch_events` 事件流。为什么不复用 `watch_history`：后者只有「当前进度」一个快照，算不出真实观看时长——跳过片头、倍速、反复重看都会失真。事件流按 `delta_sec` 累加才是真实投入。

服务端对 `delta_sec` 做 3600 秒上界钳制，防止客户端 bug 把画像时长刷爆。

### 规划 Agent（LangGraph）

```
analyze(现状+目标→能力缺口)
   ↓
retrieve(每个缺口→真实视频素材)
   ↓
plan(排步骤，绑定素材)
   ↓
validate ──有问题──→ plan（最多 1 轮）
   ↓ 通过
persist(落库)
```

**关键设计：`validate` 只对「真问题」触发重排。**

初版把「估算时长超出期限」「步骤超过 10 个」也算作阻塞问题，结果跑了两轮重排，耗时 100 秒，最终产物和第一轮几乎一样。改为：只有「所有步骤都没有视频支撑」和「步骤超过 12 个」才重排，时长超标降级为提示。

实测产出（目标：3 个月补齐 RAG 工程能力，每周 15 小时）：

1. 夯实 Embedding 与文本切分基础（600min，2 个视频）
2. 搭建向量数据库与索引存储（540min，2 个）
3. 掌握 LangGraph 工作流编排（720min，3 个）
4. 系统化 Agent 工具调用（600min，3 个）
5. RAGFlow 检索增强生成实战（660min，2 个）
6. RAG 评估与调优闭环（540min，2 个）
7. 建立学习节奏与专注执行（300min，2 个）

每步的视频都来自真实检索，`video_titles` 会回填成真实 `video_id`，模型编造的标题会被丢弃。

## 五、工程加固

| 问题 | 原状态 | 修复 |
| --- | --- | --- |
| CORS | `allow_origins=["*"]` + `allow_credentials=True`（浏览器会直接拒绝，且等于关闭同源保护） | 显式来源列表，走 `CORS_ORIGINS` 环境变量 |
| JWT | 默认密钥硬编码 + 有效期 90 天 | 环境变量强制 + 有效期 24 小时 |
| 日志 | `print` 散落各处 | JSON 结构化 + `request_id` 贯穿，响应头返回 `X-Request-ID` |
| 异常 | 未捕获异常直接抛堆栈 | 类型化异常体系 + 全局处理器，客户端只见 `{code, message, request_id}` |
| 健康检查 | 无 | `/health`（存活）+ `/ready`（含向量覆盖率与模型探活） |
| 大文件溢出 | `videos.file_size` 用 int32，存在 2GB+ 视频导致迁移失败 | 升 `bigint` |
| 画像外键 | `user_profiles.user_id=0` 违反外键约束 | `resolve_user_id` 解析到真实用户 |

## 六、遗留事项

1. **向量覆盖率 1.54%**（28,747 / 1,866,772）。全量嵌入按 84 条/秒估算约 **6.2 小时**，建议后台跑：
   ```bash
   python scripts/backfill_embeddings.py --all --batch-size 256
   ```
2. **重排延迟不稳定**：首次 2.8 秒、缓存后 0.64 秒。已设 8 秒硬超时，但仍建议前端对 `rerank=false` 提供降级开关。
3. **字幕质量是天花板**：ASR 碎片（「申考贝」「那猪那玩」）占比不低，检索再好也救不回来。建议对高价值课程跑一轮 LLM 字幕校对。
4. **watch_history 缺 user_id**：单用户场景无碍，多用户前必须补。
5. **RQ 任务崩溃隔离**：当前 worker 崩溃会导致排队任务中断，尚未做子进程隔离。

```bash
# 启动数据库
docker compose -f docker-compose.pg.yml --env-file .env up -d

# 初始化 schema（幂等）
python -c "from app.database import ensure_runtime_schema; ensure_runtime_schema()"

# 迁移 SQLite 数据（只读源库，可重复执行）

curl localhost/health
curl localhost/ready
curl "localhost/api/search/hybrid?q=闭包是什么&top_k=3"
```
