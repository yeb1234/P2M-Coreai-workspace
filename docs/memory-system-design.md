## 二、设计：四层，职责分明

参考 Codex / WorkBuddy 的设置结构，分四层。**关键区别是写入方不同**，这决定了谁能改、谁不能改。

### 第 1 层：档案（Profile）

用户手填，结构化字段。**LLM 绝对不能自动改**。

```
称呼          你怎么叫自己
职业/身份      学生 / 在职 / 转型中
当前目标       找 AI 岗 / 学 RAG / 过面试
时区           Asia/Shanghai
语言偏好        中文
每周可投入       15 小时
```

用途：每次对话都注入，影响称呼和建议强度。

### 第 2 层：助手设定（Assistant Persona）

用户手填，控制「怎么说话」。

```
语气      简洁 / 详细 / 严厉 / 温和
主动程度   只答问 / 会反问 / 会主动push
是否要引用来源
禁区      不想聊的话题
```

现状只有一个裸的 `system_prompt_extra`。建议拆成结构化字段 + 一个自由文本框，前者参与逻辑判断，后者原样拼进 prompt。

### 第 3 层：记忆条目（Memories）

**一条一句话**，带元信息。这是最核心的一层。

```
id
user_id
content        "用户在准备澳洲的 AI 工程师岗位"
kind           fact | preference | goal | constraint
source         user_stated | inferred | manual
confidence     0.0–1.0
pinned         bool        ← 用户置顶的，永不被自动覆盖
superseded_by  ← 被哪条替代了（软删除，保留历史）
created_at / updated_at / last_used_at
```

**三条硬规则**（这是整个设计的关键）：

1. **`pinned=true` 的条目，自动提取永远不能改、不能删**
2. 冲突时不删旧的，标 `superseded_by` —— 保留「用户改过主意」的历史
3. `source='user_stated'` 的优先级高于 `inferred`

第 1 条最重要，也最容易做错。用户手动改过的记忆，如果被 LLM 自动提取覆盖掉，用户会觉得「它不听我的」。

### 第 4 层：派生数据（Derived）

系统计算，只读。`user_profiles` + `journey` 就属于这层。

不参与「记忆」的读写，只作为上下文注入。

## 三、自动更新机制

每轮对话结束后**异步**跑（不阻塞回答）：

```
1. 取最近 N 轮对话
2. 调 LLM（deepseek-v4.1，外网 API）判断：
   - 有没有值得长期记住的新事实？
   - 和已有记忆冲突吗？
3. 输出结构化 JSON：
   { "add": [...], "supersede": [...], "noop": true }
4. 落库前二次校验：
   - 目标条目 pinned？→ 跳过
   - 目标条目 source=user_stated 且新值也是 inferred？→ 跳过
   - 置信度 < 0.6？→ 存为候选，不激活
```

**为什么异步**：同步会让每轮对话多 2-3 秒，而记忆提取的收益是长期的，不值得牺牲即时体验。

**为什么要二次校验**：LLM 判断「应该覆盖」和「真的覆盖」之间必须有代码兜底。这是防止「用户改过的记忆被冲掉」的最后一道闸。

## 四、怎么评估（你问的重点）

记忆系统不能靠「感觉还行」。五个指标，每个都有具体测法。

### 1. 召回率（该用的时候用上了吗）

构造 20 条需要记忆的对话：

```
前置：记忆里有「用户在准备澳洲岗位」
测试：问「帮我看看这个 JD 适不适合我」
期望：回答里提到澳洲 / 出海相关
```

**指标**：20 条里有多少条用上了相关记忆。目标 ≥ 80%。

### 2. 精确率（用了不该用的吗）

前置注入 10 条**无关**记忆（比如「用户养了猫」），
再问一个纯技术问题，看回答里会不会莫名其妙提到猫。

**指标**：误用率。目标 ≤ 5%。

### 3. 时效性（改主意了跟得上吗）

```
第 1 轮：用户在准备澳洲岗位        → 记忆 A
第 2 轮：用户说「我改主意了，想留国内」  → 记忆 A 应该被 superseded，新增 B
第 3 轮：问「帮我规划下一步」       → 必须按「留国内」回答，不能还提澳洲
```

**指标**：3 轮之后，回答里出现旧信息的比例。目标 0%。

### 4. 冲突处理（矛盾时听谁的）

```
记忆里：用户说「每周能学 15 小时」（source=user_stated, pinned=true）
对话里：用户随口说「我最近忙，一周大概 3 小时」
期望：不覆盖 pinned 那条，而是新增一条临时约束
```

**指标**：pinned 条目被修改的次数。**必须恒为 0**。

### 5. 可控性（用户改过的会不会被冲掉）

这是**最关键**的一条：

```
1. 用户手动编辑记忆：「我在准备澳洲岗位」→「我在准备新加坡岗位」
2. 之后聊 5 轮，其中一轮提到「澳洲那边机会不错」
3. 检查记忆：应该仍是「新加坡」，自动提取不能改回去
```

**指标**：用户编辑后，被自动覆盖的次数。**必须恒为 0**。

### 怎么跑这些测试

不是人工点，而是脚本化：

```python
# tests/memory_eval.py
cases = [
    {"name": "召回-澳洲岗位", "prefill": [...], "ask": "...", "expect_contains": ["澳洲", "出海"]},
    {"name": "精确-无关记忆", "prefill": ["用户养了猫"], "ask": "RAG 怎么分块", "expect_not_contains": ["猫"]},
    {"name": "时效-改主意", "turns": [...], "final_ask": "...", "expect_not_contains": ["澳洲"]},
    {"name": "冲突-pinned", "pinned": "...", "say": "...", "expect_unchanged": True},
    {"name": "可控-手动编辑", "edit": "...", "turns": [...], "expect_unchanged": True},
]
```

每条跑完记录：是否通过、耗时、token 消耗。

**跑一次约 5 分钟**（20+ 条 LLM 调用），可以放进 CI。
