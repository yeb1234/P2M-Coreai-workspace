# 检索元数据（路径 / 文件名）设计与实测

> 日期：2026-11-16
> 范围：`app/services/hybrid_search.py`、`app/services/lexical.py`、新增 `app/services/retrieval_meta.py`、`app/schemas.py`
> 数据快照：`siteyeb-pg` / `p2learning`，60,307 个语义块，8,785 个已索引视频，14,327 个视频

## 0. 一句话结论

路径和文件名必须进入检索，但**不要拼进每个块的向量**。
推荐做法：保留「只对字幕做向量」（策略 A），另开一路**视频级元数据词法通道**，
并让 rerank 看到路径文本。本方案已实现、可一键回滚，实测能把
「查某类课程」类查询从「完全答错」修到「第一条就对」，
代价是每次检索增加约 100–200ms、零重建索引。

## 0.1 回滚（唯一需要记住的一条）

```bash
# 回到 3.0 行为（三路融合变回两路、不给 rerank 拼路径、不补 meta 字段）
RETRIEVAL_META_ENABLED=0

```

没有数据迁移、没有索引重建，改回去**不需要重跑任何任务**。

## 1. 现状评估

### 1.1 代码层面：检索只看得见字幕正文

| 环节 | 位置 | 实际使用的字段 | 是否包含路径/标题 |
| --- | --- | --- | --- |
| 建块 | `embedding_pipeline._build_chunks` → `chunker.split_into_chunks` | `subtitle_segments.text` | ❌ 只写块正文 |
| 向量化 | `embedding_pipeline._embed_pending` | `content_chunks.text` | ❌ |
| 向量检索 | `vector_store.search` | `content_chunks.embedding` | ❌ |
| 词法检索 | `lexical.lexical_search` | `s.text ILIKE :term` | ❌（`v.title` / `v.filepath` 只出现在 SELECT 里，没进 WHERE） |
| 融合 | `hybrid_search.hybrid_search` | 两路 RRF：`lexical 0.8` / `vector 1.2` | ❌ |
| 重排 | `_api_rerank`（cross-encoder）/ `_llm_rerank` | 只有 `hit.text` | ❌ |
| 标题检索 | `lexical.title_search` | `videos.title` | ⚠️ 存在，但只被 `agents/tools.py` 的独立工具调用，不参与 `/api/search/hybrid` |

结论：**课程名、章名、课时名在检索链路里完全不可见**。
唯一例外是 `title_search`，它只被 agent 的「按标题找视频」工具使用。

| 事实 | 数值 |

| 已索引视频 / 视频总数 | 8,785 / 14,327 |

| 每视频块数：均值 / 中位数 / 最大 | 6.86 / 5 / 422 |

### 1.3 失效样例（改造前，`RETRIEVAL_META_ENABLED=0` 实测）

| 查询 | 改造前 top-3（全部来自向量通道） | 判断 |
| --- | --- | --- |
| 黑马前端 jQuery 第五章 | 《04.登录页面_标签和样式准备_》《06.首页_标签和样式准备_》《04-javascript书写位置》 | 全错。库里实际有 **117 个** jQuery 相关视频，一条没召回 |
| 什么是 GC 算法 | 《27633794_..._提示工程特训》《1--[视频]01.第01周知识精讲》《3--[视频]03.第01周作业点评》 | 全错。真正的视频叫《3、什么是GC算法》，没出现在 top-5 |
| jQuery 动画 获取元素位置 | 《10-爱旅行3》《02-获取位置》《15-爱旅行-自动轮播》 | 半对：第 2 条是对的，但第 1、3 条是「爱旅行」案例，和动画无关 |

两类查询的失败原因不同：

1. **「查某类课程」**（前两条）：答案只存在于路径里。字幕正文永远不会出现
   「这一节属于第五章 jQuery」这种话 —— 这是信息本身不在正文里，不是排序问题。
2. **ASR 错字**（第二条）：讲师说的是 GC，转写出来是 **「JC」**（见 `content_chunks`
   实际文本：「什么是JC算法…JC就是垃圾回收机制的简写」）。此时向量和词法
   都救不了，只有标题里那个正确的「GC算法」能救。

> 这段 ASR 错字是本次调研最有价值的发现之一：它说明**文本级重排也会跟着错**。
> 只把路径拼进索引而不给 reranker 看，等于让最后一个环节把正确答案删掉（见 §5.3）。

## 2. 元数据构造规则

实现：`app/services/retrieval_meta.py::build_meta(filepath, title)`，纯函数，不落库。

### 2.1 规则

1. **切根前缀**：`/videos/`、`/itjc/`、`D:/ITJC/`（沿用 `app/utils/paths.py` 的口径），保留大小写。
2. **逐层清洗**：每一层目录、文件名都过 `clean_video_title`（去站名、去 `(1)` 后缀）。
3. **丢噪音层**：只承担「装东西」的层级不参与语义 ——
   `视频` / `01、视频` / `02-视频` / `4.视频` / `录播` / `直播回放`。
   这些层每个视频都有，留在 meta_text 里只会稀释匹配。
4. **取最近 3 层目录**（`META_LEVELS=3`）+ **课时名**拼成 `meta_text`。
   再往上是「阶段三 / 01、视频」这类零信息量层级。
5. **课程名（course）**：跳过资料库分类层（`前端 / Python / 产品经理 / mksz`，可用
   `RETRIEVAL_META_LIBRARY_ROOTS` 覆盖）。`/videos/前端/黑马前端V7.6/...` → `黑马前端V7.6`。
6. **课时序号（lesson_no）**：`^(\d{1,3})[、.．:：\-_]` / `^第 N 节` / 纯数字。
   解析不到就是 `None`，**不猜**。
7. **短文件名兜底**：文件名只有序号时（`2.mp4`），课时名换成 `第 2 节`，
   语义完全由父目录提供。
8. **去重**：课时名已经包含最后一层目录时不再重复拼接。
9. **展示层级（display）**：`资料库 / 课程 / 最后一层目录`，最多 3 段，
   给前端卡片和 rerank prompt 用（比现有 `display_folder_path(levels=2)`
   多带了「章」这一层，见 §5.4）。

### 2.2 真实样例（全部来自库内数据）

**① 深层嵌套（用户给的例子）**

```
/videos/前端/黑马前端V7.6/01、视频/03、阶段三 JavaScript网页编程/05、第五章 jQuery/5-5 jQuery动画/02-获取位置【itjc8.com】.mp4
```

| 字段 | 值 |
| --- | --- |
| meta_text | `03、阶段三 JavaScript网页编程 / 05、第五章 jQuery / 5-5 jQuery动画 / 02-获取位置` |
| display | `前端 / 黑马前端V7.6 / 5-5 jQuery动画` |
| course / lesson / lesson_no | `黑马前端V7.6` / `02-获取位置` / `2` |

`01、视频` 被丢弃；`【itjc8.com】` 被清洗；两层章名都保留。

**② 中文目录名带站名后缀**

```
/videos/产品经理/Y亚慧ai产品经理课【itjc8.com】/01、01-【基础认知】AI产品经理岗位及就业规划.mp4
```

| 字段 | 值 |
| --- | --- |
| meta_text | `产品经理 / Y亚慧ai产品经理课 / 01、01-【基础认知】AI产品经理岗位及就业规划` |
| display | `产品经理 / Y亚慧ai产品经理课` |
| lesson_no | `1` |

注意：`【基础认知】` 是课程自己的章节标记，**必须保留**；
正则只删 `【itjc8.com】` 这种站点标记，不会误删 `【基础认知】`（见 textclean 的域名白名单）。

**③ 极短文件名（`03.mp4` / `02-获取位置`）**

```
/videos/前端/黑马前端8.0/01、视频/day-03/00-回顾.avi
→ meta_text = 前端 / 黑马前端8.0 / day-03 / 00-回顾

/videos/黑马ai大模型就业班(第八期)[itjc8.com]/视频/1-29 大模型Agent的原理及实践 2025-12-07/2.mp4
→ meta_text = 黑马ai大模型就业班(第八期) / 1-29 大模型Agent的原理及实践 2025-12-07 / 第 2 节
```

第二条是关键：文件名 `2` 单独没有任何语义，规则 7 把它变成「第 2 节」，
再用规则 4 的最近 3 层目录把它锚定到具体那节课。
**没有上层目录，`2.mp4` 不可检索；有了上层目录，它可以被「大模型Agent 原理」召回。**

**④ 同目录序号（`02` / `03`）**

序号**不拼进 meta_text**，只做结构化字段（`attach_sequence`）：

```
02-获取位置 → 第 2 / 9 节 | 上一节: 01-课程介绍 | 下一节: 03-滚动距离
```

理由：
- 数字本身歧义大（`5-5` 是「第五章第 5 节」，`02` 是「第 2 节」，`3-1` 是章-节），
  拼进文本会引入错误关联；
- 顺序是**关系**而不是内容。同目录的 9 个视频如果都拼上「jQuery动画 / 第 N 节」，
  它们彼此的向量会进一步靠拢（见 §3.4 实测）；
- 放在展示字段里，前端可以直接渲染「第 2/9 节 · 下一节：03-滚动距离」，
  模型也能据此说「建议按顺序看 03」。

实现方式：拿到最终 top_k 后，按父目录分组，一次 SQL
（`regexp_replace(filepath,'[^/]*$','') = ANY(:dirs)`，14k 行全扫约 **33ms**）
在本目录内按 `sort_key` 排序，得到 `position / total / prev / next`。
只在最终 ≤8 条上做，不参与排序。

## 3. 三种拼接策略的取舍

### 3.1 方案 A：现状 —— 只对字幕原文做向量

- **质量**：内容型查询（「闭包是什么」「函数返回另一个函数」）表现稳定，
  这类查询的答案确实在字幕里；课程型查询完全失效（§1.3）。
- **成本**：0。
- **重建索引**：无。
- 结论：**保留为基线**。它是唯一真正按「这段话讲了什么」排序的通道。

### 3.2 方案 B：`路径+文件名 + 字幕` 拼一起做向量

- **质量**：课程型查询会明显改善（向量里出现了 jQuery / 第五章）。
  但代价是**同视频所有块的向量被同一段前缀拉近**，段内区分度下降。
- **实测（视频 36679，45 块，前缀 98 字，bge-m3 / 1024 维）**：

  | 指标 | 仅字幕 | 路径+字幕 |
  | --- | --- | --- |
  | 同视频块两两余弦（mean / median） | 0.6123 / 0.6079 | **0.7777 / 0.7790** |
  | 跨视频（同课程另一门）余弦 | 0.5666 | 0.6693 |

  同视频相似度 +0.165（+27%），跨视频只 +0.103 —— 差异说明前缀主要提升的是
  「同视频内部的一致性」，而这恰恰是我们**不需要**的那部分：
  用户问「jQuery 动画」，要的是「02-获取位置」而不是「随便哪个块」。
  块数越多（库里最多 422 块）这个效应越强。
- **存储**：向量条数不变（60,307 × 2KB ≈ 118MB 向量本体），但**全部要重算**。
- **耗时（实测 42ms/块，batch=64，LM Studio bge-m3）**：
  60,307 × 42ms ≈ **42 分钟纯计算**，加分批 UPDATE 约 50–60 分钟；
  HNSW 索引重建（143MB）另计。
- **风险**：半途失败会造成「一半块带路径、一半不带」，检索分数不可比；
  需要一次全量重跑，且回滚也要再跑一次。

### 3.3 方案 C：`路径+文件名 + LLM 总结 + 字幕`

- **质量**：LLM 总结能补足「这门课在讲什么」的语义，理论上对课程型查询最友好，
  也是用户设想的「拼出更准确的视频描述」。
- **成本（硬约束）**：**当前只有 40 / 14,327 个视频有 `videos.summary`（0.28%）**。
  要对全库生效，等于新增 1.4 万次 LLM 调用；按本地 `qwen2.5:7b` 的经验值
  单视频数十秒算，是一个「跑一整晚」级别的批处理（**具体吞吐待验证**，
  本次没有实测，不要拍数字）。
- **一致性风险**：总结是派生数据，字幕重转会失效；`embedding_pipeline` 现在
  只判「块是不是基于当前字幕」，不判 summary 是否过期 —— 需要新的新鲜度标记。
- **幻觉风险**：总结里的错误术语会被写进向量，检索错了还很难发现。
- **存储**：向量条数不变，但 summary 文本要进 `meta_text`，前缀更长，
  稀释效应比 B 更严重。

### 3.4 推荐：A + 元数据词法通道（视频级），B/C 暂不铺开

| 维度 | A 现状 | B 拼进每块向量 | C 加 LLM 总结 | **D 元数据词法通道（本次实现）** |
| --- | --- | --- | --- | --- |
| 课程型查询 | ❌ | ✅ | ✅ | ✅（实测 top-1 正确） |
| 内容型查询 | ✅ | ⚠️ 段内区分度下降 | ⚠️ 更严重 | ✅ 不受影响（向量未改） |
| 重建索引 | 无 | 60,307 块全量（~50min） | 14,327 次 LLM + 全量向量 | **0** |
| 回滚 | — | 再跑一次 | 再跑一次 | **改环境变量，立即生效** |
| 新增延迟 | 0 | 0 | 0 | +100~200ms |
| 可解释性 | 低 | 低 | 中 | 高（命中标题/路径/章节可逐项解释） |

**为什么 D 优于 B**：路径是**视频级**信号，不是**片段级**信号。
把视频级信号塞进片段级向量，会让同一视频的所有片段互相靠近；
把视频级信号作为独立通道参与 RRF，则「一个视频最多贡献一条候选」，
不会挤占内容通道的名额。这是同一个信息放在不同层级的区别。

**为什么 D 优于 C**：D 用的是「文件名 + 目录」这种**免费、确定、永不过期**的
视频描述；C 用的是「花钱、可能错、会过期」的描述。在 D 已经能把
「什么是 GC 算法」修到 top-1 的情况下，C 的边际收益需要单独评估（见 §6）。

## 4. 已实现的改动（可直接回滚）

### 4.1 新增 `app/services/retrieval_meta.py`

| 函数 | 职责 |
| --- | --- |
| `build_meta(filepath, title)` | 纯函数，产出 `chain / course / recent / lesson / lesson_no / meta_text / display` |
| `folder_parts(filepath)` | 清洗 + 去噪音层的目录链 |
| `parse_lesson_no(stem)` | 课时序号解析（三种写法） |
| `meta_terms(query)` | 把查询拆成「可能出现在路径里的词」，额外保留去空格的整串（`什么是 GC 算法` → `什么是GC算法`） |
| `attach_sequence(hits)` | 同目录 `position / total / prev / next`，一次 SQL |

### 4.2 `app/services/lexical.py`：新增第三路召回

- `_document_frequency(terms)`：一条 `count(*) FILTER (...)` 统计所有词在
  `title + filepath` 上的文档频率（14k 行扫一遍约 40–70ms），带 10 分钟进程内缓存。
- `meta_search(query, ...)`：
  - **闸门 1（df 上限 2000）**：丢泛词。实测 df：黑马前端 6230 / 算法 810 /
    面试 758 / 第五章 524 / jQuery 117 / 组件通信 47 / 闭包 40 / GC算法 1。
  - **闸门 2（至少一个 df ≤ 600）**：整条查询都是泛词时，交回内容通道，不由路径决策。
  - **打分**：`Σ(词权重 × 命中位置系数) / Σ(词权重)`，词权重 `1/log2(2+df)`，
    位置系数 标题 1.0 / 文件名 0.95 / 路径 0.85。
    **先比命中几个词，再比命中在哪里** —— 早期版本给路径 0.5，导致
    「路径同时命中 jQuery + 第五章」的视频（0.85）输给「只有标题含 jQuery」的视频（1.0）。
  - **分数下限 0.30**：RRF 只看排名不看分数，0.15 分的「什么是 X」噪声排第 2
    照样能压过向量第 1（实测「什么是 GC 算法」top-2~5 全是这种噪声）。
  - **一个视频一条**：取「该视频内第一次提到查询词的块」，没有则取第 0 块。
    比固定取第 0 块更贴近用户想听的位置（第 0 块常常是「课程介绍」）。
  - **CTE 先截断视频候选再回块表**：不截断时，泛词（vue df=1520）会让相关子查询
    对上万个视频各算一次，单查询从 60ms 涨到 500ms+。

### 4.3 `app/services/hybrid_search.py` + `app/schemas.py`

- `Hit` 新增 `meta_score` / `meta`（`to_dict` 一并输出）。
- `schemas.py::HybridSearchHit` 增加两个可选字段（只加字段，不动其他 schema）：
  ```python
  meta: Optional[dict] = None
  meta_score: Optional[float] = None
  ```
  在此之前 Pydantic 会把这两个键静默丢掉，前端/agent 拿不到「这条属于哪门课、第几节」。
- 融合从两路变三路：`{"lexical": 0.8, "vector": 1.2, "meta": 1.5}`。
  meta 权重高于 vector 是有意的：它只在「路径能证明这条对」时出现，
  且一个视频只出一条；但仍低于「能证明这一段对」的重排，留出纠正空间。
- `_api_rerank` 送进 cross-encoder 的文档改为 `f"{meta_text}。{text}"`。
  **这是必不可少的配套**：否则「检索找对了、重排删掉了」。实测
  「什么是 GC 算法」在只送正文时，正确视频被 reranker 过滤（正文写的是「JC算法」）。
- `_llm_rerank` 的候选行加上 `[资料库/课程/章]` 前缀，让 listwise 模型能看到路径。
- 最终结果补 `meta`（展示字段 + 顺序），新增 `timings["meta_ms"]`、`timings["meta_seq_ms"]`。

4. 观察项：`timings.meta_ms`（应 < 250ms）、`degraded` 是否含异常、

### 5.2 延迟

| 项 | 数值 |
| --- | --- |
| `meta_ms`（df 冷启动） | 170–300ms |
| `meta_ms`（df 命中缓存） | 77–90ms |
| `meta_seq_ms`（同目录顺序） | 20–40ms |
| 关闭开关 | 0 |

测量条件（写报告时请带上限定语）：**全库 14,327 个视频 / 60,307 个块**，
单机 `siteyeb-pg` + 本机 LM Studio 的 bge-m3，串行执行。

「冷/热」的含义（**两档，不要只写一档**）：df 缓存是**进程内**的
（`_DF_CACHE`，写入后 10 分钟过期、上限 512 条），所以：

| 状态 | 该次 `meta_ms` | 什么时候发生 |
| --- | --- | --- |
| 命中缓存 | **77–90ms** | 查询里的词都在 TTL 内 |
| 有词需重算 | **170–300ms** | 进程重启后首次遇到该词，**或该词缓存已过期（10 分钟）** |

其中 df 统计本身约 **70–95ms/批词**（一条 `count(*) FILTER` 扫 14,327 行视频）。

所以稳态不是「永远 77–90ms」，而是「以 77–90ms 为主，**每个热词大约每 10 分钟
会重新统计一次**，那一次落回 170–300ms」。写报告时请两档都写，
否则读者会以为稳态只有 77–90ms。

### 5.3 一个必须记住的坑：重排会把路径找对的答案删掉

「什么是 GC 算法」的正确视频正文是 ASR 错字版（「JC算法」）。
只把路径拼进**索引**而不给 reranker 看，cross-encoder 判它不相关 →
`rerank_min_score=0.10` 直接过滤，用户仍然看不到正确答案。
所以「路径进检索」和「路径进重排」必须同时做，否则等于白做。

## 6. 关于「要不要加 LLM 总结」的明确答复

- **只拼字幕（A）**：内容型查询够用，课程型查询不行。
- **路径+文件名+字幕（B）**：能修课程型查询，但要付出全量重算向量
  （~50min）+ 段内区分度下降（同视频余弦 0.61 → 0.78）+ 不可灰度。
- **再加 LLM 总结（C）**：它解决的是「视频级描述」缺失。但：
  - 现在 14,327 个视频里只有 40 个有 summary，等于要从零做 1.4 万次调用；
  - 总结会随字幕变化过期，需要新的新鲜度机制；
  - 幻觉会直接污染向量，且不易发现。
- **本次采用（D）**：用「文件名 + 最近 3 层目录」当**免费的视频级描述**，
  单独走词法通道 + 喂给重排。实测已能把三个典型失败查询修到 top-1。

**如果以后要评估 C，建议的最小实验**（不做全量）：挑 50 个有 summary 的视频，
分别用「路径」「路径+summary」建两条独立通道，在同一批课程型查询上对比
top-5 命中率。只有当 summary 带来的提升显著高于「路径」时才值得铺开。

### 7.1 已知性能问题（本次未修）：`lexical_search` 的 2 字符词全表扫描

> 发现于：检索元数据通道改造时的性能剖析（2026-11-16）。
> 与本次改动**无关** —— 改造前就存在，也被记录为「本轮未修，留待下轮」。

**现象**：部分查询的词法通道耗时 **450–1050ms**，占总延迟的一半以上。
`timings.lexical_ms` 在「什么是 GC 算法」「闭包是什么」这类查询上尤其明显。

**触发条件（精确版）**：查询拆出的关键词里有 **不足 3 个字符**的词
（`算法`、`闭包`、`gc`）。`lexical_search` 用 `s.text ILIKE '%词%'` 匹配，
而 pg_trgm 的 GIN 索引要求模式里至少有 3 个字符才能抽出 trigram ——
**2 字符的词用不上索引**，退化成 60,307 行全表扫描。
3 个字符以上（`vue`、`组件通信`、`jQuery`）都能走索引。

**执行计划实证**（同一张表、同样返回少量行）：

| 词 | 字符数 | 执行计划 | 耗时 |
| --- | --- | --- | --- |
| `算法` | 2 | `Seq Scan`（rows removed 59,185） | **369ms** |
| `组件通信` | 4 | `Bitmap Heap Scan`（GIN） | **2ms** |

多个词之间是 `OR`，每个 2 字符词都触发一次全表扫描，叠加后接近 1s。

**实测（端到端 `timings.lexical_ms`，全库 60,307 块）**：

| 查询 | lexical_ms | 说明 |
| --- | --- | --- |
| 什么是 GC 算法 | 868–1048 | 拆出 `什么是`(47ms) + `算法`(350–380ms) + `gc`(300ms) |
| 闭包是什么 | 455–470 | `闭包` 为 2 字符 |
| Vue 组件通信 | 80–125 | 单词查询本身 2–6ms，慢在连接/多次往返 |
| 黑马前端 jQuery 第五章 | 32–65 | 词都 ≥3 字符，走索引 |
| 函数返回另一个函数 | 0 | 关键词被长度规则整个丢弃，**没有查库**（不是慢查询） |

> 注意：早期记录的「函数返回另一个函数 470–510ms」是错的 ——
> 那是一次错误归因，实测 `lexical_ms=0.0`。不要引用那个数。

**建议修法（下一轮，不在本次范围）**：
1. 2 字符词改用 `s.text % :term`（trigram 相似度 + GIN 索引）而不是 `ILIKE`，
   代价是召回口径变化，需要重新标定阈值；
2. 或对 2 字符词只做「前缀匹配」（`s.text LIKE '词%'`），索引可用但召回窄；
3. 或给 `content_chunks.text` 建 `pg_bigm` / 中文分词（`zhparser`）索引，一次性解决，
   但要装扩展 + 重建索引 326MB，属于架构级改动。

**为什么这次不顺手改**：它和元数据通道无关，改动会同时影响召回率和延迟；
当前工作区有多个并行改动，检索 SQL 是热点路径，不适合叠加实验性修改。

## 8. 遗留风险

1. ~~`meta` 字段前端还看不到~~ —— **已修**：`schemas.py::HybridSearchHit` 已加
   `meta` / `meta_score` 两个可选字段，`GET /api/search/hybrid` 现在会返回
   `display`、`lesson_no`、`position/total`、`prev/next`。前端渲染仍需自己接。
2. **同一视频可能出现两条**（一条来自 meta 通道、一条来自向量通道）。
   现有 `dedupe_overlapping(max_per_video=2)` 允许 2 条，本次未改
   （team 已确认：同视频 2 条可接受）。
   若要更严格，可把 `max_per_video` 调到 1（会影响所有查询，需单独评估）。
3. **`meta` 通道对「纯泛词查询」不触发**（如「黑马前端」「面试」）——
   这是设计选择：泛词的路径命中没有区分度。这类查询仍依赖内容通道。
4. **`_LIBRARY_ROOTS` 是数据快照推导的白名单**：新增资料库根目录（如「设计」「英语」）
   时课程名会退化成 `前端/新分类`，但不影响检索，可用环境变量补。
5. **ASR 错字的通用问题未解决**：本次只靠标题救回了 GC 这一例。
   批量错字（同音词、英文术语）仍需要字幕纠错流程（`subtitle_corrector.py`，默认关闭）。
6. **`meta_ms` 抖动**：冷启动 250ms，缓存命中 80ms。df 缓存是进程内的，
   多 worker 部署时每个进程各一份，命中率按查询分布决定。
7. **查询里的关键限定词不在路径上时，元数据结果会「降级为课程级」**：
   「MySQL 索引优化」里的「索引优化」在 14,327 条路径里 df=0，只剩 `MySQL` 一个词命中，
   于是顶部变成《05.安装MySQL - 了解需要安装哪些MySQL相关的软件》。
   这比改造前的向量噪声（《腾讯会议视频_主体识别_向量生成_存储向量数据库》）更贴题，
   但仍不是用户要的。生产默认开启 rerank，这类结果会被正文纠正；
   **如果以后要关掉 rerank 使用（如 `plan_agent`），需要接受这个精度损失**。
   根因是「路径只能证明课程对，不能证明这一节对」——这也是把 meta 权重
   控制在 1.5（而不是更高）的原因。
