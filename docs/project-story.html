01

这是什么

先说人话，再说技术。

想象你买了 30 门网课，加起来 1.4 万个视频文件，存放在硬盘里。你记得「有个老师讲过闭包的内存模型」， 但想不起来是哪门课、第几分钟。翻文件夹？14327 个文件名，翻不动。

这个系统就干三件事：

1把视频变成可搜索的文字

用 Whisper 把每节课的音频转成字幕，切成几秒一段的小块（359 万块），每块都记住「哪个视频、第几秒」。 从此视频不是黑盒，是可检索的文本。

2按意思找，不是按字面找

你问「函数返回另一个函数」，它能找到讲「闭包」的片段——这两个说法字面完全不同。 靠的是向量检索：把每段字幕变成一串数字，意思相近的数字也相近。

3能对话，还能记得你

不是「你问我答」，而是它会先查你的学习记录：看了多久、完成率多少、卡在哪个领域， 再结合检索结果回答，并给出带时间点的学习路径。

→
一句话定位（面试时可以直接用）： 一个面向个人技术学习者的 RAG 系统 —— 把非结构化的视频课程转成可语义检索的知识库， 再叠一层带工具调用的 Agent，做「找内容 + 做规划」两件事。

它不是什么

面试时主动划清边界，比夸大更加分：

  • 不是公网 SaaS。单机部署，面向个人，没有多租户、没有计费、没有横向扩展。
  • 不是通用视频平台。不转码、不切片分发、不做推荐流。它是「学习的检索层」。
  • 不是微服务。一个 FastAPI 单体 + 一个后台 worker，刻意不上服务网格那套。
  • 不是从头手写。主体由 AI 协作产出，我负责设计、决策、验证和排错——这点后面单独讲（第 08 节）。
02

架构长什么样

四个容器，三条数据流。先看整体，再拆每条流。

三条数据流

① 入库流：视频 → 可检索文本

文件扫描（watchdog 监听）
  → 建 videos 记录
  → 任务入队（Redis / RQ）
  → worker: ffmpeg 抽音轨 → Whisper 转写 → 切成片段
  → subtitle_segments 落库（359 万条）
  → 向量回填：bge-m3 批量嵌入 → pgvector（halfvec 半精度）
  → 建 HNSW 索引

这里有个设计取舍：转写和向量化都放后台，不在请求里做。 一个 2 小时的视频转写要几分钟，任何同步接口都扛不住。所以用 RQ 队列 + 数据库状态机双轨： 队列负责「跑起来」，数据库状态负责「跑得怎么样」，进程崩了能从状态恢复。

② 读路径：一句话 → 带时间点的片段

POST /api/search/hybrid?q=事件循环是什么
  ├─ 词法路：pg_trgm 三元组匹配（8~30ms）
  ├─ 语义路：bge-m3 嵌入 → pgvector HNSW 近邻（6~25ms）
  ├─ RRF 融合：按名次加权，词法 0.8 / 语义 1.2
  └─ LLM 重排：候选 20 条 → 精选 6 条（0.6~2.8s，可关）

为什么必须有两条路？它们失败的场景正好互补： 词法擅长精确术语（useEffect、版本号），但整句相似度会被长文本稀释； 语义能跨表述召回，但对生僻 API 名不敏感。单用任一条，抽检都会掉到 60% 以下。

③ 对话流：Agent 的 ReAct 循环

用户问「库里有讲事件循环的视频吗」
  → 组装上下文（人设 + 真实画像 + 长期记忆 + 会话摘要 + 最近 10 条）
  → LLM 决定调工具：search_video_titles + search_videos（可并行）
  → 工具返回压缩后的纯文本（不是原始 JSON）
  → LLM 组织回答，带《视频名》和时间点
  → SSE 逐 token 推给前端

这里有个不显眼但重要的细节：工具返回给 LLM 的是「人读得懂的短文本」，不是结构化 JSON。 早期试过直接塞 JSON，模型会浪费上下文去解析字段，回答质量反而下降。

04

六个关键取舍

面试官真正想听的不是「你用了什么」，而是「你为什么不用另一个」。 每条都按「背景 → 候选 → 决定 → 依据 → 代价」展开。

DECISION 01 · 存储

数据库要不要换成 PostgreSQL？向量放哪儿？

背景
SQLite 库涨到 15GB，其中 14GB 是一张向量表。单写锁导致转写任务和前端查询互相卡； 备份要停服务；换机器得拷整个文件。
候选
A. 不动 SQLite，另外装 Milvus 放向量
B. 换 PostgreSQL + pgvector，业务和向量同一个库
C. 换 MySQL + 独立向量库
决定
B。用一个容器解决两件事。
依据
关键判断是：业务库本身也是问题，不只是向量。 上 Milvus 只解决一半，SQLite 的 15GB、单写锁、备份难还在。 而 pgvector 0.8 的 HNSW 索引对 186 万条 1024 维向量完全够用 —— 实测单次查询 6~25ms。 Milvus 的优势（千万级以上、多租户、分布式）在这个量级用不上，却要额外维护 etcd + MinIO 三件套。
结果
库 15GB → 1.77GB（顺手清掉 14GB 废向量）； 359 万条片段迁移 53.8 秒（COPY 协议，6.7 万行/秒）。
代价说清楚：pgvector 的向量索引和业务表共享同一份内存与 WAL， 大规模写入时会互相影响；真到千万级向量或需要多租户隔离时，必须拆出去。 这不是「pgvector 比 Milvus 好」，是「这个量级选它更划算」。
DECISION 02 · Agent 框架

Agent 自己写，还是上 LangChain / LangGraph？

背景
原来的「小助手」是单轮问答：拼一段 prompt，调一次接口，返回。 没有工具调用、没有记忆、没有多步推理。要升级成 Agent，就得选框架。
候选
A. 自研 ReAct 循环（约 300 行）
B. LangChain + LangGraph 全家桶
C. 只用 OpenAI 原生 function calling，不引入框架
决定
B，但只用在两个地方：ReAct 对话 + 有状态规划图。
依据
自研的话，工具调用的循环控制、并行调用、状态图的中断恢复都得自己实现， 工作量不小且容易出错。LangGraph 的 StateGraph 天生适合 「诊断 → 检索 → 排步骤 → 校验 → 回退重排」这种带条件边的流程， 自研要写一套等价的状态机。
但反过来，LLM 调用层保留了一层极薄的封装（services/llm.py 约 100 行）， 不把框架的抽象直接铺到业务代码里 —— 出问题时能一眼看到实际发出的请求。
结果
8 个工具、SSE 流式、工具轨迹审计全部落地； 规划图 5 节点带条件边，实测产出 7 步路径、每步绑定真实视频。
代价说清楚：框架抽象层厚，出错时堆栈会绕好几圈。 应对方式是「所有 Agent 执行都记 agent_runs 表」—— 输入、工具轨迹、token 数、耗时全落库，出问题查表比读堆栈快。 另外 langchain 1.x 的 API 变动大，所以版本锁 >=1.0 且关键调用集中封装。
DECISION 03 · 检索

词法、语义，还是两个都要？

背景
原来的检索是 SQLite FTS5 + LIKE 兜底。实测发现中文查询根本命中不了， 而界面上还显示着「相关视频」。
候选
A. 只修词法（换 pg_trgm，够快够简单）
B. 只上语义（向量检索，够聪明）
C. 两路都做，用 RRF 融合
决定
C，并且加一层可选的 LLM 重排。
依据
实测两条路失败的场景正好互补：
· 纯词法：「FastAPI 依赖注入是怎么实现的」→ 前四条全是 from fastapi 这种碎片， 整句三元组相似度被长文本稀释；
· 纯语义：问「函数返回另一个函数」（不含「闭包」二字）能正确召回闭包内容，这是词法做不到的。
融合用 RRF（Reciprocal Rank Fusion）：不看绝对分数，只看各自排名， score = Σ w/(k + rank)，词法权重 0.8 / 语义 1.2。
结果
6 个已知答案的查询，top3 命中 18/18； 分数区间从旧方案的 0.35 提到 0.55~0.95。
代价说清楚：两路都查意味着延迟叠加、要同时维护两套索引。 优化办法是「按查询形态分流」：短查询（≤8 字）走完整词法， 长句直接跳过整句相似度只做术语匹配 —— 因为长句的整句 trgm 命中本来就不进前列， 纯属浪费。这一改把长句检索从 1.2 秒压到 157ms。
DECISION 04 · 向量精度

向量存 float32 还是半精度？

背景
1024 维向量，186 万条。float32 要 7.6GB 磁盘，全量加载进内存直接 把 16GB 的机器压死。
决定
halfvec(1024) 半精度（float16）+ HNSW 索引， 参数 m=16, ef_construction=64。
依据
半精度把存储和内存都砍半（7.6GB → 3.8GB）， 而句向量对精度不敏感 —— 余弦相似度的排序几乎不变。 HNSW 参数取 m=16 是召回率和内存的常见平衡点； ef_construction=64 建索引质量够用，建库时间可控。
配套限制
只对 ≥8 字的片段建索引。359 万片段里短于 8 字的多是 「嗯」「那个」这类 ASR 碎片，进了索引只会污染召回。
踩过的坑：一开始想用 hnswlib（独立索引文件），结果 Windows 上 编译失败（缺 MSVC）。这也反过来说明选 pgvector 的一个隐性好处 —— 它是数据库扩展，不需要编译原生库，安装就是 CREATE EXTENSION。
DECISION 05 · 队列

要不要引入 RabbitMQ？

背景
现有 RQ + Redis 跑后台转写。但 RQ 在 Windows 上用 SimpleWorker， 任务崩溃会带走 worker 进程 —— 这个缺陷让人想换一套。
决定
不换。保留 RQ，改执行模型。
依据
三条理由：
① 量级不匹配：日任务量几十个，RabbitMQ 的万级/秒吞吐完全用不上；
② 运维成本翻倍：Windows 装 RabbitMQ 要拖一个 Erlang 运行时，而 Redis 已经在跑了 （RQ + 缓存共用）；
③ 真正的问题不是队列选型：worker 崩溃的根因是「Windows 不能 fork」， 换任何 broker 都一样 —— 消费者崩了还是得重启。这是执行模型问题，不是消息中间件问题。
实际做法
队列负责「跑起来」，数据库状态机负责「跑得怎么样」。 任务状态落在 ai_jobs 表里，worker 重启时扫 running 的行重新入队， cancelling 的行直接终结 —— 不依赖 broker 的可靠性保证。
如果将来要动，正确顺序是：先做任务级子进程隔离（崩溃只死子进程）， 再看要不要换 broker。先换 broker 是治标 —— 这个判断在面试里比「我用了 RabbitMQ」值钱。
DECISION 06 · 部署

容器化到什么程度？

背景
原本靠 start.bat 起两个命令行窗口，依赖装在本地 venv。 换台机器就废，也没法交付给别人。
决定
四个服务全容器化（PG + Redis + 后端 + nginx 前端）， 但 保留本地 venv 开发模式。
依据
容器负责「交付和部署」，venv 负责「改代码」。 在 Windows 上把源码挂进容器做热重载，文件监听会慢得没法用 —— 所以不强行统一，两种模式并存，都能跑。
关键细节
· 后端容器内监听 8000 而不是 80（Linux 下非 root 不能绑 <1024 端口），由 nginx 映射；
· 依赖 condition: service_healthy 而不是只等容器启动；
· 入口脚本先等库可连、再建表、再起服务，避免启动顺序竞争；
· CUDA 拆成可选依赖，默认镜像 1.66GB 而非 4GB+。
代价说清楚：镜像 1.66GB 偏大（ffmpeg + 科学计算栈）。 进一步优化可以换成 Alpine + 按需装 ffmpeg，但这个项目是单机部署，镜像大小不敏感， 优先保证「拉下来就能跑」。
05

十个坑

按「现象 → 排查 → 根因 → 修复 → 教训」写。这些是面试里「你遇到过什么难题」的标准答料， 重点不是坑本身，而是你是怎么定位到它的。

01

中文全文搜索，一直是零命中

现象
搜索「依赖注入」「红烧肉」这类词，接口正常返回 200，但结果永远靠 LIKE '%词%' 兜底。 列表能出来，所以在页面上看着「好像能用」。
排查
直接在 SQLite 里跑 FTS5 的 MATCH，三条测试数据全部零命中。换 tokenize='trigram' 重建后，三条全部命中。
根因
FTS5 默认 unicode61 分词器按空格和标点切词。中文句子没有空格， 整句被当成一个 token —— 所以永远匹配不上。英文能搜、中文不能搜，这是最迷惑的地方。
修复
迁到 PostgreSQL 后用 pg_trgm（三元组），本质上和 trigram 分词同理： 把「依赖注入」切成「依赖注」「赖注入」这样的三字滑窗，中文天然可切。 GIN 索引让 ILIKE '%词%' 也能走索引，实测 3~32ms。
教训
「接口返回 200」和「功能正确」是两件事。这个 bug 活了半年没被发现， 因为它有兜底逻辑把错误掩盖成了「结果质量差一点」。 凡是带兜底的代码路径，都要单独验证主路径是否真的在工作。
02

319 万条向量，全是废数据

现象
库里有一张 14GB 的向量表，359 万条，看起来「已经做完了向量化」。 但检索出来的片段完全不相关：查「FastAPI 依赖注入」，返回「33B」「申考贝」「那猪那玩」。
排查

面试怎么答

每一条都标了「考察点」——知道对方想听什么，才知道该往哪答。

Q1为什么用 pgvector 而不是 Milvus？

考察点：你是「听过 Milvus」还是「真的权衡过」。

因为这个项目真正的瓶颈不止向量。当时 SQLite 已经 15GB，单写锁让转写任务和前端查询互相卡， 备份还得停服务。如果只上 Milvus，向量问题解决一半，业务库的问题原封不动。 pgvector 让业务数据和向量待在同一个库里，一个容器、一份备份、一次事务。 量级上也够：186 万条 1024 维，HNSW 实测 6~25ms。Milvus 的优势在千万级以上和分布式， 这个量级用不上，却要多维护 etcd 和 MinIO 三件套。

加分点：主动补一句「如果向量涨到千万级，或者要做多租户隔离，我会拆出去」—— 表明你知道它的边界在哪。

Q2混合检索为什么用 RRF，不直接加权求和？

考察点：你懂不懂「分数不可比」这件事。

因为两路的分数根本不在一个量纲上。词法那边是 pg_trgm 的三元组重叠率，范围 0~1， 但值域分布很偏；向量那边是余弦相似度，实际集中在 0.5~0.9。 直接加权求和，等于拿「摄氏度和华氏度加权平均」—— 权重调起来全靠试。 RRF 只用名次不用分数：score = Σ w/(k + rank)，k 取 60。 名次是天然可比的，而且对异常分数不敏感 —— 某一路给出一个离谱的高分也不会污染结果。

追问「权重怎么定的」：词法 0.8、语义 1.2。依据是抽检： 语义在跨表述召回上更可靠（问「函数返回另一个函数」能找到闭包）， 词法容易被短碎片干扰，所以给语义更高权重。

Q3RAG 的完整链路，从头到尾讲一遍

考察点：你脑子里有没有一张完整的图，而不是只知道「存向量、查向量」。

分两段。离线：视频 → ffmpeg 抽音轨 → Whisper 转写 → 切成 3~5 秒的片段落库 → bge-m3 批量嵌入（batch 256，约 84 条/秒）→ 写入 pgvector 的 halfvec 列 → 建 HNSW 索引。
在线：用户提问 → 同时跑词法和语义两路召回各 30 条 → RRF 融合 → 取前 20 条给 LLM 做 listwise 重排 → 精选 6 条 → 连同问题、画像、记忆、会话摘要一起组 prompt → LLM 生成回答 → SSE 逐 token 推给前端 → 回答里带《视频名》和 mm:ss。

容易被忽略的一环：重排是「锦上添花但不能拖死主流程」的， 所以设了 8 秒硬超时，超时直接退回 RRF 原序。检索的可用性不能依赖一个可能变慢的外部服务。

Q4Agent 和普通 RAG 有什么区别？你这个算 Agent 吗？

考察点：概念边界是否清晰，别把「调一次模型」说成 Agent。

普通 RAG 是固定流水线：检索 → 塞进 prompt → 生成。链路写死，模型只负责最后一步。 Agent 的核心区别是模型自己决定要不要调工具、调哪个、调几次。 这个项目里，问「库里有讲事件循环的视频吗」，模型会自己决定并行调 search_video_titles 和 search_videos 两个工具， 拿到结果后组织回答；问「我最近学得怎么样」，它会先调 get_learning_profile 和 get_recent_activity 拿真实数据，而不是凭空鼓励。

边界：它是「单 Agent + 多工具」，不是多 Agent 协作。 多 Agent 我刻意没上 —— 这个场景没有需要分工的子任务，加了只会增加不确定性和调试成本。

Q5工具调用怎么防止死循环？
两层。第一层是硬性上限：recursion_limit=12， 超过直接终止，避免模型反复调同一个工具。第二层是工具设计本身要幂等、要快： 检索类工具都是只读的，重复调不会产生副作用；单个工具控制在毫秒级，不会因为慢而超时重试。 另外所有执行都记在 agent_runs 表里，工具名、参数、返回摘要、耗时全落库 —— 出问题能复盘是哪一步开始跑偏的。

可以补一句：更根本的办法是让工具返回结果足够明确。 我所有工具返回的都是「人读得懂的短文本」，如果返回一堆 JSON 字段， 模型容易反复解析、反复确认，反而更容易绕圈。

Q6会话记忆怎么做的？为什么不用 LangChain 的 Memory？

考察点：你是套模板还是想过「记忆到底是什么」。

分三层，职责不同：
· 原始消息：最近 10 条原文直接进上下文；
· 会话摘要：超过 24 条时，把更早的对话压成 300 字要点（保留目标、结论、待办、偏好， 丢掉寒暄和推理过程），存在 chat_sessions.summary；
· 长期记忆：跨会话仍然成立的事实（目标岗位、明确偏好、约束）， 单独一张 memory_items 表，按重要度 + 新鲜度召回。

没用 LangChain Memory 的原因：它的抽象把「存哪儿、什么时候压、压成什么」 都藏起来了，而我需要控制压缩时机（按消息条数触发，失败就保留原文不做压缩）， 也需要和数据库事务对齐。这块逻辑一共不到 200 行，自己写比调框架更清楚。

Q7你怎么知道检索结果是「对的」？

考察点：这个是分水岭问题。答「感觉还行」就废了。

建了一个很小的评测集：6 个查询，每个我都知道正确答案在哪个视频。 比如「原型链继承」必须命中《10、原型链继承》那门课， 「RRF 融合重排」必须命中库里讲 RRF 的那一节。跑完看 top3 里有没有正确答案。 第一次跑是 18/18。

为什么这么小的集合也够用：因为我用它做「回归检测」而不是「证明系统多强」。 任何改动（换模型、调权重、改索引参数）之后重跑一遍，命中率掉了就说明改坏了。 6 个查询 30 秒就能跑完，成本低到可以每次改完都跑。

不要说「我用 RAGAS / 各种指标做了全面评估」。这个项目没做， 被追问具体指标怎么算、样本从哪来，会立刻露馅。
Q8为什么不微调模型？
因为问题不在模型能力，在数据。这个场景的失败案例几乎都是「字幕转写本身错了」 （ASR 把「闭包」听成「报表」这类），或者「库里根本没有相关内容」。 这两种情况微调都救不了 —— 前者要把字幕校对做好，后者要如实告诉用户没有。 微调适合的是「风格、格式、固定任务」这类问题，而检索增强适合「知识」问题。 我这个是知识问题。
Q916GB 内存的单机，怎么扛住 186 万条向量？
三个手段叠起来：
① 半精度存储：halfvec(1024) 而不是 vector(1024)，7.6GB → 3.8GB；
② HNSW 而不是暴力扫：不加载全量向量，靠图索引近似近邻， 查询只碰一小部分节点；
③ 入库前过滤：只对 ≥8 字的片段建索引， 359 万降到 186 万 —— 短片段多是 ASR 碎片，进索引只会污染召回。

顺带一提：最初试过 hnswlib，Windows 上编译失败（缺 MSVC）。 pgvector 是数据库扩展，安装就是一条 CREATE EXTENSION， 不需要编译原生库 —— 这在生产环境是个被低估的优势。

Q10为什么不上 RabbitMQ / Kafka？
量级不匹配，而且真正的问题不在队列。日任务量几十个，RabbitMQ 的吞吐优势完全用不上， 但 Windows 上装它要拖一个 Erlang 运行时，运维成本翻倍。 更关键的是：当时 worker 崩溃的根因是「Windows 不能 fork」， 任务崩溃会带走整个 worker 进程 —— 换任何 broker 都一样，消费者崩了还是得重启。 这是执行模型问题，不是消息中间件问题。

实际解法：队列只负责「让任务跑起来」，可靠性交给数据库状态机。 任务状态落在 ai_jobs 表，worker 重启时扫 running 的行重新入队， cancelling 的行直接终结。不依赖 broker 的持久化保证。

如果将来要动，正确顺序是先做任务级子进程隔离（崩溃只死子进程），再看要不要换 broker。 先换 broker 是治标。
Q11大改动怎么保证不把系统搞炸？

考察点：有没有工程纪律，而不是「改完能跑就行」。

四条：
① 先打 tag 留回滚点：动手前 baseline-before-3.0，任何时刻能回去；
② 源数据只读：迁移脚本用 mode=ro 打开旧库，一行都没写过 —— 这是「敢删 14GB 数据」的前提；
③ 分层提交：七次提交按依赖顺序，每层可独立回滚， 不是「一口气改完一次提交」；
④ 每层验证再往下走：迁移完先核对行数（359 万对不对）， 再跑检索，再做端到端。

补充：破坏性变更在提交信息里打 ! 标记， 并且写清楚「改了什么、为什么、怎么回滚」，方便未来的自己。

Q12这个项目最大的技术难点是什么？

考察点：你判断「难」的标准，暴露你的技术水平。

不是写代码，是判断东西有没有真的在工作。 中文检索失效、向量模型不匹配这两个问题，系统都不报错、不崩，接口一直返回 200。 它们以「结果质量差一点」的形式存在了半年。 我最后是靠「造一个已知答案的测试集，去问它答不答得上来」才发现的。

这件事给我的认知是：RAG 系统最大的风险是「静默劣化」。 传统服务挂了有 5xx、有告警；检索系统坏了只是答案变差，没人会发现。 所以后来我加的每个兜底逻辑都会想一句：它会不会把错误掩盖成「质量差」。

Q13前端流式输出怎么实现的？为什么不用 WebSocket？
用 SSE。对话是「客户端发一次、服务端持续推」的单向流，不需要双向通信， SSE 比 WebSocket 简单：基于 HTTP、能复用现有的鉴权和代理配置、断线自动重连。

两个实操细节：
① EventSource 不支持 POST，所以用 fetch + ReadableStream 手动解析 data: {...}\n\n 的帧；
② nginx 默认会缓冲响应，SSE 会被攒成一整块才发出去 —— 必须对那个 location 单独 proxy_buffering off，后端也发 X-Accel-Buffering: no 双保险。

前端渲染细节：token 是单字粒度（中文模型基本都这样）， 如果每个字都 setState，一秒钟触发几十次重渲染。 所以用 requestAnimationFrame 合并：token 先进缓冲区，按帧提交一次。

Q14如果让你继续做，下一步做什么？

按优先级三件：
① 补埋点。现在学习行为表基本是空的，所以画像里「观看时长」「活跃时段」 全是零。规划功能是有的，但输入数据不够，输出的建议就偏空泛。 这是当前最影响体验的短板。
② 字幕质量。ASR 错误是检索效果的天花板。 计划对高价值课程跑一轮 LLM 校对，把「申考贝」这类碎片修掉。
③ 全量向量化。现在只覆盖了 1.5%，全量约 186 万条、需 6 小时。 技术上没难度，是排期问题。

还有一个我想做但没做的：把「学习路径的完成情况」回流到推荐里 —— 现在路径是生成完就不管了，应该根据用户实际完成度动态调整后面的步骤。

三个真问题，和它们为什么难发现

01

密码是无盐 SHA-256，但登录一直「正常」

现象
登录、注册、改密码全都工作正常。功能测试不会失败——因为 SHA-256 确实能算出哈希、也确实能比对。
为什么难发现
密码哈希的问题只在数据库泄露时才暴露。平时它「能用」，而且是所有系统的默认写法。 真正的问题是：无盐 → 相同密码哈希相同；SHA-256 为速度设计 → GPU 每秒百亿次。
修复
换 PBKDF2-HMAC-SHA256（600k 迭代、随机盐、带算法前缀）。 关键是旧格式仍能校验、登录成功后透明重写——用户无感知，存量弱哈希随登录自然消失。
教训
「功能正常」和「安全」是两个维度。密码存储属于不需要测试、只需要审查的那类代码。
02

改了密码，下次还能用旧密码登录

现象
设置页点「修改密码」，提示「密码已修改」，页面清空输入框。然后退出、用新密码登录——失败； 用旧密码登录——成功。
根因
它改的是浏览器 IndexedDB 里的哈希，后端完全不知道。 upsertUser(currentUser, newHash) 确实执行成功了——改错了地方。
教训
这类「假成功」比报错难查一百倍：不抛异常、UI 反馈完整。 防线是写完之后从另一条路径读一次——改完密码就用新密码登录一次，30 秒成本。
03

359 万行的表，规划器以为它是空的

现象
检索能用，但某些查询莫名慢。查 pg_stat_user_tables 发现 subtitle_segments 的 n_live_tup 是 0，last_analyze 是 NULL。
根因
autovacuum 的默认分析阈值是 0.1 × 行数。批量导入 359 万行之后， 还要再变 36 万次才会触发一次 analyze——一次性导入的话，实际上永远不会发生。
修复
给大表设 autovacuum_analyze_scale_factor = 0.02，并立即 ANALYZE。 实测 359 万行只花 274 毫秒——成本极低，纯粹是没人记得跑。
教训
默认值是为「平均负载」设计的，不是为你的负载设计的。 用之前先问：它假设的使用模式，和我的实际情况一样吗？

面试官大概率会追问的三个问题

Q：你的令牌存在哪？

原来在 localStorage，现在在 httpOnly Cookie。原因不是「localStorage 不安全」这种笼统说法， 而是具体一条：localStorage 里的东西任何 JS 都能读，站点一旦有 XSS，一行 fetch 就能把会话带走， 而且服务端无从察觉——令牌是完全合法的。搬到 httpOnly 之后 document.cookie 读不到， XSS 的收益从「接管账号」降到「在当前页面里做点事」。代价是要做 CSRF，这是同一个决定的两面。

Q：多用户怎么隔离的？

数据表按 user_id 过滤，前端存储按用户分区加 u{id}: 前缀， 切换账号整页重载。这里踩过一个坑：代码里 if user_id is not None: filter(...) 读起来完全正确，但调用方永远传 None，等于统计全库。 所以隔离不能只看代码，得造两个用户互相查一次才算验证过。 越权访问返回 404 而不是 403——403 会暴露「这个 id 存在」。

Q：这个能上线吗？

单机到小团队规模可以直接跑，演示级部署有完整链路：Caddy 自动证书、pg_dump 备份、 16 项上线自检脚本。但我不认为它能做多租户 SaaS——没有组织概念，视频库是全局共享的， 没有审计日志和计费。要做那个得在数据模型上铺 tenant_id，是重构不是迭代。 说清楚边界，比声称什么都能干可信。

架构拆解：画出一条请求的完整链路

写什么
一张链路图，从用户点击到数据落地，每一层标两个东西：它负责什么、它挂了会发生什么。 然后列出三个「我认为的瓶颈」，每个都配一个可以验证它的方法。

不要写「分了控制器/服务/仓储三层」——那是结果，不是决策。 要写的是为什么这么分：哪一层必须能独立替换，哪一层值得为它多写一个抽象。
本项目实例
画出「浏览器 → Caddy → nginx → FastAPI → 数据层」之后，发现一个当时没意识到的事： nginx 只看得到 IP，看不到「谁」。所以在云上它一个人扛不住多用户限流， 按用户的速率和配额必须放到应用层。
这条结论是画图时得到的，不是写代码时撞出来的。
价值
链路图上每个「它挂了会怎样」，都是一次免费的故障演练。 这个问题答不上来的层，就是你还不够了解的层。
②

竞品对照：不比功能，比三个维度

比什么
数据模型：它把什么东西当成一个检索单元？一条还是成段？
策略分工：召回、融合、重排各自解决什么问题，边界在哪？
失败处理：断网、超时、依赖挂了，它是报错还是降级？
关键方法
找共同点。三个竞品都做的选择，往往是被现实教育过的结论，不值得重新发明。
找差异点，那才是你的机会所在。
本项目实例
看 RAGFlow、Dify、AnythingLLM，发现它们都做「分块 + 混合检索 + rerank」。 当时觉得是行业套路，等自己踩完碎片检索的坑才明白： 它们不是选择这么做，是被教训过。
价值
竞品对照最大的用处是砍需求。看完三家都没做的功能，大概率不是它们没想到， 而是做了也不划算。
③

评测口径：在写代码前定死「什么算好」

四件事
1. 用什么数据测 —— 固定查询集，20 条左右，必须含负例
2. 什么叫好 —— 命中率下限、相关性标准、延迟上限
3. 谁来判定 —— 人工判断 + 一个可量化的代理指标
4. 失败长什么样 —— 这条最重要，先写清楚错误的样子
为什么最重要的
是第四条。没有「失败长什么样」的时候，人会不自觉地把 「接口返回 200」当成成功标准。 这个项目里中文检索零命中跑了很久没被发现，就是因为 200 也是一种「成功」。
本项目实例
8 条查询，覆盖概念（闭包）、英文术语（useEffect）、跨表述（函数返回另一个函数）、 意图（RAG 召回 vs 重排）、以及应无结果（红烧肉怎么做）。
判定标准：top 3 里有几条真的能回答问题。负例标准：必须返回空。
代价
检索调了三轮才回正轨：第一轮调 RRF 权重，第二轮换 reranker， 第三轮才发现根因是检索单元只有 9 个字。

如果第一页就写了「8 条查询 + 人工判定」，第一天就会发现这个问题—— 随便一条查询的返回都是「我现在啊」「对吧」这种句子，肉眼可见。

最小形态：三页纸加起来不超过 1500 字

写多了就是浪费时间。每页三到五条，够用即可。

页最少要写可以省
架构拆解 一张链路图 + 每层的故障影响 + 三个待验证的瓶颈假设 详细时序图、完整部署拓扑
竞品对照 三个产品 × 同一个维度（数据模型 / 策略分工 / 失败处理） 功能清单、价格、截图
评测口径 20 条查询 + 判定标准 + 至少 3 条负例 完整测试报告、覆盖率数字

一句话总结：这三页纸加起来不超过 1500 字，但它决定的是「要不要返工三轮」。 而且它有一个额外好处——面试时被问「你怎么启动一个项目」，这三页就是现成的答案， 比「先看需求、再选技术栈」这种空话具体得多。
