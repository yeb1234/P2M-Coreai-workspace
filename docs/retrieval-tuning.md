# 检索质量调优

> 状态：部分现行（最后校对 2026-11-16）。「碎片检索 → 语义块检索」的切换已完成，文中「待回填向量 / 待切路由」的过程记录为历史；分块参数、A/B 评估方法、「绝对向量阈值不可用」的结论仍现行。
> 数据基线：截至 2026-11-16，`subtitle_segments` 3,593,723 条、`content_chunks` 60,259 块（向量覆盖 100%）、有字幕视频 8,785。

## 先说结论

**是的，太散了。而且不是「有点散」，是散到检索链路三个环节同时失效。**

实测数据（改造前碎片模式统计；截至 2026-11-16 `subtitle_segments` 为 3,593,723 条，长度分布本次未重跑）：

```
字幕片段 3,592,399 条（改造前实测）
平均长度        9 字（未核实，改造前实测）
中位数          8 字（未核实，改造前实测）
< 10 字占比  65.3%（未核实，改造前实测）
< 30 字占比  99.5%（未核实，改造前实测）
```

一条字幕是「那我们就来看一下」这种 8 个字的句子。拿它当检索单元，会坏三件事：

| 环节 | 为什么失效 |
|---|---|
| **向量** | bge-m3 对 8 字输入的编码几乎由字面重叠决定，不是语义。「我们来看一下」这类过渡句会以随机相似度混进结果 |
| **RRF 融合** | 词法和向量两条通路都在噪声上排序，融合后噪声叠加。加权调参是在噪声里调权重 |
| **Rerank** | 候选是一行 180 字截断的碎片，模型看不出相关性，只能靠标题猜 |
| **最终输出** | 8 条碎片加起来不到 100 字，模型没法据此回答任何实质问题 |

**所以这不是「参数没调好」，是输入单位错了。** 调 RRF 权重、换 reranker、调 top_k 都救不回来。

## 怎么评估「变好了」

不要凭感觉。用固定查询集做 A/B：

```
短查询（术语类）：  useEffect、Depends、闭包
长查询（意图类）：  函数返回另一个函数有什么用
                   FastAPI 依赖注入是怎么实现的
                   RAG 的重排为什么比召回更影响效果
跨表述查询：        什么情况下两个组件会互相影响（找 useEffect 依赖）
```

每条查询记录：**前 5 条里有几条真正相关**（人工判断）。

碎片检索的典型症状是：命中的 5 条都在同一个视频的相邻位置，
但每条只有一句话，**看起来相关实际全是废话**。
块检索的典型症状是：命中数量少，但每条都能直接回答问题。

一个可量化的代理指标：**命中块的厚度分布**（字符长度 / 覆盖的字幕段数）。
如果 top 5 的块加起来覆盖了 3 分钟以上，说明块够厚；
如果每条都只有 1–2 段，说明还是碎的。

## 一个容易搞反的点

**块的边界应该服从语义，不是服从字数。**

如果一段话在 300 字处正好讲完一个概念，就该在 300 字切，不要为了凑 400 硬塞下一句。
反过来，如果一句话说到 700 字还没完，宁可超长也别切断。

现在的实现用「累加到目标值 **且** 句末」来近似这个判断，是个折中。
真要做得更好，应该用 embedding 相似度做语义边界检测（相邻句向量相似度骤降处切分），
但那是另一个量级的工程。**先用标点边界 + 长度约束，覆盖 80% 的场景。**

## 顺带说：混合检索 + reranker 现在是对的吗

架构是对的，块化之后收益已经释放；2026-11-16 又加了第三路元数据通道。

```
词法（pg_trgm）  ─┐
向量（HNSW）    ─┼─ 加权 RRF 融合 ── rerank ── top_k
元数据（路径/标题）─┘
```

三路分工是合理的：
- 词法擅长**精确术语**（`useEffect`、`Depends`），这类查询纯向量会漏
- 向量擅长**跨表述**（问「函数返回另一个函数」也能找到闭包），这类查询纯词法会漏
- 元数据通道只在路径/标题能证明「这门课对」时出现，一个视频只出一条（见 `retrieval-metadata-design.md`）

RRF 用 `1/(k+rank)` 融合排名而不是分数，好处是不需要归一化各通路的分数尺度 ——
词法的相似度是 0–1，向量的余弦也是 0–1，但含义完全不同，直接加权相加会失真。

**这套设计没问题。** 块做好之后，再按固定查询集回来调权重。

## 关键修复：rerank 的「空结果」语义被吞掉了（已修复，现行代码保留该区分）

最后一项能修好，靠的不是阈值，是一个语义 bug：

```python
if not reranked:
    return candidates[:keep]   # 模型说「都不相关」，代码却返回原序
```

rerank 的 prompt 里明确写了「若都不相关则返回空数组」，但代码把**空数组**和**调用失败**当成同一种情况，
统一 fallback 回原序。等于把模型唯一能说「没有」的机会吞掉了。

修复后区分两者：空数组 → 返回 `[]`；异常/格式错 → fallback 原序
（现行代码：`hybrid_search.py:207-215,217-246`）。

实测「红烧肉」「量子计算机」正确返回空，「今天天气」仍返回 3 条 ——
LLM 的负判断不稳定，这个修复是概率性的，不是确定性的。

## 一个失败的尝试：绝对阈值（结论现行，样本为改造前实测）

本想用 `min_vector_score` 过滤无关结果，实测发现**不可行**（下面分数是当时那批查询的样本）：

```
无关查询（红烧肉）      0.487 – 0.512
无关查询（量子计算机）  0.529 – 0.545
相关查询（闭包）        0.579 – 0.590
```

差距只有 0.03–0.08。阈值设 0.55 会误杀一半相关内容，设 0.5 又挡不住无关结果。

原因：bge-m3 把任意中文文本的余弦相似度压缩在 0.4–0.6 这个窄区间，
**这个模型的分数不能当绝对相关性用**。

结论：**绝对阈值在这个模型上不可用**，只能靠 rerank 做相对判断；`min_vector_score`
默认 0.0（`hybrid_search.py:352`）。如果要更可靠，得换一个分数分布更分散的 embedding 模型，
或者训练一个 cross-encoder 打分器。
