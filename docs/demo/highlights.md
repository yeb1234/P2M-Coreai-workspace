# P2 项目亮点：8 个能讲、也能被验证的点

> 状态：现行（2026-11-16）。所有数字都带截止日期；历史实测数字在重录前复核，不用“实时”口吻讲。

## 先给一句话

P2 不是“又一个学习工具”。它把 14,327 条视频、359 万条字幕片段做成一个能检索、能记忆、能规划、能恢复的闭环；真正值得讲的是**三次失败之后怎么改**，不是用了多少技术栈。

如果只能讲一个，讲第 2 条：**系统把自己讲 RRF 的课，从自己的库里检索出来了。**

---

## 01 中文检索从“0 命中”救回来

**一句话卖点**：原来的 SQLite FTS5 对中文几乎不可用，换成 PostgreSQL + pg_trgm 后，中文查询从 0 命中变成 3–32ms 命中。

**证据**：

- 旧实现：FTS5 默认 `unicode61` 分词器，查“依赖注入 / Milvus 索引 / 红烧肉”都是 0 命中；切到 trigram 才命中。
- 新实现：中文词法走 `pg_trgm` + `ILIKE`，向量走 pgvector HNSW halfvec，标题/路径走元数据通道。
- 迁移结果：15GB SQLite → 1.77GB PostgreSQL；向量检索 26s → 6–25ms；359 万片段迁移 53.8s（COPY 协议）。

**怎么讲**：先说“中文检索完全失效”这个具体事故，再说“不是换一个分词器就能解决”，最后落到“业务库和向量库一起换，运维从两套变一套”。

**不要说过头**：这些是 2026-11-15 架构报告的实测快照；当前库的延迟要重新测。

---

## 02 三路 RRF：系统检索出了“讲 RRF 的课”

**一句话卖点**：词法抓 API 名和版本号，向量抓跨表述语义，元数据抓“这门课/这一节”；三路加权 RRF 融合后，系统把讲 RRF 的课程从自己的视频库里找了出来。

**证据**：

- 三路权重：`lexical 0.8 / vector 1.2 / meta 1.5`，`RRF_K=60`，`candidate_k=30`，`rerank_top_n=20`。
- meta 通道是视频级信号：一个视频最多贡献一条候选，不会挤占内容通道的名额。
- 6 个查询、18 个 top-3 位置全部命中；其中“RRF 融合重排怎么做”命中《node_rrf_融合重排和算法说明》。
- 长句优化后：Promise 链式调用 1202ms → 157ms；RRF 融合重排 1136ms → 171ms。

**怎么讲**：这是最适合现场讲的一个“自指”故事——你不是在背 RRF，你是用它检出了讲 RRF 的课。然后补一句：权重不是拍脑袋，meta 高于 vector 是因为它只在路径能证明“这门课对”时出现。

**不要说过头**：18/18 是 6 条查询的小评测，不是全量 benchmark；meta 通道也有“课程级对、节级不对”的已知退化。

---

## 03 从 SQLite + Milvus 到一套 PostgreSQL

**一句话卖点**：不是“上了向量库”，而是发现业务库本身也在拖后腿，于是把两套系统收成一套。

**证据**：

- 旧方案：SQLite 15GB、单写锁；Milvus 还要 Docker + etcd + MinIO，两套系统、两份备份。
- 新方案：PostgreSQL 17 + pgvector，业务表、向量表、全文/元数据索引在同一个库。
- 迁移后：库 1.77GB；359 万条字幕片段 53.8 秒迁完；向量检索 6–25ms。
- 边界：向量规模到 1000 万条或需要多租户隔离时，再考虑 Milvus；当前规模用 HNSW 够。

**怎么讲**：面试里不要只说“我选了 pgvector”，要说“我先判断业务库是不是问题，再决定要不要引入第二套系统”。这是架构判断，不是选型偏好。

**不要说过头**：1.77GB 是迁移当时的库体积；现在数据量更大，别把旧数字当实时。

---

## 04 记忆不是把聊天记录全塞进 prompt

**一句话卖点**：四层记忆结构，让“我想学 Java”能被接住，而不是每次都当新会话。

**证据**：

- L1 `chat_messages`：原始消息可回放。
- L2 `chat_sessions.summary`：超过 24 条压缩，保留最近 10 条；用 `summary_upto_message_id` 防并发覆盖。
- L3 `memory_items`：`fact / preference / goal / constraint / ability`，按 `pinned → importance → updated_at` 召回。
- L4 `user_data`：`p2m-profile-v1`、`p2m-persona-v1` 两个 KV，保存用户自填档案与助手设定。
- 抽取异步做，失败不影响当轮回答；`pinned` 条目绝不被自动覆盖，新条目置信度 ≥0.6 才覆盖旧主题。

**怎么讲**：先把“记忆”拆成四层，再说每一层的失败模式：摘要并发覆盖、长期记忆误覆盖、TTL 没传、去重只认完全相同字符串。能讲出缺陷，比说“我有记忆系统”可信。

**不要说过头**：当前记忆系统有 4 条已诊断未修缺陷（召回不过滤 confidence/source、按 importance 而非相关性、去重只认完全相同字符串、TTL 两条写入路径都不传）。演示时别把它们说成“已解决”。

## 05 可恢复的转写任务队列

**一句话卖点**：worker 被强杀后，DB 里的 `queued` 不会永远卡住；启动扫描和列表轮询都会把任务重新投递。

**证据**：

- 两个 RQ 队列：`ai_jobs` 负责转写/总结，`background` 负责其他重活。
- DB 状态机 + Redis 状态双向校对：`queued/started` 算活跃，`failed/finished` 不算。
- `sync_db_queue_to_rq` 在 worker 启动时修复；`reconcile_stuck_ai_jobs` 在列表 API 轮询时自愈。
- 队列可暂停；暂停只影响新任务，不杀正在跑的任务。
- 前端轮询有可见性自适应：前台 5s、后台 20s，避免一天上千次无意义查询。

**怎么讲**：先讲一次真实故障——worker 被强杀，RQ 把 job 标成 failed，但 DB 还是 queued，前端永远显示“处理中”。再说修法不是“换个更贵的 MQ”，而是把状态校对做进启动和轮询。

**不要说过头**：当前仍用 RQ `SimpleWorker`；任务级子进程隔离还没做，worker 崩溃仍会带走进程，只是状态能恢复。

## 06 学习路径绑定真实视频，不是编课程名

**一句话卖点**：路径里的每一步都指向视频库里真实存在的视频，能点开、能看、能统计完成度。

**证据**：

- 学习路径页的文案直接写明：“每一步都绑定你视频库里真实存在的视频，不是编出来的课程名”。
- 演示账号当前显示：累计观看 16 小时 38 分钟、接触 56 个视频、完成率 7%、单次专注 9 分钟。
- 路径按 7 步组织，当前 4/7 完成；每一步有预计小时数和真实视频。
- 之前的失败是：AI 自动生成 8,770 条模板笔记，学习行为数据几乎为零；所以这一版把“看视频”作为数据源，而不是让模型编笔记。

**怎么讲**：这是产品判断，不是技术亮点——学习系统的核心不是“生成一份漂亮计划”，而是计划里的每一项都能回到可执行的内容。

**不要说过头**：演示账号的数据是 seed 出来的；真实账号的数据要看当前库。

## 07 安全和运维不是“上线后再补”

**一句话卖点**：HttpOnly Cookie、CSRF、同源 CORS、分档限流、JSONL 日志和五服务资源上限，都是已经落地的边界。

**证据**：

- 会话主路径是 HttpOnly Cookie；Bearer 只给脚本/CLI 调用。
- CORS 只允许本地六个来源；注册默认关闭；登录按 IP 和账号双维度限流。
- 配额：chat 200/天、plan 20/天、admin ×5；chat 20/分钟/用户、plan 6/10 分钟、登录 30/IP/15 分钟。
- 日志：`logs/backend.jsonl`、`logs/worker.jsonl` 带 `ts / level / logger / msg / request_id / svc`；全量 JSONL 解析 0 坏行。
- 腾讯云覆盖层：backend 3g/2CPU、PG 2g/2CPU、Redis 512m、frontend 256m；日志 20m×5 / 10m×3 / 50m×5。

**怎么讲**：不要只报“我加了 JWT”。讲你为什么把 JWT 从 localStorage 挪到 HttpOnly Cookie，以及 CSRF 和 CORS 怎么配套；再讲一次日志排查的 request_id 链路。

**不要说过头**：这些是当前实现的边界，不代表通过渗透测试；没有 API 级集成测试。

## 08 把失败和边界留在文档里

**一句话卖点**：50 个 Markdown 文档全量校正，49 篇带状态标记；历史文档不删，过期处加“后续变化”。

**证据**：

- 2026-11-16 文档校正：50 个文件就地改，新建 `docs/README.md` 与 `docs/docs-refresh-2026-11-16.md`；`+1783 / −2180` 行。
- 文档状态分四类：现行 / 事实已核实 / 部分现行 / 历史参考；旧端口只保留在“已作废”标注里。
- 关键文档明确写出未修项：记忆 4 条缺陷、后端无 API 级集成测试、Alembic 与旧 `migrations.py` 并存、CORS 三处默认值不一致。
- 演示页本身也把“ESLint 不是全绿、腾讯云是假演示”写在边界一节。

**怎么讲**：这不是“文档写得多”，而是“这个项目能交给下一个人”。面试官问“你项目有什么问题”时，你能直接翻到已知缺陷，而不是现场编。

**不要说过头**：文档校正不等于代码全部验证；运行态行为仍需在目标机器上复测。

## 30 秒 / 90 秒版本

### 30 秒

> P2 是一个个人学习视频站，1.4 万条视频、359 万条字幕。最早中文检索 0 命中、向量检索 26 秒，我把它迁到 PostgreSQL + pgvector，做了词法/向量/元数据三路 RRF，长句延迟降到 157ms。现在它能从自己的库里检索出讲 RRF 的课程，也能把学习路径绑定到真实视频。腾讯云那版是轻量假演示，不声称真实 GPU 转写。

### 90 秒

> 我先讲三个失败：中文检索 0 命中、向量检索 26 秒、8,770 条笔记全是 AI 模板。然后讲三次修复：一套 PostgreSQL + pgvector 替掉 SQLite + Milvus；三路加权 RRF 替掉单向量；四层记忆替掉“把聊天记录全塞 prompt”。最后给两个证据：查“RRF 融合重排”命中库里讲 RRF 的那门课；学习路径 4/7 步，每一步都能点回真实视频。边界也讲：后端没有 API 级集成测试，腾讯云 demo 是预置数据。

## 面试可能追问

| 问题 | 回答方向 |
|---|---|
| 为什么不用 Milvus？ | 业务库也是问题；两套系统两份备份；当前规模 HNSW 够，1000 万条再考虑 |
| 为什么 meta 权重比 vector 高？ | 路径只能证明“这门课对”，不能证明“这一节对”；一个视频只出一条；仍低于 rerank |
| RRF 权重怎么定的？ | 先按通路可靠性给初值，再用小评测集调；不是全量 benchmark，18/18 只是 6 条查询的快照 |
| 记忆系统怎么防污染？ | 四层拆分、pinned 不覆盖、置信度门槛、异步抽取失败不阻塞；已知 4 条缺陷未修 |
| 任务中心为什么不用 Celery？ | 日任务几十个，吞吐用不上；Windows 多一套 Erlang；真正问题是崩溃恢复，已用 DB/RQ 双向校对 |
| 你有什么没做？ | 后端 API 级集成测试、任务级子进程隔离、真实 GPU 转写、完整公网多租户 |
