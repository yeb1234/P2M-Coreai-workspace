## 时间轴

### 00:00 — 00:40 开场：先给失败

（画面：架构页 hero，鼠标停在 14,327 上）

> 这是一个个人学习视频站，库里有 14,327 条视频、359 万条字幕片段。最早它有三个很具体的问题：中文检索 0 命中，向量检索要 26 秒，AI 生成的 8,770 条笔记全是模板。
>
> 这一版不是把页面做漂亮，而是把这三个失败修到能验证。下面用 8 分钟讲清楚：它怎么找、怎么记、怎么把几十分钟的转写跑完。

### 00:40 — 02:00 工作台 + 小助手：先看“能找到”

（动作：切到工作台；右侧小助手已打开，显示一条带课程引用的回答）

> 这是工作台。左边是待办、日历、番茄钟、笔记，右边是灵境小助手。注意回答里的课程名——不是模型编的，是检索结果，点进去就是视频库里的真实条目。
>
> 前端注册了 29 个页面，但首页只放 5 个 dashboard 插件：待办、日历、番茄钟、今日概览、最近笔记。插件里的数字和工作台下面的内容同源，不是两套假数据。

（动作：点一条回答里的课程链接，打开视频；停 2 秒）

> 这一步先让观众看到“能点”。后面再讲为什么能点到。

### 02:00 — 03:20 检索：三路召回，不是一条向量

（动作：切到架构页“检索”视角；鼠标沿三路走到 RRF）

> 检索有三路：词法抓 API 名、版本号、短词；向量抓跨表述语义；元数据抓这门课、这一节。三路各召回一批，再用加权 RRF 融合，最后送 rerank。
>
> 权重是词法 0.8、向量 1.2、元数据 1.5。元数据权重更高，是因为它只在路径能证明“这门课对”的时候出现，而且一个视频最多贡献一条候选，不会挤占内容通道。
>
> 这里有个我很喜欢的自指：我查“RRF 融合重排怎么做”，检索到的正是库里讲 RRF 的那门课。系统把自己实现的技术，从自己的数据里找出来了。

（动作：切到 IT视频站，搜索框输入“RRF 融合重排”，回车；展示结果）

> 这不是写死的推荐，是三路召回 + 重排的结果。长句原来要 1.2 秒，现在 157 毫秒；不是靠加机器，是把整句 trgm 换成技术术语 ILIKE。

### 03:20 — 04:20 学习路径：每一步都能点回视频

（动作：切到学习路径页，滚到路径卡片）

> 学习路径最容易造假：模型编几个课程名，看起来很完整，实际上一个都点不开。这一版反过来——每一步都绑定视频库里真实存在的视频。
>
> 当前这条路径 7 步完成 4 步；每一步有预计小时数，点开就是具体视频。上面的累计观看、完成率、单次专注来自真实播放行为，不是手填的。

（动作：点开一步，展示视频列表；不要真的播放太久）

> 这也是产品判断：学习系统的核心不是生成一份漂亮计划，而是计划里的每一项都能执行。

### 04:20 — 05:20 记忆：不是把聊天记录全塞进 prompt

（动作：回到工作台，点小助手右上角“聊天历史”）

> 记忆分四层：原始消息、会话摘要、长期记忆条目、用户档案 KV。超过 24 条消息就压缩，保留最近 10 条；摘要带 `summary_upto_message_id`，并发时不会互相覆盖。
>
> 聊天历史这里，标题不是一排“学习对话”，而是首条用户消息生成的主题，加 `#` 后 6 位 id、条数、时间。这样 100 多条会话才能找回来。

（动作：指着列表里的标题、`#id`、条数）

> 长期记忆还有两个边界：`pinned` 条目不会被自动覆盖；新条目置信度至少 0.6 才覆盖同主题。它不是“记住一切”，是“有选择地记”。

### 05:20 — 06:40 任务中心：worker 崩了也能恢复

（动作：切到 IT视频站，打开 AI 任务中心；如果队列为空，用架构页任务视角 + 截图）

> 转写不是发个请求然后等。API 写任务和状态，worker 从 Redis 消费；RQ 的 queued/started 和 DB 状态双向校对。
>
> 之前真实遇到过一次：worker 被强杀，RQ 把 job 标成 failed，但 DB 还是 queued，前端永远显示“处理中”。修法不是换更贵的 MQ，而是把状态校对做进 worker 启动和列表轮询。
>
> 现在队列可以暂停；暂停只影响新任务，不杀正在跑的任务。前端轮询前台 5 秒、后台 20 秒，不会一天打上千次空查询。

### 06:40 — 07:40 部署与边界：五服务，假演示

（动作：切到架构页“部署”视角）

> 部署是五个容器：frontend、backend、worker、PostgreSQL、Redis。端口规则五位：123 前端、124 API、125 数据库、126 缓存中间件，P2 尾号 02。数据库、Redis、API 只绑回环，对外走 `http://localhost/api`。
>
> 腾讯云那版是轻量假演示：预置视频、预生成字幕/转译、模拟任务进度；不声称真实 GPU 转写。它的作用是让界面和主链路在云上跑起来，不是替代生产转写。

### 07:40 — 08:00 收尾：把边界留在桌面上

（动作：切到架构页“边界”一节）

> 这一版能演示的是检索、记忆、路线和任务恢复。不能演示的是真实 GPU 转写、完整公网多租户、后端 API 级集成测试；ESLint 也还不是全绿。
>
> 我觉得这些边界比“全部完成”更值得讲——因为它们决定了下一版先修什么。

## 60 秒压缩版

> P2 是一个 1.4 万条视频的个人学习站。最早中文检索 0 命中、向量检索 26 秒。我把它迁到 PostgreSQL + pgvector，做词法/向量/元数据三路 RRF，长句从 1.2 秒降到 157 毫秒。现在查“RRF 融合重排”，能命中库里讲 RRF 的那门课；学习路径 4/7 步，每一步都能点回真实视频。腾讯云版是预置数据的轻量 demo，不假装真实 GPU 转写。

## 3 分钟压缩版

1. **00:00–00:30** 三个失败：0 命中、26 秒、8,770 条模板笔记。
2. **00:30–01:20** 架构：五服务、三路 RRF、四层记忆；用架构页“检索”视角讲。
3. **01:20–02:10** 工作台 + 学习路径：29 页面、5 插件、路径绑定真实视频。
4. **02:10–02:40** 任务恢复：DB/RQ 双向校对，worker 崩了不会永远 queued。
5. **02:40–03:00** 边界：后端无 API 集成测试；腾讯云是假演示。

## 被追问时的短答

| 追问 | 短答 |
|---|---|
| 为什么不用 Milvus？ | 业务库也是问题；两套系统两份备份；当前规模 HNSW 够，1000 万条再考虑。 |
| RRF 权重怎么来的？ | 按通路可靠性给初值，再用小评测集调；18/18 只是 6 条查询的快照。 |
| 为什么 meta 权重 1.5？ | 路径只能证明课程对，不能证明这一节对；一个视频只出一条；仍低于 rerank。 |
| 记忆会不会污染？ | 四层拆分、pinned 不覆盖、置信度 0.6 门槛、异步抽取；已知 4 条缺陷未修。 |
| 任务中心为什么不用 Celery？ | 日任务几十个，吞吐用不上；Windows 多一套 Erlang；真问题是崩溃恢复，已做 DB/RQ 校对。 |
| 你有什么没做？ | API 级集成测试、任务级子进程隔离、真实 GPU 转写、完整公网多租户。 |
