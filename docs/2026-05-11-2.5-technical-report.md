## 1. 报告定位

这份文档不是普通更新日志，而是一份面向软件开发研究和复盘的技术手册。它记录 2.5 版本中完成的关键改进、为什么这样改、具体改动到哪些层、用什么方式验证，以及这些实践对长期维护有什么价值。

SiteYeb / P2M CoreAI Workspace 当前定位是个人优先、本地优先、局域网友好的 CoreAI 工作台。它把待办、日历、番茄钟、时间中心、笔记、本地 IT 视频站、AI 转录总结、灵境小助手和插件导航放在同一个前端体验中。随着功能增多，2.5 的核心任务不再是继续堆功能，而是把已经复杂的功能整理成更清晰、可测试、可继续演进的结构。

本轮改进可以概括为一句话：

> 把“能用但容易乱”的逻辑，拆成“能解释、能测试、能回归”的模块。

## 2. 总体改进亮点

### 2.1 从功能堆叠转向结构化工作台

2.5 之前，很多功能已经存在，但部分逻辑集中在页面组件里，例如视频播放页、日历页、跨模块同步、通知面板、小助手上下文刷新等。随着用户界面和业务规则不断增加，页面组件容易出现以下问题：

- 事件处理、状态同步、UI 渲染混在一起。
- 鼠标、触摸、拖拽、悬停等交互重复计算。
- 同一类逻辑散在多个页面，每个页面都写一点。
- 前端测试很难直接覆盖内部规则，只能靠人工点击。
- 小 bug 修起来容易引入新回归。

2.5 的主要动作是把这些复杂点按职责拆开：

- 页面组件负责编排。
- hook 负责状态订阅和交互状态。
- 纯函数负责计算、过滤、转换和同步计划。
- contract test 锁住架构边界。
- Playwright 锁住真实布局。

### 2.2 重点优化方向

本轮重点覆盖以下方向：

- 页面路由懒加载和预加载。
- 共享时钟，减少重复定时器。
- AI 任务中心轮询降频和后台可见性判断。
- Todo 提醒按最近提醒时间唤醒。
- 灵境小助手上下文从固定轮询改为状态驱动。
- 日历派生数据集中化。
- Todo 到日历同步计划化。
- 视频播放器进度拖动和媒体事件拆分。
- 视频列表进度显示口径统一。
- 通知面板定位和时间文案纯函数化。
- 媒体查询监听集中化。
- Playwright 布局回归和 Vitest 契约测试扩展。
- README、changelog、踩坑记录、后续 TODO 完整更新。

## 3. 技术背景和主要问题

### 3.1 前端复杂度增长

随着页面数量增加，插件导航里已经不只是几个简单页面，而是包含：

- Dashboard
- Todo
- Calendar
- Notes
- Pomodoro
- Time Center
- IT 视频站
- Settings
- AI Agent
- 多个扩展插件页面

如果所有页面都同步打进首屏 bundle，首屏加载会变重；如果每个页面自己处理响应式、定时器、派生数据，又会出现重复逻辑。

因此 2.5 引入了更清晰的策略：

- 页面按插件懒加载。
- 导航 hover / touch 时预加载。
- 共享基础能力，例如媒体查询和时钟。
- 大页面只保留编排，交互细节下沉到 hook。

### 3.2 视频站复杂度过高

IT 视频站是当前项目里最复杂的前端模块之一，包含：

- 本地视频列表。
- 文件夹树和多文件夹选择。
- 搜索。
- 最近观看。
- 最新视频。
- 收藏。
- 继续观看。
- 播放器。
- 字幕。
- 雪碧图预览。
- AI 总结。
- AI 任务中心。
- 批处理。
- 播放列表。
- 右侧可拖拽面板。

这类页面天然容易变成“巨型组件”。2.5 继续拆分视频站，把播放控制、媒体事件、进度条、视频格式化、播放列表 UI 等逻辑分层。

### 3.3 日历和待办跨模块同步易混乱

Todo、Calendar、Pomodoro、Time Center 都会产生和时间有关的数据：

- Todo 有截止日期和提醒时间。
- Calendar 要显示 Todo 截止事件和提醒事件。
- Pomodoro 完成后要写入专注记录。
- Time Center 可以创建提醒，也可以同步 Todo 提醒。

这些模块如果互相直接写，很容易出现：

- 重复事件。
- 旧事件没有删除。
- 已删除 Todo 的日历事件残留。
- 提醒时间改了，但日历没有更新。
- 同步逻辑不好测。

2.5 把 Todo 到 Calendar 的同步拆成计划函数：先算出 add/update/delete，再执行写入。这样同步逻辑不再是 effect 里一段难测的过程代码。

### 3.4 固定轮询带来的性能浪费

之前部分逻辑依赖固定 interval：

- AI 任务中心固定刷新。
- 灵境小助手上下文固定 1.5 秒刷新。
- Todo 提醒曾经固定扫描。
- Header 时钟和时间中心可能各自启动定时器。

固定轮询简单，但会带来问题：

- 页面后台仍可能做无意义工作。
- 没有数据变化时也重复计算。
- 多个组件各自启动定时器，难以追踪。
- 测试中时间相关行为更难稳定。

2.5 的原则是：

- 真正需要时间推进的地方保留 tick，例如正在运行的番茄钟。
- 可由状态变化驱动的逻辑改为订阅状态变化。
- 可预测时间点的提醒改为 setTimeout 到最近提醒时间。
- 后台标签页降低刷新频率。

## 4. 关键改进一：插件页面懒加载和预加载

### 4.1 问题

插件页面越来越多，如果全部在应用启动时同步加载，会让首屏 bundle 变大。很多页面用户不一定每次都会打开，例如 Leetcode、Shop、Tokens、OpenClaw 等扩展页面。

### 4.2 改进方法

在 `src/config/pageRegistry.tsx` 中引入页面 loader：

- 用 `React.lazy` 懒加载页面组件。
- 建立 `PAGE_LOADERS` 映射。
- 提供 `preloadPage`。
- Sidebar 鼠标悬停时预加载。
- MobileTabBar 触摸时预加载。

这样首屏只加载当前需要的页面；用户准备切换页面时，提前拉取目标页面 chunk，减少点击后的等待。

### 4.3 技术细节

设计思路：

- 路由注册仍然统一在 page registry。
- 页面入口不再全部静态 import。
- 每个页面对应一个动态 import 函数。
- 预加载只触发 import，不强制切换页面。

典型模式：

```tsx
const TodoPage = lazyPage(() => import('../components/todo/TodoPage'), 'TodoPage');

export const PAGE_LOADERS = {
  todo: () => import('../components/todo/TodoPage'),
  video: () => import('../components/video/VideoPage'),
};

export function preloadPage(id: ActiveView) {
  void PAGE_LOADERS[id]?.();
}
```

### 4.4 验证方式

新增契约测试锁住以下内容：

- `pageRegistry.tsx` 必须包含 `React.lazy`。
- 必须包含 `preloadPage`。
- Sidebar 必须在 hover 时预加载。
- MobileTabBar 必须在 touch 时预加载。

这种测试不是验证 UI 像素，而是验证架构不会被以后误改回同步加载。

## 5. 关键改进二：共享时钟，减少重复定时器

### 5.1 问题

Header 上有实时时钟，Time Center 也有当前时间、秒表、倒计时等。不同组件如果各自 `setInterval`，会造成：

- 多个 1 秒定时器并存。
- 后续维护时不知道谁在刷新。
- 页面切换时容易忘记清理。

### 5.2 改进方法

新增 `src/hooks/useClockNow.ts`：

- 全局只维护一个 timer。
- 组件订阅当前时间。
- 没有订阅者时清掉 timer。
- Header 和 Time Center 共用同一个 hook。

### 5.3 技术细节

核心思想类似轻量级外部 store：

- module scope 存当前时间。
- module scope 存 listener set。
- 第一个订阅者启动 interval。
- 最后一个订阅者卸载时停止 interval。

这样多个组件读取同一个时间源，不再各自开 timer。

### 5.4 验证方式

契约测试检查：

- Time Center 使用 `useClockNow`。
- Time Center 内部不再直接 `setInterval`。
- 秒表状态通过 base elapsed 计算，不额外维护另一个 interval。

## 6. 关键改进三：AI 任务中心自适应轮询

### 6.1 问题

AI 任务中心需要刷新任务状态，但固定轮询容易浪费资源。尤其后台标签页里，用户看不到页面，继续高频请求没有意义。

### 6.2 改进方法

在 `src/hooks/useAiJobCenter.ts` 中改为：

- 页面可见：3 秒刷新。
- 页面不可见：10 秒刷新。
- 使用 `setTimeout` 链式调度，不使用固定 `setInterval`。
- 监听 `visibilitychange`，可见性变化后重新安排下一次刷新。
- 后台时避免刷新当前视频详情。

> 后续变化（2026-11-16 现状）：自适应轮询的 `setTimeout` + `visibilitychange` 骨架保留，但间隔已调整为可见 5 秒 / 不可见 20 秒（`src/hooks/useAiJobCenter.ts:378`），不再是文中的 3 秒 / 10 秒。

### 6.3 技术细节

`setTimeout` 比 `setInterval` 更适合这里：

- 每次请求完成后再决定下一次。
- 避免请求慢时多个 interval 重叠。
- 可以根据当前队列状态和可见性动态调整间隔。

### 6.4 验证方式

契约测试检查：

- 包含 `document.visibilityState === 'visible' ? 3000 : 10000`。
- 监听 `visibilitychange`。
- 使用 `window.setTimeout(tick)`。
- 不使用 `window.setInterval`。

## 7. 关键改进四：灵境小助手上下文状态驱动

### 7.1 问题

灵境小助手需要知道当前页面上下文，例如当前视频、当前笔记。之前为了让上下文保持最新，使用 1.5 秒固定刷新：

- 即使页面内容没变，也重复读取状态。
- 小助手打开时一直空转。
- 这种逻辑不利于性能，也不够精确。

### 7.2 改进方法

新增 `src/hooks/useAssistantPageContext.ts`，让小助手直接订阅相关状态：

- `activeView`
- `activeNoteId`
- 当前视频
- 笔记列表更新时间 fingerprint

状态变化时重新计算上下文；没有变化时不刷新。

### 7.3 技术细节

小助手上下文构建仍复用 `getAssistantPageContext()`，但触发机制从 interval 改为 React/Zustand 状态订阅。

关键点：

- 小助手面板传入 `chatOpen`。
- 只有打开时才更新上下文。
- 视频页关注当前视频 id、summary、transcription、segments。
- 笔记页关注 active note 和笔记更新时间。

### 7.4 技术收益

- 去掉 1.5 秒固定轮询。
- 当前视频切换、笔记更新时更及时。
- 上下文刷新原因更明确。
- 后续接入 Todo、Calendar、Pomodoro 上下文时可以继续扩展 hook。

### 7.5 验证方式

契约测试检查：

- `AIChatPanel` 使用 `useAssistantPageContext(chatOpen)`。
- `AIChatPanel` 不包含 `window.setInterval`。
- `AIChatPanel` 不包含 `1500` 固定轮询数字。
- hook 依赖 `useVideoStore`、`useNotesStore`、`useUIStore`。

## 8. 关键改进五：Todo 提醒按最近时间唤醒

### 8.1 问题

待办提醒如果固定每 15 秒扫描一次，在没有提醒时也会持续运行。对于个人工作台，这种浪费不大，但随着模块增多，每个功能都这样做，整体会变差。

### 8.2 改进方法

在 `useCrossModuleSync` 中：

- 遍历未完成且有提醒时间的 Todo。
- 找到最近的未来提醒时间。
- 如果提醒时间到了，触发通知和声音。
- 如果还有未来提醒，只安排一次 `setTimeout` 到最近提醒时间，最多 60 秒兜底。
- Todo 状态变化时 250ms 后重新计算。

### 8.3 技术细节

这个方案本质是“事件驱动 + 最近 deadline 调度”：

- 有提醒才设置 timer。
- 没有提醒就不保留 timer。
- Todo 更新会重新安排。

### 8.4 验证方式

契约测试检查：

- 提醒逻辑包含 `nextReminderAt`。
- 使用 `setTimeout(runReminderCheck)`。
- 提醒逻辑不使用 `setInterval`。
- 不再出现固定 `15000` 轮询。

## 9. 关键改进六：Todo 到日历同步计划化

### 9.1 问题

Todo 到 Calendar 的同步涉及多种情况：

- Todo 新增 dueDate，需要创建日历事件。
- Todo 修改 dueDate，需要更新日历事件。
- Todo 删除 dueDate，需要删除日历事件。
- Todo 新增 reminderAt，需要创建提醒事件。
- Todo 修改 reminderAt，需要更新提醒事件。
- Todo 被删除，需要清理残留日历事件。

如果这些逻辑直接写在 effect 里，很难单独测试。

### 9.2 改进方法

新增 `src/hooks/todoCalendarSyncPlan.ts`：

- 输入：当前 todos、当前 calendar events。
- 输出：同步计划。
- 计划包含：
  - `add`
  - `update`
  - `delete`

`useCrossModuleSync` 只负责执行计划：

```ts
const plan = buildTodoCalendarSyncPlan(todos, calendarStore.events);
plan.add.forEach((data) => calendarStore.addEvent(data));
plan.update.forEach(({ id, data }) => calendarStore.updateEvent(id, data));
plan.delete.forEach((id) => calendarStore.deleteEvent(id));
```

> 后续变化（2026-11-16 现状）：这个独立的「计划函数」文件后续重构中已移除；Todo/日历联动改走 `src/stores/scheduleStore.ts` 的排程数据，同步逻辑在 `src/hooks/useCrossModuleSync.ts` 内完成。

### 9.3 技术细节

同步使用两个 marker 区分自动生成事件：

```ts
export const TODO_DUE_MARKER = 'todo:due';
export const TODO_REMINDER_MARKER = 'todo:reminder';
```

这样清理时只删除自动生成的 Todo 事件，不误删用户自己创建的普通日历事件。

### 9.4 技术收益

- 同步规则可测试。
- effect 变薄。
- 以后排查重复事件更容易。
- 后续接入更多自动事件时，可以继续扩展计划函数。

### 9.5 验证方式

新增 `src/__tests__/todoCalendarSyncPlan.test.ts`：

- 有 dueDate/reminderAt 时生成两个 add。
- 已有事件时生成 update。
- Todo 不存在时删除残留自动事件。

契约测试还要求：

- `useCrossModuleSync` 只调用 `buildTodoCalendarSyncPlan`。
- `dueData` / `reminderData` 不再写回 effect hook。

## 10. 关键改进七：日历派生数据集中化

### 10.1 问题

CalendarGrid、WeekView、CalendarPage 都需要从事件和 Todo 中派生数据：

- 哪些事件显示。
- 哪些 Todo 已完成。
- Todo 按日期分组。
- 月视图有哪些事件。
- 周视图有哪些事件。
- 某天详情有哪些事件。
- 番茄热力图如何计算。

如果每个组件各自处理，会出现规则不一致。

### 10.2 改进方法

新增 `src/components/calendar/calendarDerivedData.ts`，集中提供：

- `createCompletedTodoLookup`
- `shouldShowCalendarEvent`
- `groupEventsByDate`
- `groupTodosByCalendarDate`
- `getEventsForCalendarMonth`
- `getEventsForCalendarDates`
- `getEventsForCalendarDate`
- `getPomodoroHeatMapForMonth`

### 10.3 技术细节

核心思想是让 UI 组件只关心：

- 当前月有哪些天。
- 哪些事件属于这些天。
- 哪些 Todo 属于这些天。
- 当前视图如何展示。

过滤规则集中在 helper 中：

- 已完成 Todo 可以影响 Todo 事件显示。
- reminder / event / pomodoro 的显示规则统一。
- 月视图和周视图复用同一组函数。

### 10.4 验证方式

契约测试检查：

- helper 包含关键函数。
- CalendarGrid、WeekView、CalendarPage 使用 helper。
- CalendarPage 不再直接 `Object.values(calendarEvents)`。
- 月/周 days 使用 `useMemo`。

## 11. 关键改进八：媒体查询集中化

### 11.1 问题

多个组件各自写：

- `window.matchMedia`
- `window.innerWidth`
- resize listener

这会造成重复监听，也容易 SSR 或测试环境出错。

### 11.2 改进方法

新增 `src/hooks/useMediaQuery.ts`：

- `useMediaQuery(query)`
- `useIsMobile(breakpoint = 768)`
- `useWindowWidth()`

替换使用位置：

- AppLayout
- TodoFilters
- VideoPage
- VideoPlaylistPanel
- CalendarGrid

### 11.3 技术收益

- 响应式判断统一。
- 组件少写浏览器 API。
- 测试更好锁定。
- 后续需要优化 resize 策略时只改 hook。

### 11.4 验证方式

契约测试检查：

- hook 导出三个函数。
- 关键组件使用 hook。
- 关键组件不再直接 `window.matchMedia`。
- CalendarGrid 不再直接 `window.innerWidth`。

## 12. 关键改进九：视频播放器进度条拆分

### 12.1 问题

视频播放器进度条涉及多种输入：

- 鼠标按下跳转。
- 触摸开始跳转。
- 拖动过程持续 seek。
- mousemove 计算悬停时间。
- SpritePreview 悬停位置。
- 控制条容器宽度。

之前这些逻辑分散在 `VideoPage.tsx` 中，重复计算百分比：

```ts
Math.max(0, Math.min(1, (clientX - rect.left) / rect.width))
```

### 12.2 改进方法

新增 `src/components/video/useVideoProgressScrubber.ts`：

- 统一 `getClientX`。
- 统一 `getRatioFromClientX`。
- 统一 start scrub。
- 统一 drag move。
- 统一 hover preview。
- 返回 `progressBarRef`、`hoverTime`、`hoverX`、`playerWidth` 和回调。

### 12.3 技术细节

hook 接收：

- `videoRef`
- `videoContainerRef`
- `duration`
- `onProgressChange`

hook 输出：

- `progressBarRef`
- `hoverTime`
- `hoverX`
- `playerWidth`
- `startScrub`
- `updateHover`
- `clearHover`

VideoPage 只负责把这些交给 `VideoPlayerControls`。

### 12.4 技术收益

- 鼠标和触摸使用同一套进度计算。
- hover 预览和拖动不会各算各的。

## 14. 关键改进十一：视频进度显示口径统一

### 14.1 问题

视频列表和播放列表都有进度条，但播放列表里的 `PlaylistItem` 没有真实 `duration` 字段。之前为了显示进度，曾使用：

```ts
watch_progress / (watch_progress + 60)
```

这会制造“看起来像真实进度”的假比例。

### 14.2 改进方法

在 `src/components/video/videoFormat.ts` 中新增：

- `getWatchProgressPercent(progress, duration)`
- `formatWatchProgress(progress, duration)`

规则：

- 有真实 progress 和 duration 才返回百分比。
- 没有真实 duration 返回 `null`。
- UI 收到 `null` 时不画进度条。

### 14.3 技术收益

- 视觉展示更诚实。
- 后续如果后端给 PlaylistItem 增加 duration，可以自然显示真实进度。
- 避免误导用户。

### 14.4 验证方式

新增 `src/__tests__/videoFormat.test.ts`：

- 30/120 = 25%。
- 超过 100% 时 clamp 到 100。
- 负数 clamp 到 0。
- 缺 duration 返回 null。
- 格式化输出一致。

## 21. 对软件开发研究的价值

这轮改进很适合作为软件开发报告案例，原因是它不是单纯“做功能”，而是覆盖了真实项目演进中更难的部分。

### 21.1 从用户反馈到结构改进

很多改动来自真实使用中的问题：

- 视频页左右间距不舒服。
- 番茄钟背景音切换乱。
- AI 任务中心规则难理解。
- 深色主题不好看。
- 设置按钮不能折返。
- 播放列表宽度难调。
- 移动端页面原始。

这些问题表面是 UI 和体验，深层是状态、布局、测试、数据口径和架构边界。2.5 的价值在于没有只修表面，而是把多次出现的问题归纳成通用能力。

### 21.2 用小抽象解决真实重复

本轮新增的抽象都比较小：

- `useMediaQuery`
- `useClockNow`
- `useAssistantPageContext`
- `useVideoProgressScrubber`
- `useVideoElementEvents`
- `calendarDerivedData`
- `todoCalendarSyncPlan`
- `notificationPanelPosition`
- `notificationTime`

这些不是为了抽象而抽象，而是每个都对应明确痛点：

- 重复监听。
- 重复定时器。
- 重复计算。
- 页面组件过厚。
- effect 不可测试。
- UI 逻辑无法单测。

### 21.3 组合测试策略

2.5 形成了三层验证：

1. 纯函数单测：验证计算规则。
2. 契约测试：验证架构边界。
3. Playwright：验证真实布局和主题。

这种组合比只写一种测试更适合复杂前端工作台。

### 21.4 渐进式重构

本轮没有推倒重写，而是渐进式拆分：

- 先保留行为。
- 再抽 hook。
- 再补测试。
- 再跑构建。
- 再补 Playwright。
- 最后更新文档和提交。

这是一种适合个人项目、小团队项目的务实重构方式。

## 23. 结论

SiteYeb / P2M CoreAI Workspace 2.5 的核心价值不是某一个单点功能，而是把项目从“个人工具快速堆功能”的阶段，推进到“可以长期维护、可以测试、可以复盘、可以继续扩展”的阶段。

这轮改进体现了几个重要软件工程原则：

- 先让真实工作流跑起来，再从痛点中抽象。
- 抽象要小，必须对应真实重复和真实风险。
- 能用状态驱动就不要固定轮询。
- 能做纯函数就不要藏在 effect 里。
- 能用契约测试锁住结构，就不要只靠人工记忆。
- UI 改动要用 Playwright 看真实布局。
- 文档不是最后的装饰，而是维护系统的一部分。

因此，2.5 很适合作为一个个人 CoreAI 工作台从原型走向稳定版的开发报告案例，也适合作为研究“如何在真实使用反馈中渐进式重构前端复杂系统”的样本。
