## 1. 本轮目标

2.6 不是大规模加新插件，而是把 2.5 后真实使用中暴露出来的几个“状态不可信、刷新不稳定、预览不清晰”的问题彻底收口。

本轮重点：

- 番茄钟刷新后状态残留。
- 番茄钟临时运行态和永久历史/配置的存储边界。
- 番茄钟设置、完成历史和轻量运行态的后台 v2 同步。
- Todo、日历1、日历2 统一到后台 `schedule_items`。
- 日历2 拖动更新和同时间段任务冲突显示。
- 主题刷新后回到默认皮肤。
- 视频播放器雪碧图预览不可见或质量过低。
- 视频主界面 hover 预览缺失。
- 相关测试、契约和文档补齐。

## 2. 问题一：番茄钟重置/跳过后刷新又恢复旧状态

### 2.1 现象

用户点击番茄钟“重置”或“跳过”后，界面看起来已经回到初始状态。但马上刷新浏览器，页面又恢复出旧的专注倒计时，甚至继续显示之前的专注阶段。

这类问题非常影响信任感。时间管理工具的状态必须可解释：点了重置就应该重置，点了跳过就应该进入明确的下一阶段或停止状态。

### 2.2 排查过程

排查集中在 `src/stores/pomodoroStore.ts` 和本地存储适配器 `src/lib/idbStorage.ts`。

当时发现两个关键点：

1. `resetTimer()` 会重置 `timer`，但没有稳定清理 `_lastTickTimestamp`。
2. 番茄钟使用 `localOnlyStorage`，这个存储为了减少频繁写 IndexedDB，有 3 秒延迟写入。

第二点是根因之一。也就是说：

1. 用户点重置。
2. Zustand 内存状态已经变了。
3. IndexedDB 里的旧状态可能还没来得及写入新值。
4. 用户立即刷新。
5. 应用从 IndexedDB 读到了旧运行态。
6. 旧专注倒计时又回来了。

这不是 UI 没刷新，而是持久化写入时序不适合“计时器运行态”。

### 2.3 解决方案

本轮做了三层修复。

第一层：重置和跳过必须完整清理运行态。

`resetTimer()` 现在会：

- 删除当前未完成 session。
- 把 timer 恢复到 work 初始时长。
- 清理 `_lastTickTimestamp`。

`completePhase()` 的兜底停止分支也会：

- 写回完整的 work 初始时长。
- 清理 `_lastTickTimestamp`。

第二层：番茄钟持久化改成即时写入。

在 `src/lib/idbStorage.ts` 中新增：

```ts
const IMMEDIATE_LOCAL_STORAGE_NAMES = new Set(['p2m-pomodoro-storage']);
```

当写入的是 `p2m-pomodoro-storage` 时，不再进入 3 秒延迟队列，而是直接 `await doLocalWrite(scopedName, value)`。

> 后续变化（2026-11-16 现状）：这个即时写入集合后续又加入了 `p2m-notification-storage`、`p2m-plugin-storage`、`p2m-ui-storage`（`src/lib/idbStorage.ts:49`），延迟队列仍是 3000ms。

第三层：明确临时/永久存储边界。

番茄钟数据现在按下面边界理解：

| 数据 | 性质 | 是否持久化 | 说明 |
| --- | --- | --- | --- |
| `config` | 永久 | 是，本地缓存 + 后台 v2 | 工作时长、休息时长、长休间隔、每日目标、背景音策略、当前背景音、各背景音音量、上次播放状态 |
| 已完成 session | 永久 | 是，本地缓存 + 后台 v2 | 用于统计、日历和历史记录 |
| 正在运行 timer | 临时运行态 | 是，本地即时 + 后台轻量快照 | 用于刷新恢复和局域网设备接续 |
| 未完成 active session | 临时运行态 | 是，本地即时 | 只在 timer 仍指向它时保留 |
| `_lastTickTimestamp` | 临时运行态 | 是，本地即时 | 用于刷新后扣减离线时间 |
| 重置后的 active session | 不保留 | 否 | 重置后必须从持久化恢复中消失 |

第四层：后台只同步关键状态，不同步每秒 tick。

前端每秒倒计时仍只在浏览器内完成。后台 `user_data` 只在开始、暂停、继续、重置、阶段完成、切换 Todo、设置变化、历史变化、15 秒 heartbeat、页面隐藏或关闭前写入。这样既能让局域网设备刷新后接上状态，也避免计时器每秒访问数据库。

### 2.4 测试覆盖

`src/__tests__/pomodoroStore.test.ts` 扩展到覆盖：

- 完成历史保留，未完成历史默认不算永久历史。
- running 状态刷新后扣减离线时间。
- paused 状态刷新后不扣减时间。
- 过期 running 状态恢复成 paused + `0`，不静默重置。
- reset 后刷新仍保持初始状态。
- skip 兜底后刷新仍保持 idle。
- 旧版本分钟制 `timeRemaining` 迁移成秒。
- config 作为永久数据保留。
- 关键事件会写入远程 runtime v2。
- 15 秒 heartbeat 只在 running 状态写入，idle 和 paused 不重复写。
- 后台 config/history/runtime 可以在新浏览器打开时恢复，并按离线时间推算剩余秒数。

## 3. 问题二：番茄钟不同用户和局域网同步边界

### 3.1 背景

之前用户提到在别的电脑或别的用户环境打开后，番茄钟信息“一团糟”。这类问题不能只看一个 store，要看它到底走后端同步还是本地 IndexedDB。

### 3.2 处理原则

最终方案不是“全本地”，也不是“每秒写后台”，而是混合模式：

- 浏览器本地负责每秒倒计时、声音播放和页面生命周期。
- 后台只保存可以恢复的关键状态：设置、完成历史和轻量运行快照。
- 本地 IndexedDB 继续作为缓存和离线兜底。
- 登录用户才做后台同步，未登录时继续纯本地模式。

`usePomodoroStore` 仍然保持：

```ts
storage: createJSONStorage(() => localOnlyStorage)
```

这样可以避免 Zustand 每秒 tick 触发远程持久化。远程同步改由 `src/lib/pomodoroSync.ts` 和 store 里的显式同步动作负责。

### 3.3 结果

- 同一浏览器、同一用户：先从本地缓存快速恢复，再合并后台 v2 数据。
- 同一浏览器、不同用户：本地缓存继续用 scoped key 隔离。
- 不同设备、同一账号：刷新后能恢复同一 Todo、同一阶段和接近真实的剩余时间。
- 所有客户端都关闭且当前阶段已经过期时，不自动记完成番茄；重新打开最多恢复成 0 秒暂停。
- 旧后台 `p2m-pomodoro-storage` 不再作为权威数据，避免迁移前的大 JSON 污染新状态。

后台 v2 键：

| 键 | 内容 | 合并规则 |
| --- | --- | --- |
| `p2m-pomodoro-config-v2` | 工作/休息时长、长休间隔、每日目标、环境音策略、当前环境音选择、各环境音音量、上次是否正在播放 | `updatedAt` 最新者为准 |
| `p2m-pomodoro-history-v2` | 已完成番茄历史 | 按 session id 合并 |
| `p2m-pomodoro-runtime-v2` | 状态、阶段、剩余秒数、上次同步时间、关联 Todo、当前 session、设备 ID、动作名 | `updatedAt` 最新者为准 |

背景音相关字段统一放在 `p2m-pomodoro-config-v2`，不再只存在浏览器本地：

- `ambientPlaybackMode`：`manual` 表示手动控制，休息阶段也持续播放；`focus` 表示只随专注计时播放。
- `ambientSound`：按钮状态，`none` 表示关闭，具体声音表示对应按钮亮起。
- `ambientVolumeBySound`：每个环境音独立音量，例如咖啡馆、雨声、壁炉各自保存。
- `ambientWasPlaying`：刷新或局域网另一台设备恢复时，用来判断手动模式下是否应该继续播放。

如果浏览器拒绝自动播放，前端会把 `ambientSound` 写回 `none`，并把 `ambientWasPlaying` 写回 `false`，避免“按钮亮着但实际没声音”的状态继续保留。

## 4. 问题三：主题刷新后回到默认皮肤

### 4.1 现象

用户切换皮肤后，刷新页面会回到默认主题。这个问题看起来像主题没保存，但实际更接近“主题应用时机不稳定”。

### 4.2 原因

旧逻辑里，应用主题依赖初始化过程中的延迟执行。异步恢复用户状态、Zustand 持久化 hydrate、React 首次渲染之间存在时序差。

如果主题应用早于 UI store 恢复，就可能应用默认主题。

### 4.3 解决方案

新增 `src/hooks/useApplyStoredTheme.ts`。

应用入口 `src/App.tsx` 现在在：

```ts
useApplyStoredTheme(initialized && Boolean(currentUser))
```

之后才根据 UI store 的 `themeId` / `customTheme` 应用主题。

这把“猜一个 timeout”改成了“等状态真的恢复后再应用”。

### 4.4 测试

契约测试锁住：

- `App.tsx` 必须使用 `useApplyStoredTheme(initialized && Boolean(currentUser))`。
- 不允许回到 `setTimeout(() => ...)` 的方式。
- hook 必须读取 `useUIStore`、`themeId`、`customTheme` 并调用 `applyTheme`。

## 5. 问题四：播放器雪碧图预览不稳定

### 5.1 现象

早期播放器进度条雪碧图预览有两个问题：

- 没生成时没有清晰反馈。
- 用 `<img>` + `objectPosition` 做帧定位，在实际浏览器里不够稳定。

### 5.2 解决方案

新增共享 hook：

```text
src/components/video/useSpriteMeta.ts
```

职责：

- 请求 `/api/videos/{id}/sprite`。
- 读取响应头 `X-Sprite-Meta`。
- 校验 `frame_width`、`frame_height`、`cols`、`rows`、`total_frames`。
- 返回 `idle/loading/ready/error` 状态。
- 提供固定尺寸和响应式两种背景定位 style 生成函数。

播放器进度预览 `SpritePreview.tsx` 改成：

- loading 时显示“生成预览中...”。
- error 时显示“暂无雪碧图”。
- ready 时用 `backgroundImage` 和 `backgroundPosition` 定位帧。

后端 `backend/app/main.py` 增加：

```py
expose_headers=["X-Sprite-Meta"]
```

否则浏览器 CORS 下前端读不到自定义响应头。

## 6. 问题五：视频主界面没有 hover 动态缩略预览

### 6.1 目标

用户希望视频主界面卡片也能像常见视频网站一样，鼠标悬停后自动预览片段。

### 6.2 设计约束

这个功能不能一进页面就请求所有雪碧图。因为视频列表可能很大，如果首页 20 个视频同时请求雪碧图，会把 ffmpeg 和磁盘压力拉满。

最终规则：

- 只在桌面端启用。
- 鼠标停留在封面区域约 450ms 后才启用。
- 离开封面立刻停止。
- 加载失败不显示错误文案，只回退静态缩略图。
- 不影响收藏按钮、时长角标和播放进度条层级。

### 6.3 实现

`VideoListSections.tsx` 新增卡片封面预览结构：

- `VideoCardPreviewFrame`
- `VideoCardThumbnail`

`VideoCardPreviewFrame` 负责：

- hover 延迟。
- 调用 `useSpriteMeta(previewEnabled ? video.id : null, enableSpritePreview)`。
- ready 后用 `setInterval` 每 450ms 切换帧。
- 用 `getResponsiveSpriteFrameStyle()` 生成响应式背景定位。

移动端通过：

```ts
const isMobile = useIsMobile();
enableSpritePreview={!isMobile}
```

禁用自动预览。

### 6.4 测试

Playwright 增加场景：

- 进入视频列表后等待 600ms，不应该请求 sprite。
- hover 视频封面后，才应该请求 `/api/videos/101/sprite`。

契约测试锁住：

- 列表卡片必须使用 `useSpriteMeta(previewEnabled ? video.id : null...)`。
- 必须有 `onMouseEnter` / `onMouseLeave`。
- 必须移动端禁用。

## 7. 问题六：雪碧图分辨率过低

### 7.1 现象

用户反馈雪碧图质量太低。排查后发现后端固定：

```py
FRAME_WIDTH = 160
```

这意味着每帧只有约 `160x90`。播放器预览宽度是 `180px`，视频主列表卡片通常更大，低清源被放大后必然发糊。

### 7.2 解决方案

后端 `backend/app/services/sprite.py` 改为读取可配置项：

```py
FRAME_WIDTH = max(160, int(settings.sprite_frame_width or 320))
FRAME_INTERVAL = max(1, int(settings.sprite_frame_interval or 5))
COLS = max(1, int(settings.sprite_columns or 10))
JPEG_QUALITY = min(31, max(1, int(settings.sprite_jpeg_quality or 2)))
```

`backend/app/database.py` 新增默认配置：

```py
sprite_frame_width: int = 320
sprite_frame_interval: int = 5
sprite_columns: int = 10
sprite_jpeg_quality: int = 2
```

所以 `.env` 可以写：

```env
SPRITE_FRAME_WIDTH=320
SPRITE_FRAME_INTERVAL=5
SPRITE_COLUMNS=10
SPRITE_JPEG_QUALITY=2
```

如果想更清晰，可以把宽度调到 `480`，但文件体积和生成耗时会明显增加。

### 7.3 老雪碧图自动过期

`has_sprite(video_id)` 不再只判断文件是否存在，还会读取 meta，确认：

- `frame_width`
- `frame_interval`
- `cols`
- `jpeg_quality`

必须和当前配置一致。

如果旧 meta 是 `160x90`，会被视为 stale，下次请求自动重建。

### 7.4 测试

新增：

```text
backend/tests/test_sprite_quality.py
```

覆盖：

- 默认 `FRAME_WIDTH >= 320`。
- 默认 `JPEG_QUALITY <= 2`。
- 旧 160 元数据会被认为过期。
- 当前配置元数据可以复用。

## 8. 问题七：Todo、日历1、日历2 排程联动

### 8.1 背景

待办、日历1、日历2 原本容易出现同一个任务在不同入口状态不一致的问题。尤其是日历2 拖动时，如果把拖动结果当成新建，就会出现“拖一下变两条”的现象；如果重叠事件按普通绝对定位直接铺满宽度，又会导致任务2 完全盖住任务1。

### 8.2 数据方案

新的方案以后台 `schedule_items` 作为统一排程源：

| 字段 | 说明 |
| --- | --- |
| `startAt` | 开始时间，精确到分钟 |
| `dueAt` | 截止时间，精确到分钟 |
| `sourceType` / `sourceId` | 关联 Todo、普通日历事件或其他来源 |
| `title` / `color` / `status` | 多视图共同展示所需的轻量信息 |

Todo、日历1、日历2 都从同一份排程数据派生展示。Todo 编辑时间、日历拖动、日历事件表单保存，都应该更新同一条 `schedule_items`，而不是在某个视图里再复制一条。

### 8.3 日历2 展示方案

日历2 的重叠处理只属于展示层：

- 同一天、同一时间段有冲突时，先计算冲突组。
- 组内事件分配列号和总列数。
- 每个事件只占自己的列宽，保留一点间距。
- 拖动时只更新当前事件的开始/截止时间，不改变其他事件。

这样同一时间出现任务1和任务2时，两条都会显示出来；任务2 不会完全盖住任务1。日历1 暂不引入这套视觉分列，避免影响已有月/周视图。

### 8.4 Todo 右侧专注按钮

Todo 不再要求用户额外勾选番茄钟时间。只要任务有开始时间和截止时间，右侧专注按钮就可以按时间段自动计算需要的番茄数。

计算规则按当前番茄设置走：

- 默认 `25 + 5` 分钟时，2 小时给 4 个番茄。
- 如果是 `35 + 5` 分钟，则按完整 focus 轮次向下取整。
- 优先保证 focus 轮次能跑完，不为了填满时间强行增加半个番茄。

## 11. 设计原则沉淀

### 11.1 计时器状态不能只靠内存

番茄钟这种功能，用户天然会刷新页面、切页面、关浏览器。运行态可以持久化，但必须有明确边界：

- 正在运行可以恢复。
- 重置后不能恢复。
- 过期后不能静默变成新一轮。
- 写入不能被延迟队列拖后腿。

### 11.2 永久历史和临时运行态不能混在一起

完成 session 是历史。未完成 active session 是运行态。它们都在同一个 store 中，但业务意义完全不同。

测试必须覆盖这个差异，否则很容易出现“清历史把当前运行也清了”或“重置后未完成 session 又恢复了”。

后台同步也要遵守这个差异：历史按 session id 合并，运行态只保存可推算的小快照。清空本地历史后，如果远程历史更新时间更旧，不能再把旧远程记录合回来。

### 11.3 远程同步不能接管每秒倒计时

番茄钟跨设备恢复需要后台状态，但不能让后台承担实时计时。

- 每秒 tick 只发生在浏览器。
- 开始、暂停、继续、重置、阶段完成和切换 Todo 立即写后台。
- running 状态每 15 秒写一次 heartbeat。
- 页面隐藏、刷新或关闭前补写一次快照。
- 多设备冲突先按 `updatedAt` 最新者为准，后续再补显式接管 UI。

### 11.4 Todo 和两个日历必须共享同一排程源

Todo、日历1、日历2 不再各自维护一份时间状态。统一用 `schedule_items` 作为后台主表，可以避免：

- Todo 改了时间，日历没同步。
- 日历2 拖动后新增一条重复事件。
- 同一个任务在不同视图里开始/截止时间不一致。

日历2 的重叠显示是展示层能力，不应该改变 `schedule_items` 的数据语义。

### 11.5 预览图要按需，不要批量

雪碧图生成依赖 ffmpeg。任何会触发 ffmpeg 的功能都应该：

- hover 后再加载。
- 可失败回退。
- 不阻塞列表。
- 不在首页批量生成。

### 11.6 可配置质量比写死参数更稳

固定 `160px` 在开发期够用，但真实 UI 会放大。雪碧图这类素材应至少暴露基础配置：

- 单帧宽度。
- 采样间隔。
- tile 列数。
- JPEG 质量。

### 11.7 契约测试适合锁结构边界

很多问题不是单元测试能完全捕捉的，比如“不要回到 setTimeout 应用主题”“不要一进页面请求 sprite”。这类适合用轻量契约测试锁住关键代码结构。

## 12. 下一步升级点

> 后续变化（2026-11-16 复核）：本章列出的媒体素材队列、雪碧图质量档位 UI、旧图批量重建入口、番茄多设备接管提示、真实后端 smoke、AI 任务中心 e2e 截至本次校对均未落地（无对应 service / 测试文件），逐条状态见 `docs/2.6-roadmap.md`。

### 12.1 媒体素材生成队列

雪碧图和缩略图现在仍偏按需生成。下一步可以做统一媒体素材队列：

- 待生成数量。
- 当前生成中。
- 失败原因。
- 暂停/继续。
- 重试失败。
- 每轮上限。
- 后台低优先级生成。

### 12.2 雪碧图质量档位 UI

当前质量可通过 `.env` 调。后续可在设置页增加：

- 标准：`320px`
- 高清：`480px`
- 极清：`640px`

并提示文件体积和生成耗时。

### 12.3 旧雪碧图批量重建入口

现在旧图是访问时自动重建。后续可以增加管理按钮：

- 扫描低清雪碧图数量。
- 批量重建当前文件夹。
- 批量重建全部视频。
- 支持暂停。

### 12.4 番茄钟多设备接管提示

番茄钟 v2 已经同步设置、完成历史和轻量运行态。下一步不再是“是否同步历史”，而是把多设备冲突提示做清楚：

- 另一台设备刚刚开始或继续番茄时，本机刷新后给出来源提示。
- 当前设备准备覆盖运行态时，提示这是接管当前番茄。
- 展示最近一次写入的设备 ID、动作名和更新时间。
- 保持默认规则简单：没有人工选择时仍按 `updatedAt` 最新者为准。

### 12.5 番茄真实后端 smoke

现有测试已经覆盖同步服务和 store 行为。后续还需要一条真实后端 smoke，专门验证局域网链路：

- A 设备开始番茄并关联 Todo。
- B 设备刷新后恢复同一 Todo、同一阶段和接近真实的剩余秒数。
- 暂停、继续、重置后刷新保持一致。
- 完成历史在两个设备产生不同 session 时按 id 合并。

### 12.6 真实后端 smoke 测试

2.6 已经强化了 mock 和单元测试。下一步建议增加可选真实后端 smoke：

- 登录。
- 打开视频页。
- 读取视频列表。
- 读取 AI 设置。
- 读取健康检查。
- 不做破坏性操作。

账号密码必须通过环境变量传入，不写入仓库。

### 12.7 AI 任务中心 e2e

继续把之前最容易乱的批处理规则锁住：

- 继续未完成。
- 全部重跑。
- 只失败。
- 只补字幕。
- 只补总结。
- 外部 LLM 总结成功也算完成。

## 13. 结论

2.6 的核心价值是把“看起来能用”的状态改成“刷新后仍可信”的状态，把“能显示预览”改成“清晰、按需、可配置、可测试”的预览。

这轮没有追求新功能数量，而是解决真实使用中的几个硬问题：

- 番茄钟不再被旧持久化状态拖回去。
- 番茄钟配置、完成历史和轻量运行态可以通过后台 v2 数据在局域网设备间恢复。
- 番茄钟背景音的策略、选中按钮、分声音量和上次播放状态进入后台配置，刷新后不会只恢复按钮而丢失播放判断。
- Todo、日历1、日历2 统一到 `schedule_items`，开始/截止时间按分钟保存。
- 日历2 重叠任务不再互相覆盖，拖动更新也不再生成重复事件。
- 主题刷新恢复更稳定。
- 视频雪碧图预览从播放器扩展到列表卡片。
- 雪碧图清晰度达到更适合当前 UI 的默认水平。
- 测试覆盖从前端扩展到后端质量配置。

这让 2.6 更适合作为后续继续做媒体素材队列、真实后端 smoke、AI 任务中心 e2e 和番茄多设备接管提示的基础版本。
