# 可迁移的经验

> 状态：现行经验清单（2026-11-16 校对）。故障模式与检查清单仍成立；所举历史实例的修复状态已就地标注。

从这轮改造里提炼的**问题模式**，不是「我做了什么」。

每一条都能脱离这个项目单独成立 —— 换一个系统，同样的症状还会出现。

> 配套文档：`docs/maintainability.md` —— 那份讲**工作方法**（动手前问什么、怎么验证、卡住往哪查、先改什么）。
> 这份讲**故障模式**（哪些 bug 不报错）。建议一起看。

## 一、八种「不报错但错了」的问题

这类问题最贵。因为它们不抛异常、不留日志，只有主动去验证才会发现。

### 1. 统计口径错了，但数字看起来很合理

**症状**：报「近 7 天学习 44 分钟」，实际 338 分钟，差 8 倍。
**根因**：`取最近 200 条明细 → 求和`。200 条只覆盖不到一天。
**特征**：44 分钟不多不少，是个「像真的」的数字，没有任何异常信号。

**怎么防**：有 `LIMIT` 的地方不能求和。聚合走 SQL，明细才 `LIMIT`。

### 2. 隔离写了，但没生效

**症状**：多用户下画像把所有用户的数据加在一起算。
**根因**：

```python
resolved_id = resolve_user_id(db, user_id)   # 算出了真实 id
if user_id is not None:                      # 但用的是入参
    query = query.filter(WatchEvent.user_id == user_id)
```

入参永远是 `None`（调用方不传），所以 `if` 永远不成立，等于统计全库。

**特征**：代码读起来完全正确。`if user_id is not None` 是标准写法。

**怎么防**：隔离逻辑必须能被**执行结果证伪**。
造两个用户，各写一条数据，互相查一次。不这么做只能算「写了隔离代码」。

### 3. 字段有了，但从来没人写

**症状**：`watch_events.user_id` 有列、有索引，但全是 NULL。
**根因**：加字段时改了模型，没改写入路径。（该实例已修：写入路径现在绑定 `user_id`。）

**怎么防**：加隔离字段的同一个 PR 里，必须有一条写入测试。
空字段比没有字段更危险 —— 它让人以为「已经隔离了」。

### 4. 假成功：界面说改好了，其实没改

**症状**：设置页「修改密码」提示成功，下次还能用旧密码。
**根因**：改的是浏览器 IndexedDB 的哈希，后端完全不知道。
`upsertUser()` 确实成功了 —— 改错了地方。（该实例已修：改走 `POST /api/auth/change-password`，服务端 `token_version + 1`。）

**怎么防**：**写完之后，从另一条路径读一次。**
改完密码就用新密码登录一次。30 秒的成本。

### 5. 只在第一次点击时正确

**症状**：勾选学习步骤后卡片收起，想再点「完成」得重新展开。
**根因**：操作后整页 `loading`，组件卸载重建，`useState` 重新初始化。

**怎么防**：任何「操作后需要再操作一次」的流程，连点两次验证。
单元测试测不出来（store 是 mock 的，不重渲染）。

### 6. 切换身份时的写入竞态

**症状**：A 的笔记写进了 B 的账户。
**根因**：写盘有 3 秒 debounce，期间切换了账号，定时器触发时用的是新会话。（该实例已修：登出先 flush 再清会话、IDB key 加用户前缀、切号整页重载。）

**怎么防**：
- 登出前**先 flush 再清会话**（顺序反了数据就丢）
- 本地存储 key 带用户前缀
- 切换账号**整页重载** —— 笨但不会漏

### 7. 异常类型名骗人

**症状**：全量回填报 `DiskFull`，但磁盘还剩 334GB。
**根因**：容器 `/dev/shm` 默认 64MB，PostgreSQL 的并行查询（`work_mem` 64MB × 2）撑爆它。

**怎么防**：**别拿异常类型名当诊断结论。**
顺着报错里的名词往下找 —— 它说的是「共享内存段无法扩展」，不是「磁盘满」。

### 8. 默认值假设了错误的使用模式

- autovacuum 默认阈值适合持续小批量写入，不适合一次性导入 359 万行
- Redis 默认 `maxmemory 0` 适合专用缓存，不适合和业务共存的队列
- `ENABLE_DOCS` 默认 `true` 适合开发，不适合公网（该实例已修：现行 `database.py:147` `enable_docs` 默认 `False`，文档站仅在显式开启时暴露）

**怎么防**：用之前问一句「这个默认值假设的使用模式，和我的实际情况一样吗？」

## 二、四类「以为做了，其实没做」

### 1. 「有配置」不等于「有实现」

项目里曾经有 `use_langchain: true` 这样的开关，看起来接了 LangChain，
实际代码根本没走那条路。**开关是承诺，代码才是事实。**

> 历史实例：该假开关已不存在；现行 `agents/chat_agent.py`、`agents/tools.py`、`services/llm.py`
> 真实 import `langchain_core` / `langchain_openai`。教训本身仍成立：判断接入与否要看代码调用，不看配置位。

### 2. 「有鉴权」不等于「有权限」

`/api/admin/*` 有 22 个端点，全都没有 `Depends(...)`。
不是不会写，是**从来没问过「谁能访问这个路径」**。

> 该实例已修：`routers/admin.py:60` 在 router 级挂 `dependencies=[Depends(require_admin)]`，
> 该路由下全部端点受管理员依赖保护；个别单端点（如 `delete_user`）另在函数级重复声明。

自检：列出所有写方法端点，逐个问「谁该能调」。答不上来的就是缺口。

### 3. 「有降级」不等于「降级是对的」

`/health` 返回 `degraded` 但 HTTP 200 —— 探针认为健康，实际数据库连不上。
降级要能让调用方做出不同决策，否则只是把错误藏起来。

### 4. 「有文档」不等于「有人看」

写了十页安全指南，不如把 `ALLOW_REGISTRATION` 默认值改成 `false`。

**没人读文档，但所有人都会用默认值。**

## 三、可以复用的检查清单

### 上线前（16 项，跑脚本）

```bash
./scripts/preflight.sh https://your-domain
```

关键是**它能跑**。清单会忘，脚本每次都会跑 ——
这一轮唯一一个「装了锁没配钥匙」的问题（`JWT_SECRET` 还是示例值）就是脚本抓出来的。

### 多用户隔离（手工，5 分钟）

1. 造 A、B 两个账号
2. A 建一条数据，B 查一次 → 必须看不到
3. B 直接访问 A 的资源 id → 必须 404（不是 403，403 会暴露 id 存在）
4. B 调管理端 → 403
5. 登出 A、登录 B、刷新页面 → 不能看到 A 的任何内容

### 查询性能（改完索引或导入数据后）

```sql
-- 统计信息是否新鲜
SELECT relname, n_live_tup, last_analyze FROM pg_stat_user_tables
WHERE n_live_tup > 100000 AND last_analyze IS NULL;

-- 索引是否真的被用
SELECT relname, idx_scan FROM pg_stat_user_indexes
WHERE idx_scan = 0 ORDER BY pg_relation_size(indexrelid) DESC LIMIT 10;
```

第二条尤其有用：**建了索引但 `idx_scan = 0`，说明要么查询没走它，要么这个索引白占空间。**

## 四、判断「能不能上线」的框架

不要问「能不能上线」，问四个更具体的问题：

| 问题 | 不合格的表现 |
|---|---|
| 凭证放在哪？被偷了会怎样？ | localStorage、URL 参数、日志里 |
| 数据边界在哪？越权怎么发现？ | 「应该没问题」 |
| 出问题能退回去吗？多久？ | 只能重装 |
| 崩了怎么知道？ | 等用户来投诉 |

四个都能立刻答上来，才算能上线。

## 五、这个项目现在还差什么（诚实版）

面试时主动说这些，比被问出来好：

- **没有组织/团队概念**：`user_id` 是唯一隔离维度，做不了「一个团队共享一份视频库」
- **视频库全局共享**：产品选择，不是疏漏；做 SaaS 需要 `tenant_id` 贯穿所有表
- **没有审计日志**：谁改了谁的权限查不到
- **没有配额计费**：有每日上限，但没有按量计费和账单
- **没有 refresh token**：12 小时过期 + 改密码即撤销，够用但不是标准做法
- **单进程线程池**：多副本部署需要分布式锁

这些不是「补个功能」，是数据模型层面的重构。**说清楚边界比声称什么都能干可信。**
